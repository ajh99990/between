# 人物什么时候才算看过一条消息

临时试稿 · 2026-10-25 · 依据 Between 固定版本 `c5fddc8d3b3ae81b77d41cba4cede78286e8dd0d` 的待实施设计。

上午十点，甲发来一句：“今天有点累。”

系统收到并保存了这句话，人物什么时候才算看过？方案以**正文实际提供给人物模型**为界：收到消息以后，系统先保管它；人物选择查看，程序再把保存的正文交给模型。这中间可以相隔一段时间。

下面就沿着这一条来信往下走。假定人物所需的既有背景已经准备好，此刻也允许接收甲的通知。先看她选择打开消息的正常过程，再看系统怎样保存和使用这次读取的记录。

## 保存来信，让人物知道有消息可看

收件入口保存“今天有点累”的原文，并留下收到时间、正文位置和处理进度。方案把这样的来信记录叫作 `InboxItem`。它让后面的程序能找到这条消息，也能继续记录它何时实际提供给模型。[^1]

此刻给人物的是通知概况，例如：“甲在十点发来一条消息。”允许出现的信息包括来源对象、通道、收到时间和条数。正文摘要、关键词、图片识别结果，以及根据正文算出的情绪，都在读取之后才可进入人物理解。

这个范围直接决定了“打开消息”是否有意义。人物此时知道甲发了消息，还不知道甲说自己累；她可以根据既有背景决定现在看，也可以先不看。提供无正文概况的拟议工具叫 `inbox.list`。[^2]

通知机会受人物当前的注意安排控制。默认允许通知；已有暂不查看的安排时，新来信仍存入收件箱，等到相应处理机会再由人物选择查看。收件入口可以照常保存、校验签名和去重，收件本身不要求每条消息立即调用模型。[^2]

## 选择打开后，正文怎样进入模型

这一次，人物模型选择打开甲的消息，调用拟议工具 `inbox.read`，请求读取指定来信。

服务先检查本次处理允许读取的对象和消息范围。权限符合时，从保存的来信取得正文，将它提供给人物模型；越界请求则返回失败。私聊处理固定在同一个联系人范围内，所以这次处理甲的消息，所用材料也按甲的范围准备。[^3]

这里有两个相接的模型步骤。前一步面对背景和通知概况，作出“查看”的选择；中间由程序调用工具取出原文；后一步拿到“今天有点累”，再理解甲在说什么、判断接下来做什么。方案允许一次人物运行包含多次“模型 → 工具 → 模型”，这两个步骤可以属于同一次运行。[^3]

程序为每一次模型请求准备输入时，都会固定这一份输入包含的消息 ID 列表和一个名为 `cutoff` 的输入截止标记。这样，每次请求包含哪些消息就有了明确范围。若甲在生成期间又发来一句，新来信先保存到收件箱，下一处理步骤重新决定是否查看。[^4]

到这里，甲的这条原文已经进入人物输入。读取这件事完成了；是否回复、怎样回复，继续由模型判断。

## 用一条记录说明何时真正提供过

假设正文是在十点零二分提供给模型的。十点是系统收件的时间，十点零二分才是本次处理获得正文的时间。

后续交流需要知道这条差别：人物下次与甲说话时，哪些原话已经可以使用？后台整理材料时，哪些消息已经进入过人物输入？因此，除了保存来信，还要保存它实际提供给模型的记录。方案称之为 `Exposure`，并给出了三个明确的内容：[^5]

```text
Exposure(run_id, item_id, exposed_at)
```

| 内容 | 在这一条来信中记录什么 |
| --- | --- |
| `run_id` | 哪次人物运行接触了正文。本例中，从通知选择读取、再理解所取正文，可以属于同一次运行。 |
| `item_id` | 实际提供的是哪条来信，用它关联回甲的原文。 |
| `exposed_at` | 正文实际提供的时刻，本例为十点零二分。 |

读取服务负责保存实际的 `Exposure`。以后查询这次人物运行，就能回查它接触过的来信；查询甲这条来信，也能区分收件和实际提供的时间。[^5]

这些业务记录保存在 PostgreSQL。现行存储选择是关系键、时间、版本使用列，结构化内容使用 JSON；`InboxItem` 和 `Exposure` 分别描述来信与实际提供，物理表怎样划分仍需细化。[^6]

## 读取记录怎样影响后续使用

后续上下文构造和后台整理都按实际提供记录筛选材料。在甲这条消息尚未提供给人物模型时，正文保持隔离：它不会成为人物回复、情绪评价、画像提取、梦与反思、生活生成或公开选题模型的输入。这个限制也覆盖“另一个模型先分析正文，再把结论交给人物”的间接路径。[^7]

实际提供以后，“今天有点累”就可以在甲这一联系人的允许范围内用于后续交流。后台也可以从已查看的消息中提出值得记住的材料，并保留来源，供后续验证和保存；即使人物尚未回复，也有这个入口。是否值得成为长期记忆，是接下来记忆机制要处理的问题。[^7]

读取记录与权限各自发挥作用：前者说明人物接触过什么，后者决定这次可以使用什么。以后再次读取原文或来源引用时，服务仍检查范围；甲的私聊原文继续受甲的范围限制。[^8]

## “看过”说明到哪里

在这套机制中，“看过”具体指正文实际提供给模型。它记录的是输入事实，模型是否正确理解，还要看后续判断。人物也可以看过而暂不回复，因此查看记录与回复状态分别表达不同的事情。[^5][^9]

这一区别也适用于读取没有完成的情况。人物选择不打开，消息继续保存在收件箱；请求未通过权限检查，服务返回失败；正文尚未实际提供时，读取意图本身还不能记为一次实际提供。

## 实现时还要细化什么

来信、实际提供、读取权限和输入范围的职责已经明确。具体实现还缺少以下细节：

- `InboxItem`、`Exposure` 的完整表结构、唯一约束，以及 `inbox.list / inbox.read` 的完整参数、返回结构和错误码。
- `cutoff` 的具体表示、构造方式及其与消息 ID 列表的配合规则；生成期间新到消息在下一处理步骤如何衔接运行。
- 实际提供的确认方式，以及模型请求与提供记录写入的准确顺序。例如，请求发出后连接中断，或者实际提供后记录写入失败，怎样核对、补记与处理重复提供，尚未形成完整协议。[^10]

因此，实现这一步既要能保存消息、按范围读取，也要让实际提供记录与模型输入相符。前面描述的是业务过程，模型请求和数据库写入之间的失败衔接，需要在上述细化中落实。

这条来信现在走完了保存、选择读取、进入模型输入和留下记录的过程。沿着同一个例子，后续可以再增加一个情况：人物选择晚一点看。那时再讲这个选择怎样保存、到时怎样重新获得处理机会。
