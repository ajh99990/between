# 选择稍后再看以后，谁来提醒

临时重组稿 · 2026-10-25 · 依据 Between 固定版本 `c5fddc8d3b3ae81b77d41cba4cede78286e8dd0d` 的待实施设计。

上午十点，甲发来一句：“今天有点累。”

沿用[上一篇](01-人物什么时候才算看过一条消息.md)的前提：人物所需的既有背景已经准备好，此刻也允许接收甲的通知。系统保存原文，人物获得“甲发来一条消息”的概况。这次她选择先不打开，十点半再看甲的消息。

这个选择需要在本次模型调用结束后继续有效。十点到十点半之间，程序要知道甲的正文仍应留在收件箱；十点半到了，即使甲没有再发消息，也要有人把这件事交回人物判断。前一部分由保存下来的注意安排表达，后一部分由持久化的到期任务续接。[^1]

## 把“十点半再看”保存下来

人物模型作出选择后，通过拟议工具 `attention.set` 提交注意范围和复看时刻。本例的范围是甲这一段关系，复看时刻是十点半。在这之前暂不查看甲的新消息，并不同时表示所有其他通道或联系人都被关闭。方案也允许把范围选为全局普通消息或某个通道；采用哪种范围，要随这次选择明确保存。[^2]

这份记录叫作 `AttentionPlan`。入站调度读取它，判断当前有哪些通知机会；上下文构造程序读取它，准备这次处理可以使用的材料。服务负责检查请求的权限、时间和版本，保存后把结果交回模型。人物负责选择，工具和服务负责让这个选择成为后续程序可读的状态。[^3]

注意安排还需要配套保存“到十点半再处理一次”的任务。方案把这种未来处理机会叫作 `WakeJob`。它不会预先替人物写好十点半的回复；它留下的是一件到时要重新判断的事。已有设计给出了这类任务至少需要表达的内容：[^4]

| 内容 | 在这次安排中起什么作用 |
| --- | --- |
| 为何唤醒 | 因为人物选择了稍后重新查看消息。 |
| 关联哪件事 | 能找到这次注意安排，知道需要复看的范围是甲。 |
| 到期时间 | 到十点半取得新的处理机会。 |
| 是否仍有效 | 后来领取时，能检查这次机会是否已经取消或被新安排替代。 |
| 处理状态 | 能区分这件事尚待处理、已经处理，或留下了需要恢复的失败。 |

这些是业务内容，还不是完整字段或状态枚举。服务和调度器保存、维护这类记录，运行协调器在到期时领取。与上一篇的来信一样，业务记录和任务保存在 PostgreSQL；注意安排与到期任务怎样划分物理表，仍需在实现时细化。[^4][^5]

本例的十点半是人物作出的示例选择，不是所有未读消息都采用的固定等待时长。文中的时刻按首版人物时区 `Asia/Shanghai` 解释，系统存储使用 UTC。[^6]

## 等待期间，新消息怎样处理

保存后的注意安排继续约束收件和输入准备。甲再发一条消息时，入口照常保存原文、收件时间和处理进度；本例的暂不查看安排仍有效，正文继续留在收件箱。收件入口可以校验签名和去重，这些机械处理不需要先让人物理解正文。[^7]

在人物被允许获得通知概况时，概况仍只有来源对象、通道、收到时间和条数。摘要、关键词、图片识别结果，以及从正文推算的情绪，都要等实际读取以后才能使用。上一篇的实际提供边界在等待期间同样生效，包括后台整理材料的路径。[^7]

默认允许通知机会，是没有另外选择暂不查看时的默认行为。已经保存的注意安排则表达这段时间的具体选择。忙碌程度可以成为人物作选择时的材料，程序不会按一个忙碌分数直接替她静音。首版也不先读取未读正文来判断是否紧急；发送者自称“紧急”，不能据此突破已经生效的暂不查看安排。[^2][^8]

后台可以定时查询到期任务。只有真实到期、可见通知、有效结果或恢复事项，才构成人物运行的触发条件；保存每条新来信，并不要求立刻调用一次模型。扫描间隔属于工程参数，现有设计没有给它一个具体数值。[^9]

## 十点半到时，重新交给人物选择

这次没有新安排替代原选择。到十点半，运行协调器领取复看任务，读取最新状态，检查这条触发是否仍然有效。如果它已经取消或被替代，便不再按原来的十点半安排继续处理。[^10]

对仍有效的任务，程序准备当前时间、当下仍适用的背景和收件箱概况。甲的正文此时仍未自动进入输入。模型拿到的是一次新的选择机会，可以决定查看甲的哪些消息，也可以继续延后或暂不行动。[^10]

假设她这次选择打开甲的原消息，后续就回到上一篇的读取过程：调用 `inbox.read`，服务检查允许的对象和消息范围，把保存的正文实际提供给模型，并留下 `Exposure`。直到这一步，她才获得“今天有点累”的内容；是否回复、怎样回复，继续由模型判断。[^11]

如果人物仍选择稍后看，就保存新的注意安排和相应的复看机会。写入仍经过服务检查，保存成功后才作为成功结果交给模型。本次到期处理据实际执行情况完成，或留下可恢复的失败；“到期任务处理过”本身不代表所有消息都已读，也不代表已经回复甲。[^10]

## 每次复看仍有自己的范围

本例处理甲，准备的私聊材料就固定在甲的范围内。若几个联系人的处理机会同时到期，调度器分别领取相应运行、重新准备各自的材料；同时到期不会把不同私聊正文合成一份人物输入。[^12]

同一个对象的输入也有边界。每次模型请求固定消息 ID 列表和输入截止标记 `cutoff`；甲在模型生成期间又发来的内容先保存到收件箱，下一处理步骤重新决定是否查看。这样，十点半开始的一次处理使用了哪些来信，仍然能回到上一篇的实际提供记录核对。[^13]

注意安排约束接下来是否查看，已经实际提供的记录说明此前接触过什么。人物稍后决定暂不看新消息，不会把已经看过的内容重新变成未读。至于已经读到、但想晚些认真处理的问题，还需要保存另一类责任，后面的[第 05 篇](05-改了安排以后还记得欠谁什么.md)会接着讲。[^14]

## 到期稍晚，或者处理没有完成

如果服务稍晚才取得处理机会，程序使用执行当时的时间和最新状态，让人物从现在作判断，记录的也是这次真正执行的时间。已经过时的触发按当前有效性处理，不补造一次十点半准时发生的决定。[^15]

服务中断时，已经保存的来信、注意安排、关联唤醒和未完成事项，仍是恢复处理的依据。系统恢复以后重新判断这些记录的当前状态。这里的延迟属于运行情况，需要与人物主动选择暂不查看分别记录；它没有自动形成一段人物故意冷落甲的经历。更完整的领取、并发和重启恢复过程由[第 11 篇](11-工具没做完时人物怎样继续行动.md)展开。[^15]

保存新安排失败与执行已保存的安排失败，也发生在不同位置。前者尚未取得新安排生效的确认；后者已有持久记录，需要留下可恢复的失败。对没有取得确认的请求，当前能依据的仍是已确认记录，不能据此宣布已经改为十点半或已经查看完毕。若请求中断使保存或实际提供的结果无法确定，这一结果应保持待核对；已有设计尚未给出完整的核对、补记和重试协议。[^16]

如果到期判断还停在只提供通知概况的阶段，模型调用失败时，甲的正文仍未实际提供。若流程已经走到提供正文，则按实际提供情况核对，不能用模型是否成功回答来反推有没有看过。保存来信、保存安排、处理到期机会、实际提供正文，各自留下自己的结果；恢复时据这些结果接续。[^10][^11][^16]

## 实现时还要细化什么

注意范围、默认通知、持久复看、到期重新选择和未读隔离已经确定，以下细节仍需落实：

- `AttentionPlan`、`WakeJob` 的完整字段、索引、状态与唯一约束，以及 `attention.set` 的参数、返回结构和错误码。
- 全局、通道、关系三种注意范围同时存在或发生变化时，怎样计算重叠规则的优先级和覆盖关系。
- 注意安排与复看任务配套保存的完整失败处理；请求超时、结果未知、部分写入时如何核对与恢复。
- 外部模型请求和实际提供记录之间的失败衔接，包括连接中断、记录写入失败和重复提供；这一缺口沿用上一篇，不能用“任务已处理”替代提供结果。
- 扫描间隔、领取失败后的重试参数和重新获得处理机会的具体调度配置。[^17]

十点半这次复看若最终完成读取，甲的原话就进入了人物的已知材料；若人物继续延后，下一次机会仍由保存的安排续接。选择、持久记录和到期处理共同让“稍后再看”在两次模型调用之间继续有效。
