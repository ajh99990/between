# 改了安排以后，还记得欠谁什么

临时重组稿 · 2026-10-25 · 依据 Between 固定版本 `c5fddc8d3b3ae81b77d41cba4cede78286e8dd0d` 的待实施设计。

继续前面的例子。甲的消息已经实际提供给人物模型，人物也有自己的日常安排。接着，甲发来一个请求：“晚点能帮我看看这份资料吗？”她想认真看，但眼下还有自己的事，决定稍后处理。

这里出现了两个不同问题：她准备什么时候做，以及她已经对甲承担了什么责任。未来安排可以变化，已经看见的请求和已经说出的承诺却需要继续有依据。系统因此分别保存计划、待处理事项和实际结果，再在下一次处理机会把它们接起来。[^duty-main]

## 先判断这件事处在哪一种责任里

同样是“以后再做”，可能来自三种不同过程。

第一种是她自己想做。看到一张有趣的图，她想到之后可以发给甲，但尚未说出口。系统可以保存这个念头、复看时间和失效条件；重新看到它时，她也可以决定不发。此时还没有对甲形成发送图片的责任。

第二种是她已经看到甲的请求，打算稍后处理。需要留下原问题、当下处境、她为什么延后、准备何时复看。她可以先短答，也可以暂时不回复；只要尚未发出承诺，这仍是内部已看待办。

第三种是她明确向甲作出承诺，例如“八点发给你”。这时记录需要能回查实际发送成功的原话、对象、时间及履行条件。到了八点，系统不仅要知道有件事可做，还要知道她已经向谁说过什么。[^duty-kinds]

方案将这三类事项放在同一个可查询的业务对象 `Commitment` 中，用已经选定的 `kind` 区分：

| `kind` | 责任含义 | 后续处理依据 |
| --- | --- | --- |
| `private_intent` | 尚未表达的自身意图 | 动机、复看时间、失效条件；重访时可以放弃 |
| `known_pending` | 已经知道、尚待处理的事项 | 原问题与来源、当时处境、延后理由、复看时间；有短答时关联其记录 |
| `expressed_promise` | 已经向对方表达的承诺 | 实际发送成功原话、目标、时间和履行条件；继续记录失败、改期和告知 |

名称里的“承诺”不能掩盖三种不同含义。真正的对外责任只属于第三种。它也不等于一根关系进度条：愿意继续交流、接受道歉、相信以后会履约，可以分别变化；一次答应先建立预期，实际履约才提供行动证据。[^duty-kinds]

## 从模型的决定，到服务保存的事项

模型结合已经读到的请求与当前处境，决定要不要留待处理，以及怎样表达。拟议的 `commitment.record` 把事项种类、原话或其他来源、复看时间和履行条件交给服务；服务检查本次范围、来源、时间与版本，成功后保存为后续可以查询的事项。需要未来处理时，再关联对应的持久唤醒。[^duty-record]

这条显式写入发生在当前运行内。记忆整理以后可以提炼有价值的材料，但即时责任不依赖后台从自然语言里猜出一次承诺，更不能把任意一句“以后看看”自动认定为已经发出的约定。

如果人物同时选择短答，短答与内部待办需要协同记录。它们保存的事实不同：待办说明她已经知道并准备后续处理；出站记录说明这句话是否实际发出。短答投递失败，内部待办依然在，但对方收到“稍后回复”的承诺尚未成立。[^duty-delivery]

发送结果未知时，也保留这个未知。模型生成了“八点发给你”的文字、准备发送、发送结果已确认，是不同环节。当前方案尚未给出所有发送失败与业务写入之间的完整同步协议；这里不能用“一个原子事务”跳过外部投递的不确定性。后面的运行与平台机制会解释已知失败和未知结果怎样继续核查。

## 到期以后，重新处理哪一件事

现在假设甲的资料请求已经留作待办。到复看时间，程序取回的是甲这件事的原问题、已发短答、延后理由、期限、已有结果和最新处境。模型据此决定现在完成、协商改期，还是确认已无须继续。[^duty-due]

到期只产生新的处理机会，不自动发出原先模板，也不把原问题标为解决。拟议的 `commitment.resolve` 需要有相应依据。对于需要执行动作的责任，真实结果成功且满足原履行条件后才可解决；如果取消或已经无须继续，则保存实际判断和处理依据，而不是让事项悄悄消失。

这个过程始终在甲的范围内取材。乙的消息也到期时，程序分别处理相应对象的运行；不能把两人的私聊正文合在一个模型输入里。过时的共享生活检查可以合并，欠不同人的事情仍逐件保留。[^duty-due]

注意安排和待办时间也各自有效。例如，她留下十点四十分再处理甲，同时选择十点三十五分再看新消息。十点三十五分到时，可以先选择看乙；十点四十分再取回甲的原问题和材料。这两个时间是示例，不是默认配置；它们展示的是“什么时候愿意看新消息”和“什么时候回来处理已经知道的事情”如何分别保存。

### 新消息怎样影响旧事项

甲又来一句无关闲聊，原资料请求继续存在。若甲说“那算了”，这条消息仍须先经过实际读取，模型才判断它取消的是不是这个请求，并留下取消依据。系统不采用“只要有新消息就删除旧延期”的规则。[^duty-cancel]

同样，改日程、结束谈话、睡觉，都不会自行清掉这条责任。人物可以重新商量时间，也可以确认不再继续；这些变化需要有记录，而不是由聊天轮数或一个新话题触发自动归零。

## 未来计划为什么另存

她本来准备下午整理图片，现在想把一段时间留给甲的资料。系统需要能比较原安排、拟议改动以及受到影响的其他事项。

这类未来安排叫作 `ActivityPlan`。它采用可滚动修订的粗日程，爱好也可以提前占用时间；当前活动另有复核点，不要求预先把每天排满。它保存打算何时做什么，包括起止时间、人物时区、内容、修订版本和相关约定引用。日程服务保存并修订它；当日安排、时间冲突检查和唤醒器随后读取。[^plan-meaning]

计划与上一篇的当前处境、事件分别承担任务。计划表示准备做，当前处境表示目前采用的活动与已知进展，事件记录收到、选择、尝试或发生的经过。甲在做饭期间聊了一件事，可以留下独立对话和事件，不必追加进“做饭”的日程正文。事件也可以没有日程关联；时间重叠本身不证明两人共同参加某项活动。

安排还具有 `planned / in_progress / closed / canceled` 等生命周期，用来表达计划的进程。关闭安排不证明工作已经完成；要判断资料是否读完或文件是否发出，仍需实际结果。计划起止、真实发生、系统写入和获知时间分别保存。存储统一使用 UTC，显示和日程解释用人物时区，首版为 `Asia/Shanghai`；区间按 `[start,end)` 解释。“今天”“昨天”沿用输入进入系统时绑定的日期。[^plan-time]

## 先看改期影响，再提交新版本

同一人物运行里，模型可以用 `schedule.read` 看已有安排，再通过 `schedule.propose_change` 提出改动，最后用 `schedule.commit_change` 提交选择。这些是拟议接口，完整 schema 仍需细化；现有职责已经明确。[^plan-tools]

提出改动至少要带当前版本、目标时段、变化内容和依据。程序返回已有占用及对其他责任的影响；模型再选择保留、改期、并行或取消。时间有重叠不意味着数据库一律拒绝，因为有些活动可以并行；程序也不能擅自裁剪另一项安排，替人物作出取舍。

源方案的例子是：14:12，甲建议一起看视频；人物原本14:30整理图片，打算推迟至15:00。工具先返回15:00的占用情况，提交成功后，她才有依据说安排改好了。失败时返回具体失败，下一步继续处理；不能先告诉甲成功，再期待后台提取补成那个结果。

### 哪些时间可以改变

所有写入口在提交时使用权威时钟检查历史保护。[^plan-history]

| 要改的部分 | 提交规则 |
| --- | --- |
| 已过去的时间段、原安排版本、实际事件 | 保留已有记录，不覆盖。技术录错可以追加更正说明和来源。 |
| 正在进行的活动 | 从服务端提交时刻建立未来修订，保留此前经过和原计划，只改变剩余部分。 |
| 未来安排 | 可以改；返回占用和其他责任影响，交给人物判断。 |
| 已经对某人作出的承诺 | 不因删除或移动日程自动取消；另外处理改期、履行或告知。 |

管理员、模型工具、批量导入、整日重生成和 MCP 入口都走同样的服务。旧版本与修改原因保留，技术更正不伪装成过去当时就已经不同。

如果模型提出改动时读到的版本已经落后，提交服务返回最新状态，让模型重新判断。它不会把旧输出覆盖到新安排上。第十一篇会深入这种版本和时间检查怎样与可暂停运行配合；在这里，改期闭环至少需要读当前安排、查看影响、提交校验和确认结果四步。

### 回合后发现漏记时

一次回复结束后，提取流程仍可发现漏记的邀请、时间或承诺，但它提出的是候选。候选继续经过同一服务的来源、版本和时间检查；若等待期间状态已变，就交下一次判断，不在后台静默修改已经过去的安排。这里的“回合后”是一次实际回复后，不是整场聊天结束。[^plan-post]

这条补漏路径与当前运行的显式工具写入各有用途：已经作出的改期选择及时保存，之后发现的材料再核对。它们不会通过文本提取自动认证一件尚未发生的活动或一条送达结果未知的承诺。

## 完成动作与完成对人的责任

如果人物答应“处理完后告诉甲”，实际处理完成只是其中一部分。工具返回成功，需要保存实际取得什么、何时取得、涉及哪个对象以及成功、失败或未知的状态。然后再按原承诺条件判断还欠哪一步。[^duty-result]

例如，帖子确已发布但还没按约告诉甲，告知责任仍然存在；消息发送结果未知时，也不能认定甲已经知道。平台受理和公开发布本身又有区别，后面的真实平台章节会解释相应回执。这里保留的判断依据是：完成声明与原责任条件，必须能连接到真实结果。

对于她自己没有说出口的意图，重访时可以决定不做；对于双方重新商量的约定，保存新的时间和依据；对于已经发生的外部动作，则不能仅删除待办就声称外界也撤销了它。事项进程帮助查询和续接，不是强制每件事按同一条直线结束。

## 她自己忘了，也需要留下经过

责任机制同样记录人物的过失。她答应下班发资料，自己忘了，后来看到安排才想起来。她可以主动说明补发，也可能在被问起后处理；具体感受和表达由人物及后果决定，不固定触发一种道德情绪。[^duty-own]

此时分别保留“想补救”“道歉已经发出”“资料实际发出”“对方怎样回应”。她觉得事情已经说开，不代表知道对方也释怀。一次失约也不自动让关系所有方面下降；后面的关系机制会依据事件、此前经历和后续行为更新相关判断。

这也解释了为什么具体事项可以有进程，整个人却不应变成单一状态。改期不等满意，任务暂缓不等失去全部兴趣，谈话收尾不等疏远。自己的事情可以继续、暂停、换做法或放弃；约定可以履行、失约或重新商量。这些是可回访的业务变化，不是人物必须经历的固定心理阶段。[^duty-own]

## 实现时要检查和细化的地方

确定性检查应覆盖：无关新消息不会删除待办；取消有实际读取及判断依据；过去时间不能被任何入口改写；未来重叠返回影响而不静默裁剪；版本冲突后重新判断；重复唤醒或重启不会重复解决责任、恢复已取消安排。短答投递失败和发送未知也要分别检查，确认内部待办与对外承诺没有混记。[^duty-check]

已有设计明确了三种 `kind`、拟议工具职责、最低输入和履行依据。仍待细化的是完整表结构、状态转换和错误码；各类责任的复看或失效参数；请求与具体事项的关联、取消和重议怎样表达；以及外部投递与责任记录在失败时怎样核对、补记和防重复。不能仅靠一段自然语言描述推定这些协议已经完成。

下一篇会继续沿着甲这件事，解释哪些经历值得留下、怎样按对象和时间找回来。保存责任保证事情还能接着处理；选择记忆则让以后回顾它时，仍能找到合适的原话、经过和结果。
