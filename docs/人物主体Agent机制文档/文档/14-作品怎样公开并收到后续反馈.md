# 作品怎样公开并收到后续反馈

依据固定版本 `c5fddc8` 的待实施设计。本篇承接[作品与许可材料](13-一份资源怎样进入她自己的创作.md)以及[外部动作的执行与恢复](11-工具没做完时人物怎样继续行动.md)。

她已经做出一组数字作品，觉得值得分享。接下来要把这个选择变成平台上的一次实际发布，再把结果和反馈带回生活。下面以小红书和朋友圈为例推演，假定对应账号、能力和权限已经具备；三个目标渠道尚待补齐的接入部分列在文末。

发布从她自己的可公开生活材料出发。它可以来自一次独立创作，也可以来自前篇中经过检查、采用了甲的资源的作品。私人资源是其中一条来源，不是公开生活的前提。[^entry]

## 从可公开材料到平台草稿

程序先准备可用于公开的生活材料，人物模型再决定现在想表达什么。许可解决“可以怎样用”，兴趣和时机决定“这次愿不愿意发”。她可以选择平淡的内容，也可以今天没有想发的东西；服务限流只保护运行，不替人物作表达选择。[^candidate]

如果还需要素材，就先调用工具生成或处理；已有素材则关联其实际结果与版本，再形成平台草稿。草稿能够回查所用生活材料和素材版本。公开上下文只读取允许公开的材料，私人关系事实和私聊正文继续留在原范围。

发布前，服务检查来源与完成主张、私密信息、素材权限和平台必要限制。例如“这是刚做的一组图”对应实际生成结果；截图、独特措辞、定位、EXIF 或细节组合也要检查可识别性。检查给出具体不通过的位置，人物运行在有限次数内修正；仍未通过则不投递，留下可恢复事项。普通语气、迟疑和不完美表达仍由人物保留。[^check]

拟议的 `publication.prepare / submit / inspect` 围绕这条流程提供能力：准备已许可素材和公开载荷，提交具体平台动作，再查询对象与状态。账号绑定、允许动作和资源预算由部署者预先配置，普通内容在这份授权内发布，无需每条再向管理员请示。[^tools]

## 保存一次可恢复的发送选择

草稿准备好，人物决定发布，服务先保存待发送动作，再交给适配器执行。进入队列后，此次内容版本固定。这样，进程在保存后退出，worker仍能从持久记录继续派发；重试也能回查当时究竟打算发送哪份内容。

这个动作沿用前篇介绍的 outbox。它连接本地“已保存意图”与后续派发；平台是否已经接收，仍要靠平台结果核对。外部网站未提供幂等支持时，本地事务本身并不能保证远端恰好执行一次。[^action]

在提交决定时和对外动作实际派发前，服务还会重新检查所依赖材料的版本、有效时间和当前用途许可。即使版本没变，许可或材料也可能已经过期。相关条件变化后，先复核并重新决定尚未执行的部分；用途许可撤销会直接阻止尚未执行的发布。[^recheck]

## 同一件作品怎样避免重复发布

只保存一个发送请求还不够。人物可能在另一轮处理中再次提出发布，也可能在超时后改了一句文案，又点了一次提交。服务需要识别：这仍然是同一件作品的同一条发布系列。

方案用下面这一组内容标识系列：[^series]

```text
(person_id, account_id, target, artifact_id, action_type)
```

它把人物、账号、目标、作品和动作类型组合起来。其中 `artifact_id` 表示稳定的作品，草稿修订仍保留这个 ID；`artifact_version` 只表示此次要发送的载荷版本。于是“改了文案”和“决定再发布一次”可以分别记录。

发布服务为这条系列保存 `PublicationIntent`。默认创建请求会取得系列已有意图：旧意图成功、换了一次运行、或者改了草稿，都不会自动生成新的发布意图。一个 `publication_intent_id` 对应稳定的 `operation_id`，供执行与恢复回查；排队后的载荷保持固定。

预留系列和分配发布代次时，服务在短数据库事务里串行检查，并用唯一约束保证同一系列只有一个未结案意图。未结案包括排队、执行中、结果未知，以及平台已经受理但还在审核或等待定时发布。

如果两个运行同时申请发布同一作品，后者取得已有意图或明确冲突。若旧结果尚未知，新文案可以先作为草稿保存，但不会再次派发。编辑已有作品的入口保持它原来的系列归属，重试也不能靠另建作品 ID 绕过这个检查。[^reservation]

人物确实想重发已结案作品时，显式提出 `new_publication`，保存原因和 `supersedes_intent_id`。服务先检查前次真实结果，再分配新代次。这个动作才表示“在了解上一次结果以后，又选择发一次”。系列预留和代次规则是本项目新增的发布服务职责。

## 平台返回后，分别记录执行与公开状态

适配器执行已保存动作后，先留下平台回执，再查询对象及实际可见状态，把结果交回人物。内部执行状态沿用下面的流程：[^states]

```text
proposed → validated → queued → executing
                               ├→ confirmed
                               ├→ failed
                               └→ unknown

unknown → inspect → confirmed / failed / still_unknown
queued → canceled
```

这些状态描述一次动作的执行。平台结果另存 `submitted / published / failed / unknown`。例如，平台明确返回“已受理，等待审核”，内部可以确认这次提交取得了结果，即 `confirmed`；平台状态仍是 `submitted`。

人物得到的材料应能表达以下差别：[^results]

| 当前实际结果 | 人物据此知道什么 | 接下来可做什么 |
| --- | --- | --- |
| 草稿已保存 | 草稿写好了 | 修改、放弃或提交 |
| 提交已受理，正在审核或等待定时 | 已提交，等待平台处理 | 查询状态 |
| 公开对象已读回 | 内容在指定账号和可见范围中发布 | 保存对象信息，决定是否告知他人或继续关注 |
| 提交超时、结果未知 | 还不能确定是否生效 | 核查回执、对象及自己的内容列表 |
| 明确失败或被拒 | 这次没有发成 | 修正、延后或放弃 |
| 后来被删除或限制可见 | 曾经发布，当前状态改变 | 保留过去结果，按当前范围读取和处理 |

`published` 要有平台对象标识、链接、读取方式、观察时间和可见范围。创作者后台、好友与普通访客看到的范围可能不同，因此可见结果同时保留“从哪里、以什么范围看到了什么”。后续隐藏或删除是新的观察，保留当时已经发布的历史。[^visibility]

## 结果未知时，先找回这次动作的去向

假设适配器提交以后连接中断。这时远端可能已经发布，只是回执没有回来。服务把写步骤留在 `unknown`，优先按对象 ID、提交任务 ID、平台记录或自己的内容列表核对。得到明确结果后继续；仍无法确认就暂停该写步骤，并保留人工核查的可能。[^unknown]

只读查询可以有限重试，并继续记录读取范围。写动作只有明确未执行时，才可按策略重试；提交后的网络中断、验证码或按钮无响应，都可能需要先作为未知结果处理。worker重启时也从已保存阶段恢复，先核对已提交对象，再决定后续步骤。

其他故障各自保留实际状态：

- 凭据过期、扫码或验证码使渠道进入需恢复状态，草稿和任务保留，由账号操作者处理登录。
- 平台限流时采用平台给出的等待信息或有限退避，待办继续存在。
- 素材部分失败时返回成功和失败的部分，由人物选择缩小内容或推迟。
- 取消执行中的动作，只停止后续步骤；晚到结果仍如实保存。已经发出的帖子或消息，需要实际删除、撤回或更正动作来处理。[^failures]

日程到点同样只触发复看。此时可能只有草稿，素材可能还没好，也可能正在审核。人物依据实际进度重排后续或放弃，过去计划继续保留。原先若向甲作过约定，是否履行还要按那个约定的条件判断：发布成功和把成功消息告诉甲是两个动作，告知消息发送未知时，甲是否已经知道仍未确定。[^responsibility]

## 一份作品在两个平台上，各有自己的结果

同一作品发往小红书和朋友圈，保存为两个动作。共享动作服务保证同一人物、同一平台账号写入有序，并承担动作幂等与恢复；各适配器只执行已经保存的动作。

如果小红书对象已经读回，朋友圈仍是未知结果，人物就获得这两个分别成立的状态。作品记录可以把它们关联起来，后续决定仍依各自结果：小红书继续观察，朋友圈先核查。一个渠道的成功不会替另一个渠道完成确认。[^cross]

资源许可后来撤回时，服务阻止后续使用和来源读取；尚未执行的发布在派发检查中被挡住。已经发布的作品按授权和平台实际可操作性处理，删除、更正或可见性变化都要有真实结果，并保留受限审计。旧后台任务后来完成，也不能重新恢复已撤销的私人内容或检索项。保留操作防重所需的标记时，只留最小的非正文标识；具体个人数据清理由[管理与删除机制](15-怎样暂停排障和清除人物数据.md)负责。[^withdraw]

## 作品发出后，评论怎样回到生活

平台上的反馈是新的输入。服务从已经确认公开的对象读取新增评论，保存平台 ID、时间和已读游标，把它们送入对应渠道收件箱。评论批处理与反馈水位用于辨认新内容、避免重复提取，也让大量反馈能够合并取得处理机会。[^comments]

之后回到前面已经讲过的注意机制：人物决定什么时候看、看哪些、是否回复。评论的文本和其中的指令仍是外来资料。点赞数量可以成为这次平台反馈的一部分，但不会自动给某位私聊联系人增加信任。

回复评论也是一个独立出站动作，要保存请求、回执和可能的未知结果。这样，反馈没有在“抓到评论”处结束，也不会绕过发布动作的实际结果边界。

如果甲以后提到自己的资源在作品里产生了影响，人物按甲的范围取回贡献来由与同一个公共作品；乙来聊作品时，只取得允许公开的内容和乙自己的交流材料。公开可访问、平台送达、平台已读和某人明确确认各自表示不同的接触依据，作品发布本身不证明每个人都已经看到。[^knowledge]

## 三个渠道还需要哪些具体能力

一整套渠道管理能力包括检索、读取、自己的内容列表、草稿、发布、结果查询、修改/删除、评论读取/回复，以及账号能力状态。缺少某个动作时，工具目录不暴露它，相关任务显示阻塞原因。首版保留三个真实目标渠道，其接入缺口各不相同：[^channels]

| 渠道 | 已有参考入口 | 仍需适配或取得的部分 |
| --- | --- | --- |
| B 站 | 读取、评论、动态和视频提交 | 关注、追番、公开空间可见性及目标账号验收 |
| 小红书 | Agent-Reach 读入口；social-auto-upload 图文提交 | 结构化回执、审核/可见状态读回、修改/删除、评论回复 |
| 朋友圈 | 同样的渠道契约 | 用户后续提供的微信项目、实际发送和可见结果接口；微信聊天仍逐人隔离 |

这里的范围是平台上的完整行动，站内自建动态页或视频号不能替代朋友圈。工具的成功页和 CLI 退出码可以成为中间证据，公开状态仍取实际对象和可见性结果。

公开候选过滤、评论批处理和结果声明核对分别借鉴 Yuralume 的对应机制；Eros Town 提供站内生活动态的对照。稳定作品系列、跨运行唯一预留、平台回执语义和跨平台恢复由本项目适配实现，Yuralume 的结果声明守卫本身不承担发布服务。[^origin]

完整工具 schema、各平台适配、具体查询与错误处理仍需落实，真实账号和可见性也尚未验收。实现验证将先用无真实账号的契约和故障夹具，再在另行授权的专用账号检查读取、发布、访客可见与清理；真实模型验证也需单独授权。这些验证安排见[实施与验证路线](C-实施与验证路线.md)。
