# 一句话怎样成为可回查的记录

机制重组稿 · 2026-10-25 · 依据 Between 固定版本 `c5fddc8d3b3ae81b77d41cba4cede78286e8dd0d` 的待实施设计。

前两篇讲了甲的消息怎样保存、何时提供给人物。现在给同一次交流增加一句新话：下午 14:10，甲说“我正在开周会”。假定人物已经选择读取了它。

她可以据此理解甲暂时忙着，也可以继续关心甲上午说过的疲惫。以后再次谈到这件事，系统还应能找回：是谁这样说、当时指什么时间、人物何时获得正文，以及这句话能在哪段交流里使用。

这需要把**收到一段话的经历**与**话中表达的说法**分别留下。收到消息是已经发生的收件事件；甲正在开会，是甲对自己情况的报告。两者有关联，也各自有能说明的范围。[^1]

## 把收到的事和话里的说法分别留下

收件入口保存了甲的原文，也能追加“某时收到这条消息”的发生记录。方案把收到、观察、尝试、决定或模拟发生的事情记为 `Event`。这些记录由相应领域服务追加，后来可以用于回顾、状态更新、排障，也可以成为记忆选择的材料。是否值得长期记住，留给第 [06 篇](06-经历怎样留下以后找得到的记忆.md)处理。

人物读到正文以后，理解的是甲在报告自己正在开会。方案用 `Claim` 保存这样的说法：保留说话者、来源和适用时间，供之后查询和比较。它既能承载联系人的报告，也能承载人物模型提出的判断；查询时仍能分辨是谁作出的说法。[^2]

例如，后来有人问“甲那天下午为什么没有及时回复”，系统可以找到甲的这条原话。它提供了一条解释依据；是否还需要其他材料，由人物结合问题判断。若甲说的是一句不实的话，实际收到消息的经历仍成立，而话里的内容仍保留为甲的报告。

这一区别在关系问题上尤其重要。若甲说“你昨天答应做我女朋友了”，可回查的是甲说过这句话。找不到此前承诺时，人物可以存疑、询问或表达判断；检索缺证没有替双方确认关系。她自己说“我不记得答应过”，同样只表达了此刻的认识，并不能证明历史上绝无此事。[^1]

## 保存来源，也保存这份材料能说明什么

记录里有两个分别回答问题的标记：`source_kind` 回答材料从哪里来，`statement_kind` 回答它表达的是报告、观察、计划还是其他含义。查询保留二者，才能让后续理解沿着原来的依据继续。[^3]

|来源 `source_kind`|保留的依据|据此能说明的范围|
|---|---|---|
|`channel_message`|某联系人某时的陈述|甲说自己在开会；共同经历、人物是否接受约定还要有相应依据|
|`tool_receipt`|指定工具在指定账号、目标上的实际返回|工具读到或执行到的部分，连同它的覆盖范围|
|`character_decision`|人物的选择、意图、接受、拒绝或主观感受|她作出了这个选择；动作是否完成另有结果|
|`simulation`|生活服务已提交的虚构人物生活进展|属于人物模拟生活的事，不证明真实用户参与、真实消费、平台动作或现实第三人的行为|
|`profile_revision`|经批准的人物虚构底稿|该版本成立的设定；新设定不会倒推成过去任意时刻都已知道|
|`model_inference`|根据所列材料形成的推测|人物目前的推断，仍可随后复核、纠正|

对应的陈述类别是 `reported / observed / planned / decided / simulated / inferred`。甲这句话的来源是 `channel_message`，正文按 `reported` 保留。说法本身还保存 `asserted_by`、稳定的 `subject/predicate` 和原话；如果是在转述别人，再连接被转述的来源。记录的稳定主体与事项，能帮助后续判断两段材料是否真的在说同一件事。[^3]

这些类别没有把所有材料排成一个统一的可信度分数。甲说“最近很累”，人物通常可以据以体贴回应，无须先上网证明。要确认某篇帖子是否公开，则查询对应平台结果；要确认人物是否说过一句话，则查询出站记录。拟议工具 `facts.query` 返回原文、来源、适用时间和冲突，人物再结合语境理解它们。[^4]

计划与结果也沿着这条原则分开。“下午发小红书”是计划，“已经请求发布”是尝试，平台受理是提交结果，读回对应帖子才支持相应发布状态。人物说出明确承诺还涉及第 [05 篇](05-改了安排以后还记得欠谁什么.md)的责任记录，不能只凭 `planned` 判断已经对外答应。[^1][^3]

## 一条记录怎样带着时间保存

以最早保存“我正在开周会”的收信记录为例，原方案给出下面这个记录外壳。它是说明字段含义的示例；实际标识使用无身份含义的随机 ID。[^5]

```json
{
  "event_id": "ev-example-1",
  "person_id": "person-example",
  "scope": "contact",
  "counterpart_id": "contact-a",
  "group_id": null,
  "occurred_at": "2026-10-24T14:10:00+08:00",
  "recorded_at": "2026-10-24T14:10:01+08:00",
  "valid_from": "2026-10-24T14:10:00+08:00",
  "valid_until": null,
  "exposed_at": null,
  "source_kind": "channel_message",
  "statement_kind": "reported",
  "source_ids": ["message-example-1"],
  "activity_id": null,
  "revision": 1,
  "payload": {"claim": "我正在开周会"}
}
```

这个例子展示收件 Event 携带的报告内容。Claim 的完整结构、提取方式及其与事件记录的具体持久化衔接仍需细化。

`event_id` 标识这条发生记录，`person_id` 标识人物，`counterpart_id` 与 `group_id` 连接对应联系人或群。`payload` 放本条内容，`revision` 标明记录版本，`source_ids` 使后续查询能回到原材料。这个外壳还把几种时间分开：

- `occurred_at` 是所知的发生时间；`recorded_at` 是系统实际写入时间。不知道准确时刻时，保存所知的区间和精度，不为记录齐整补造秒数。
- `valid_from/valid_until` 表示说法或状态适用的时间。示例中的未知结束时间，不使“甲正在开会”永久有效。当前状态另有 `recheck_at`；超过适用条件后，以最后已知情况呈现，再按需要复核。
- `exposed_at` 是正文实际提供给模型的时刻。示例保留收件时的空值；详细读取记录仍是第 01 篇的 `Exposure(run_id, item_id, exposed_at)`，外壳里的字段只作查询摘要。实际提供也不代表理解正确。[^6]

`activity_id` 可以为空。一件事可以发生在日程之外，时间接近也不足以推断某位联系人参加了人物的活动。日程自己的预计起止、生命周期与实际完成证据，由第 05 篇继续展开；安排时间、发生时间、获知时间始终各有位置。[^6]

存储时间统一用 UTC，显示与日程解释采用人物时区，首版是 `Asia/Shanghai`。时间截止采用半开区间 `[start,end)`；甲说“今天”或“昨天”时，在输入进入系统时绑定日期。以后摘要再提起这句话，仍沿用当时的日期。[^7]

业务对象可以由关系字段和 JSON 正文共同保存，并不要求一个名称对应一张表或一个服务。具体表结构仍需细化；各领域的时间与权限校验继续生效，不能被一个随意覆盖的整个人物 JSON 绕开。[^2]

## 查询时，先决定这次能读哪些材料

人物之后与甲谈到开会，可以在甲的范围内查询这条说法。`facts.query` 按对象、时间或问题取相关材料，服务先过滤允许范围，再检索；拿到一个 `source_ids` 引用后，再读原文时也要检查范围。引用是核对路径，不会自动授予跨联系人读取权限。[^8]

记录的范围有四种：`character` 是人物自己的可共享生活材料；`contact` 仅对应联系人；`group` 是该群已公开的内容；`system` 是运行和管理材料。甲的私聊原文属于甲的范围，乙不会仅因同一天也在聊天而获得它。[^9]

自己的共享材料也有边界。人物的“今天有点疲惫”可以供与乙的交流使用；导致疲惫的甲私聊原文及可识别细节仍留在甲的范围。`character` 范围里的未发布草稿也不因此自动可以公开。

因此，系统还分别保存**公开使用许可**与**对方接触情况**。公开许可针对特定作品、用途和范围，来自 `PublicationGrant` 或已经确认的自有材料规则；材料重要并不能替代许可。公开作品也不会反向解锁私人来源。资源怎样形成可公开作品，由第 [13 篇](13-一份资源怎样进入她自己的创作.md)继续说明。

对方接触过什么，则用 `KnowledgeReceipt(person_id, counterpart_id, artifact_or_fact_id, basis)` 保留依据。`basis` 区分送达、平台已读和对方确认。送达不证明已读或理解；一份作品公开可访问，也不代表每个联系人都看过。第 [14 篇](14-作品怎样公开并收到后续反馈.md)会把这种记录接到实际发布与通知上。[^9]

群聊仍按群范围保留，不把甲在群里的一句话抄到所有人的私聊记忆。将来私聊需要引用群内容时，只给接收人确实有权看到的群事实或另获许可的内容；删除成员、撤销授权后，重新计算可读范围。[^10]

## 新材料出现后，怎样修正原来的认识

假设后来出现另一份材料，说明甲在同一时段并没有开会。查询先比较是否是同一主体、同一事项，以及适用时间是否重叠。“上午在家”和“下午外出”不构成这样的冲突；同一下午对是否在开会的不同说法才需要并列核对。

材料不足时，查询返回未知或两种说法及出处，由人物按语境决定要不要询问。来源校验失败的记忆候选会隔离；语言相似不应让冲突悄悄消失。[^11]

形成新的认识时，新记录用 `supersedes_id` 指向旧说法，原记录及其来源关系仍可回查。若撤回的是人物自己的错误自述，据它整理的记忆要标记待重算，不能继续作为独立证据；已受影响的关系证据和外溢也要失效、重建。第 [06 篇](06-经历怎样留下以后找得到的记忆.md)和第 [08 篇](08-关系怎样依据经历变化和纠错.md)分别讲清这两条后续路径。[^11]

对历史的技术录错，可以追加纠正说明。过去日程仍保留当时版本，进行中的活动只从提交时刻修改未来部分；管理员、批量导入等入口遵守同样的提交时钟检查。这样的纠正保留“后来知道了什么”，不会把历史伪装成当时就不同。[^12]

如果错误内容已经公开，内部认识修正后，还需要实际的更正或删除动作处理公开结果；删掉本地一行记录不能说明外界没有看过。个人数据清除的范围和防复活要求，另在第 [15 篇](15-怎样暂停排障和清除人物数据.md)展开。[^11]

## 环境材料也按这条路径进入理解

甲说自己在开会，只提供了甲报告的环境。人物不会因此知道未被告知的地点、在场者和动静，也不会因为在线收到这句话就成为共同在场的人。

环境情况、实际接触的信息和人物的解释分别保留：场景中已经确认检票口变更，人物可能还没看到通知；她看到了，也可能暂时理解错。没有依据的地点、天气或旁人保持未知。共同情境只共享有依据的部分，同处一处也不代表双方注意到了相同信息。环境改变时，更新有变化或有新依据的部分，既不每轮随意换地点，也不把过去位置永久沿用。[^13]

这些材料有时影响人物选择，有时直接限制行动结果。例如信号中断可能使消息发不出去，即使人物尚未理解这个变化。她也可以选择走到安静处或关闭通知；想改变、尝试改变、已经改变分别留下依据。第 [04 篇](04-没有新消息时生活怎样继续.md)进一步说明人物自己的处境怎样持续推进，第 [11 篇](11-工具没做完时人物怎样继续行动.md)处理实际动作与结果。[^13]

## 实现还需要细化什么

现有约定已经给出了来源、陈述、时间、范围和纠错含义，完整数据库迁移、各对象的全部字段及写入接口仍需细化。记录外壳不是所有业务对象的完整 schema，Claim 的具体提取和持久化接口也不能由这个例子补出。

这套分离思路适配了 Yuralume 的回合后提取、Eros 的分层画像和 BST 的状态账本。Yuralume 的 audience/knowledge 区别可供采用，但多人场景采用“缺少公开许可保持私有”；BST 的显式清除标志用于防止旧值复活，并不采用编辑旧聊天改写人物历史的权威模型。来源版本及原有能力范围见[配套 B](B-决定取舍与来源导读.md)。[^14]
