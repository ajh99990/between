# 怎样暂停排障和清除人物数据

机制重组稿 · 2026-10-25 · 依据 Between 固定版本 `c5fddc8d3b3ae81b77d41cba4cede78286e8dd0d` 的待实施设计。

甲的视频已经读过，人物也做出了一份作品。某次发布后没有收到明确回执，任务仍在等待核对。这时管理员需要知道：作品究竟发出去了没有，人物还在等什么，以及暂停人物会影响哪些后续动作。

管理端沿着前面各篇留下的记录查看真实进度，再执行允许的暂停、恢复核查或数据清除。它需要看到具体的输入和动作链路，不能只凭一份人物总摘要推测发生了什么。[^1]

## 先找到这次任务停在哪一步

管理视图从具体任务和时间线展开。甲的来信已收到、正文已提供、人物已经回复，是三个环节；计划做作品、生成出作品、请求发布、平台已公开，也各有依据。第 01、03、11、14 篇建立的这些记录，为排障提供可回查的入口。

管理端需要呈现以下内容，并保持各自的来源与读取范围：[^1]

|要弄清的问题|需要查看的记录|
|---|---|
|人物当时依据什么生活背景行动|完整人物设定及来源、当前活动、日程及其修订|
|这段时间实际发生了什么|事件时间线、具体动作及真实结果|
|与甲的交流走到哪里|逐人的收件、实际提供、回复记录，甲相关的承诺与任务状态|
|某句话依据什么生成|那次来源受限的上下文快照、实际输入范围、状态版本、已发生动作及公开输出|
|感受或关系怎样变化|相应情绪评价、证据与结算记录|
|平台任务是否需要续接|动作阶段、平台结果、等待事项及恢复记录|

例如本次发布结果未知，管理端查的是已保存的动作、平台对象或提交任务、实际返回和后续核查结果。第 11 篇的内部 `confirmed` 与第 14 篇的平台 `published` 仍分别显示；只收到审核受理，不能通过修改管理记录把它变成已经公开。[^2]

如果问题是“她为什么对甲这样说”，则回看这次真正给模型的材料及状态版本，再接上已经发生的动作和最终输出。乙的私聊不会为了让解释显得完整而混进甲的快照；一篇覆盖所有联系人的总摘要也不能代替这次实际输入。[^1]

## 谁能看到这些排障材料

正常用户只看人物对外发出的消息。内部提示、模型输入、工具结果和诊断在鉴权管理端按范围查看，不进入聊天或 TTS。日志保存简短决定依据和来源，不要求存取模型隐藏思维链。[^3]

记录本身也延续原来的权限。甲的资源贡献关系只供甲的关系回顾及有权限的管理流程查看；公开作品不会反向开放甲的私聊。原始私聊导出另设权限与审计，工具凭据在界面上显示密钥引用。[^1][^4]

复现一次运行时，可以查模型、材料选择、参数、工具 schema 和提示词版本；原样采用的上游核心提示词有固定 SHA、路径和原字节 hash，胶水材料单独保存。这些记录解释某次运行的输入条件，并不把内部材料变成普通用户可见内容。[^5]

新项目需要这些管理能力，具体界面可以围绕新运行记录组织。旧后台不构成架构前提，现有界面也不是这些新能力已经实现的证据。[^1]

## 暂停人物以后，哪些动作会停止

管理员可以暂停人物和撤销尚未执行的动作。对已在执行的请求，取消只停止后续步骤；已经发出的帖子或消息仍然存在，晚到结果继续如实保存。需要撤回时，再发起真实的删除或撤回动作。[^2]

因此，暂停本次发布任务不会让未知结果变成失败，也不会使一个已经公开的帖子消失。恢复核查仍使用已保存的动作阶段与真实平台结果。worker 重启时先核对已提交对象，不把本地重启当成重新发布的理由。[^6]

平台要求登录恢复时，渠道标记为需恢复，草稿与任务继续保留，由账号操作者处理登录；模型不借别人的会话，也不编造成功。点击后超时的结果可由平台对象、自己的内容列表进一步查询，人工也可核查。平台限流按其等待信息或有限退避处理，保留待办；部分素材失败时，保留成功和失败部分，由人物决定缩小内容还是推迟。[^6]

日程修订同样经过原有服务：所有入口在提交时检查权威时钟，过去部分保留，进行中只从提交时刻形成未来修订。管理员、批量导入或 MCP 都不能把过去的失败改成成功；技术录错可以追加带来源的纠正说明。[^7]

## 甲撤回资源以后，现有记录怎样处理

如果甲撤回私人资源，后续使用和来源读取先受撤回限制；尚未执行的发布还会在实际派发前复核当前许可。已有公开内容则依据授权与实际可操作性处理，保留受限审计。删除私聊里的一个气泡，本身不能撤销所有已经产生的公开副作用。[^8]

第 13 篇分开保存私人成因、贡献关系和可公开作品，第 14 篇保存实际发布结果，所以这里能分别处理：哪些原材料不再读取，哪些待执行动作不再允许，以及哪些外部对象还需要真实的更正或删除。

若内部保存过错误认识，新认识仍通过来源和替代关系连接旧说法，派生记忆及受影响关系证据按各自机制失效、重建。公开事实的改变依靠真实外部动作，不能用删除数据库行宣称外界从未看过。[^9]

## 删除联系人数据，要处理到后续使用路径

甲请求清除个人数据时，处理范围包括私密正文与检索项：删除或不可逆脱敏这些内容，同时阻止旧队列和摘要在以后再次带回它们。只有主记录不再显示、旧任务却还能从摘要恢复原文，尚未达到这项删除要求。[^10]

另一方面，某次外部动作可能已经发生，恢复程序仍需要最小标识避免重复执行。确需留下的操作防重记录只保留最小的非正文标识，不借防重继续保存私聊内容。具体保留哪些标识、怎样验证旧任务和检索不再复活正文，仍需要实现阶段细化和验证。[^10]

这与历史保护共同生效：人物的生活历史不能伪造，个人数据可以按删除请求清除。过去日程不可改写不意味着个人正文必须永久保存；清除个人数据也不意味着可以假称某次已经发生的外部动作从未发生。

具体保留期限要在接入真实用户前配置并验证，本方案没有授权无限存储。内部 HTTP 重试、向量批次和 token 等执行记录本身也有期限，不全部进入人物事件或长期记忆。[^10][^11]

## 管理与删除仍需完成的实现工作

目前确定的是观察能力、按范围访问、暂停和撤销边界、数据清除结果及防复活要求。管理页面、细粒度权限配置、导出审计格式、各存储中的删除或不可逆脱敏方式、最小防重标识和保留期限仍需细化。

后续验收要沿实际运行记录验证这些行为：能回查某次输入与结果，暂停不掩盖已发生动作，删除后旧队列和摘要不会重新提供已清除内容。文档中的链路说明不替代这类实现和验收记录。
