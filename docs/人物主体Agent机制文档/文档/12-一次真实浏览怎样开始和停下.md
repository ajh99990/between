# 一次真实浏览怎样开始和停下

依据固定版本 `c5fddc8` 的待实施设计。本篇承接[工具等待与运行恢复](11-工具没做完时人物怎样继续行动.md)，给同一位人物增加一个输入来源：她主动去找的内容。

假设到了下午，她想看一些与穿搭或图像风格有关的视频。当前活动、粗安排和下次复核已经按生活机制保存好。程序现在要做的，是给她一个能实际选内容、取得内容、再决定下一步的机会。

这次浏览可以从自己的兴趣开始，也可以接着甲已经被查看的来信展开。两种入口最后都会遇到同一个问题：**这次究竟接触了什么，接触之后还想做什么？**[^start]

## 先有方向，再选择具体内容

运行开始时，程序准备她已有的兴趣、最近确实接触过的内容、当前处境、可投入的时间和本次剩余资源。人物模型根据这些材料选择探索方向，然后搜索或读取推荐。

搜索结果提供对象 ID、标题、来源和可用阅读方式。模型据此选择一个具体对象，再请求字幕、正文、可得画面或评论。搜索得到的是候选，读取取得的内容才成为下一步理解的材料。[^loop]

比如，她选中一个视频，工具取得了其中一个分 P 的部分字幕、几幅抽样画面和一批评论。模型可以顺着里面的观点继续查，也可以换一个视频、停下来与甲讨论，或者觉得这次已经够了。每一步都把真实结果交回模型，再由它选下一步。因此，一次探索是多步选择形成的过程；日程里“刷 B 站一小时”只给出安排，不要求模型在这一小时里连续调用工具。

如果读取需要等待，沿用前篇的运行机制：先保存动作请求，由执行服务工作，让出人物决策机会。结果到达后重新准备当前材料再继续。此时允许查看的新来信也可以获得处理机会；切到另一位联系人时，仍按那位联系人的范围重建输入。[^waiting]

## 工具返回的不只有内容，还有取得范围

人物之后要谈这段视频、记下想法或据此创作，就需要分清资料覆盖到哪里。读取结果因此同时保留以下内容：[^coverage]

| 读取结果中需要保留什么 | 后面怎样使用 |
| --- | --- |
| 对象、来源与读取时间 | 找到这次实际接触的内容，连接后续讨论和想法 |
| 实际分 P 与时间片段 | 知道取得了视频的哪一部分 |
| 正文或字幕是否截断 | 判断当前理解覆盖到哪里，是否值得继续读取 |
| 实际取得的画面范围 | 让关于视觉内容的判断有对应材料 |
| 评论的排序、条数与取得范围 | 分辨本次看过的一批评论与平台上的全部评论 |
| 成功、失败和缺失项 | 决定继续查、换一种读取方式，还是带着已知限制停下 |

如果只取得标题，人物可以根据标题表达兴趣或疑问。没有字幕、画面读取失败，就保留这些缺失。评论返回空数组时，还要结合读取结果判断它表示没有取得评论、当前查询没有返回，还是确有对应范围内的空结果；它本身不足以说明整个平台无人评论。

工具结果先作为可回查的运行材料保存。人物能理解的每次搜索或读取，都记录为稳定事件，保留搜索关键词与时间、读取对象及覆盖范围；内部 HTTP 重试、向量批次等留在执行记录里。人物若受到某句话触动，可以选择留下带来源的记忆，不必先在聊天里复述一遍。全部字幕、评论和工具日志也不因此自动成为长期聊天记忆。[^memory]

## 为什么人物只见领域工具

上述过程需要的是“找内容”“读内容”“看评论”“关注作者”这些能力。拟议的 `platform.*` 工具组以具体账号、动作、对象和资源引用为输入重点，返回实际结果与覆盖范围。服务按当前运行的授权裁剪可调用能力，再由受限的后端适配器执行。[^tools]

这样，人物只要理解一次动作要做什么、结果说明什么；后端可以针对渠道选合适工具。首版的小红书只读路径优先适配 Agent-Reach 的渠道注册、动作注册和统一错误；B 站深读优先借用 kukemc 的字幕、画面、评论组合逻辑，并以 public-clis 的规范化输出和动态回读作对照。

适配启用前，要确认固定依赖仍可取得，目标账号也能完成读取。上游已有依赖停止维护的情况，因此接口不锁死某个 SDK。失败时可以改用正常网页读取，继续遵守登录、付费和访问限制。读取适配不调用 kukemc 的全片历史上报来证明看完；观看依据始终是实际取得的内容范围。[^adapters]

部署者预先绑定人物自己的账号，确定允许动作与资源预算。人物获得的是这些已允许能力，而不是操作者个人 cookie、凭据文件或整套 CLI 命令。MCP 可以承载领域工具；付费投币、自动回复、任意命令、凭据操作等能力仍分别受授权约束，不会随着某个 CLI 接入就一并开放。网页、字幕和评论也继续作为资料进入模型，不改变系统授权。[^permissions]

## 怎样结束一次探索

人物主动选择结束时，保存本次实际接触的内容、当前想法、停止理由、下一步和下次查看机会。她可以转去休息，也可以保留之后继续关注的安排。生活记录沿用已经发生的接触，不把剩余计划时间填成新的观看经历。

另一种结束来自资源上限。首轮 B 站探索验证采用以下初值：[^budget]

| 限制项 | 首轮初值 |
| --- | --- |
| 模型决策步 | 最多 12 次 |
| 读取调用 | 最多 8 次 |
| 视频对象 | 最多 3 个 |
| 总墙钟时间 | 最多 6 分钟 |

接近上限时，程序告诉模型还有多少资源。若触顶，运行记录为被上限中断，并保存尚待处理的事项；之后能否继续，由后续处理机会判断。人物自己停止与程序中断有不同原因，恢复时需要保留这个区别。

这些数值是第一次验证的成本保护初值。她可以只看一个视频，也可以很早就结束；三个名额没有要求她一定搜索三个视频做总结。费用还受单次运行预算封顶。长视频的 ASR 若超过预算，应分段或延后，不能悄悄调用付费服务；具体费用额度仍需配置。上限的后续调整也要依据实际记录，而不是把它当成人的注意力参数。

完整探索循环借用了 Yuralume“执行工具后再组织后续输出”的思路，但上游本身是最多一次工具、两遍生成。这里的多次自主选择、资源上限和可恢复步骤，是本项目的适配；短而完整的探索也意味着首版实际覆盖有限。[^origin]

## 甲发来的链接怎样接进来

现在给这个例子增加一个情况：甲发来另一个视频链接，人物已经按注意规则打开了这条消息。她可以接受建议，再读取视频和评论，随后与甲讨论。

系统分别记录甲发来链接、她选择读取、工具实际取得内容，以及双方发生的对话。时间和对象把这些记录联系起来；日程只在人物真的改变安排时修订。读一个视频不需要把整个过程写进日程说明。[^private]

与甲讨论的观点和关系变化留在甲的范围里。视频本身允许共享的内容，以及人物实际产生的个人兴趣变化，可以成为她自己的接触记录。乙随后问她在做什么，可以得到同一份共享当前活动和允许分享的观看结果；甲的私人观点、感情和身份仍保留在甲的范围。

这也给下一篇留下了自然入口：人物确实接触到某个风格，产生了尝试的兴趣，接下来怎样做出一份实际作品？

## 渠道能力与实现缺口

首版的目标包括 B 站、小红书和朋友圈，各自要形成可回查的真实行动。B 站除了读取内容与评论，还包括自主继续或停止、关注作者、追番，以及需要分享时发布动态或视频；小红书包括参考阅读、图文创作、发布与后续评论；朋友圈从同一份生活材料产生公开内容，微信聊天继续逐人隔离。发布过程见[作品公开与反馈](14-作品怎样公开并收到后续反馈.md)。[^channels]

现有工具提供了部分入口，仍有明确缺口：

- B 站的关注、追番和公开空间可见性，需要专项适配与目标账号验收。
- 小红书的读入口与图文提交已有参考实现，结构化回执、审核及可见状态读回、修改/删除、评论回复仍需补适配。
- 朋友圈等待用户后续提供微信项目；目前定义渠道契约，实际接口与验收依赖该工具，视频号不是朋友圈的替代入口。

工具目录根据真实能力提供动作；缺少能力时，相应任务记录阻塞原因。完整参数、返回 schema、错误码和适配实现仍待细化。已有的动作名称与覆盖要求确定了接口应表达什么，不等于三平台已经接通。
