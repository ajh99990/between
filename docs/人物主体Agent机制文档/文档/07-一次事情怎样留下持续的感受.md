# 一次事情怎样留下持续的感受

> **现行规则更新（2026-10-26）：** 本文正文保留固定旧版设计；当前联系人锁定的记忆读取及相关输出/验收条件已由[现行05的跨联系人回想与对外称呼](../../plans/人物主体Agent方案/05-记忆与上下文.md#跨联系人回想与对外称呼)与[09的T21](../../plans/人物主体Agent方案/09-验证与实施路线.md)替代。允许明确回想自身已知记忆，对外不得说出来源用户名字，使用模型自选代称；未读、跨人物及保密边界仍保留。

机制说明 · 依据 Between 固定版本 `c5fddc8d3b3ae81b77d41cba4cede78286e8dd0d` 的待实施设计。

甲说过自己今天很累，这段来信已经被查看并留下记忆。现在给这段交流增加一个情况：人物也正在处理自己的工作，已经向甲说明暂时不方便长聊，甲又发来“怎么还没弄完”。

这句话可能是玩笑，也可能让她感到被催促。判断需要看前文、双方的相处方式，以及她眼下的情况。即使产生了一点烦躁，也还要回答另一个问题：过一会儿继续处理工作、再和甲说话时，这份感受怎样延续？

本篇的机制是：**模型理解已经接触的事情，提出有来源的评价；服务接受变化并保存连续状态；此后的模型读取实际接受的状态，再决定行动。** 首版选择 Emotion Engine（下称 EE）作为情绪与信任账本的代码基础，语境理解与行动选择仍由人物模型完成。这里先讲感受，长期信任在下一篇展开。例子是设计说明，不是实测输出或推荐台词。[^1]

## 先理解发生了什么，再提出变化

模型开始评价时，甲这条消息必须已经实际提供给人物。服务保存但人物尚未查看的正文，不进入这次评价，也不经后台分析提前变成“甲让我烦”的结论。

这次模型读到的材料包括自己的当前工作、生活疲惫、甲的相关关系记录、原话和时间。模型可以理解为玩笑、催促、误解，也可以保留不确定。例如，“此前已说明仍被催，她感觉自己的安排没有被尊重”，描述的是她的理解；甲究竟有没有故意施压，仍要依照来源判断。[^2]

有明显触动时，模型提出变化后的最终状态、简短说明与来源；没有明显影响时，可以保持原状态。这里没有“每条消息必须生成一次情绪事件”的要求。日常的问候也可以自然回应，不必先组织一条复杂的内心解释。[^2][^3]

变化也可以来自自己的生活。完成工作、身体疲惫、回忆起一件已知的事、重新理解旧经历，都可能影响当下。人物可以一面为做完事情高兴，一面仍想休息；原因不清楚时也可以保留“有些低落但不清楚为什么”。未知原因不需要补成一场从未发生的冲突。[^3]

## 连续状态保存了什么

一句“她现在有些烦”能说明感受，却不能单独回答下次读取时怎样延续。服务还要保存本次变化发生在何种状态之上、何时计算过，以及依据哪件事。EE 提供当前 PAD、人物基线、短波动和事件解释等材料，适配服务把它们与项目中的身份、范围和来源关联。[^4]

PAD 分别表示愉快、激活与掌控三个连续维度。`baseline` 是引擎的基线，`pulse` 表示近期刺激留下的短波动。它们帮助引擎表达状态及其时间变化；有意义的文字说明和原因仍然保留，模型需要理解“因何烦躁”，才有条件判断下一步。[^5]

一次有来源的理解称为 `Appraisal`。它记录所评价的事件、指向对象、解释和前后状态。后面若重新理解同一件事，可以指出它替代哪次评价，旧解释仍留在历史中。当前感受则由 `AffectState` 延续。下面是现行方案已经规定的最小适配字段：[^6]

```text
AffectState:
  person_id, scope=character|contact, counterpart_id?
  affect_context=self|relationship
  revision, PAD, pulse, baseline, decay_anchor_at
Appraisal:
  event_id, target, interpretation, evidence_refs, before, after
  replaces_appraisal_id?
```

`target` 回答这次感受指向谁或什么；`scope` 回答谁可读取；`affect_context` 区分自己的生活感受与对某个联系人的感受。例如，对甲的催促有所不快，不会因此获得读取乙私聊的权限。三种含义各自保留，内部状态身份也不代替权限检查。[^6]

这些字段表达接线必须满足的条件，尚不是完整数据库或工具 schema。完整字段类型、索引、请求及错误返回格式仍待细化。事件真伪、工具结果是否可信，也继续由前面已讲的来源记录判断。[^6]

## 变化怎样提交，并在本批处理中真正用上

服务从数据库取得当前状态，并按明确的当前时间计算供模型读取的状态。模型解释材料后，可通过拟议的 `affect.appraise` 业务工具提交已查看事件、主观理解和期望版本。服务检查来源可见性、受影响的身份、版本与是否重复，再调用 EE 的状态核心函数。[^7]

EE 接受的是模型提出的**最终 PAD**。引擎据此生成 pulse 并记录轨迹，不把同一次变化当作增量再加一遍。接受成功之后，结果要回到本次人物运行，模型读取被接受的状态，再决定短答、解释、提出边界、换话题或暂缓。[^2][^8]

这个顺序直接影响一次交互是否成立：如果模型先写完回复，才在后台保存情绪，那么刚保存的变化并没有参与这次行动选择。现行接线要求同一批处理中先获得实际接受结果，再继续决定；完整的输入组装由[上下文篇](09-这一轮模型究竟拿到什么.md)展开。

```text
已经实际接触的事件与相关情况
    → 读取按明确 now 计算的生活状态和本联系人状态
    → 模型提出有来源的评价；也可以保持不变
    → 服务核验身份、可见性、期望版本和重复键
    → EE 计算最终状态，宿主保存接受结果
    → 模型读回实际结果，选择本次行动或回复
```

解释有歧义时，可以只保留不确定说明而不改数值。写入失败或版本已经变化时，模型必须看见失败及实际结果，重读状态后再决定；它不能把一次未被接受的提议当作已经完成的更新。人物最终说过什么和系统实际保存了什么可以不同，但这份差异要能追溯。[^8]

## 时间经过一次，状态也只推进一次

假设这次烦躁发生在下午，两分钟后又读取状态。服务需要知道上一次算到什么时刻，才能只处理这两分钟的时间影响。为此，状态保存独立的 `decay_anchor_at`：一次提交同时保存计算结果和新的时间锚点。同一时刻再次读取时，不再重复计算刚处理过的时间。[^9]

首版不直接沿用 EE 仍根据旧 `last_interaction_iso` 反复计算的路径，也不启用按对话轮数回拉状态的 `pre_turn_decay`。多来几条短消息、增加几次工具调用、切换一个联系人，均不能使自然恢复突然加速。pulse 的短时变化同样使用明确的时间锚点。[^9]

时间演化可以在需要读状态或到达唤醒时计算，不需要每秒调用一次模型。这也允许人物暂时没有新消息时仍经过一段时间，而不是直到下一句聊天才算“活了一轮”。具体衰减参数仍需后续校准；当前没有规定烦躁应该精确持续几分钟。[^9][^10]

首版同时关闭 EE 的缺席信任衰减。几天没联系不会自动成为不可靠的证据。感受的时间变化、关系中的实际疏远与信任判断，使用各自的依据。[^9]

## 生活感受和对甲的感受怎样同时存在

完成一件工作带来的轻松属于人物自己的生活；与甲尚未说开的误会属于甲的关系范围。首版分别延续一份生活感受和每个联系人的关系感受，模型读取有意义的并列材料，例如“今天仍有点累；和甲还有一件事没说清”。这些材料不求和或平均成一个总心情。[^11]

生活感受来自自己的活动、环境和已确认的生活经历，保存当前 PAD、简短感受及时间，并遵守共享事实的可见规则。甲的关系感受保存对甲的短时触动、未解决事项、信任与来源；换到乙时，甲这一份材料不会进入乙的上下文。生活感受则不会仅因切换交谈对象而消失。[^11]

EE 原包以 `character_id + relationship_id` 标识状态。适配后，逐人关系包继续保留这个边界，生活包使用内部保留的 `self` 命名空间，只允许写自身状态并禁用信任更新。这是项目对 EE 的扩展，`self` 本身不授予额外读取权限。[^11]

这类并列材料也容许局部变化：误会缓和不必同时消除疲劳，喜欢一个人不等于此刻想长聊。感受、行动意愿、实际表达与行动结果各自有依据，后续表达机制据此选择这一次怎样交流。[^3]

## 一段交流怎样留下有限的跨场景影响

有时，对甲的瞬间无语只留在两人的交流中；有时，反复越界让她在离开对话后仍想安静一会儿。后一种情况需要额外评价：当前交流留下什么未解决的事，为什么会影响下一件事，何时值得再看一次。

这个判断在冲突发生、当前交流结束或已安排的复看时进行。强度、持续时间、反刍和当前生活压力都可以参与理解，但没有一个固定强度充当自动开关。模型明确接受某种持续影响后，才形成跨场景余效 `Spillover`。[^12]

```text
Spillover:
  appraisal_id, private_source_ref, shared_effect, recheck_at, ended_at?
```

服务保留私有来源用于纠正和审计，共享部分则只含受限标签和简短影响描述。与乙交流时，模型可能得到“仍有些烦，想安静一会儿”，不会得到甲的姓名、原话或私人长摘要，也不能沿私有引用解读原因文档。脱敏失败时，服务拒绝发布这段共享描述。[^12]

模型仍可决定正常与乙聊天；余效不会直接扣乙的信任，也不强制把烦躁发泄给乙。它影响下一步判断，具体行动仍需理解眼前的人和事。[^12]

一份余效关联稳定的评价 ID。读取、复看或重新加载，都只是继续使用这份材料，不各自叠加一次刺激。误会澄清后，追加有来源的新评价，替代当前采用的解释并终止或重算相关余效；旧判断和原消息保留各自历史。借鉴 FAtiMA 的是原因、对象及重新评价的区别，跨联系人权限和余效接线由本项目补充。[^12][^13]

## 重试和并发时，怎样保住同一份状态

EE 核心函数对传入的状态对象计算并返回结果。首版从数据库读取状态副本，调用 `record_turn(state, ...)` 等需要的核心函数，然后由宿主将新状态、证据、时间锚点和结算键一并事务提交。数据库保存权威状态，不另维持一份能独立改写的 EE JSON 文件；CLI 的 `save_state` 也不作为权威写入口。[^14]

事务负责让这次变化作为一组提交，稳定键负责让重试仍指向同一次变化。宿主分别为来源事件、评价修订、关系证据和结算保留稳定键。上游防重集合有保留窗口，不能独自承担长期防重。两个请求发生版本冲突时，后到的请求重读当前状态，不用旧副本覆盖已经接受的变化。[^14]

本篇这条变化链在模型读回已接受的感受、据此选择行动时完成。一次交流还可能提供影响长期信任的证据；这些证据怎样保存、何时结算，以及等待工具时怎样结束当前批次，由[下一篇](08-关系怎样依据经历变化和纠错.md)接着展开。

模型只获得业务层读写能力。初始化、重置、迁移及手工改信任等管理命令不直接开放；`host_approved` 表示服务已经验证调用范围和来源，不是对模型提议的无条件相信，也不是每轮要求真人确认。[^14]

## 误会解开后，已经经历的感受怎样继续

继续本例：甲解释那句话只是指另一件已说过的小事，人物发现自己先前误解了催促的对象。服务保存纠正及其来源，旧评价标为被修正。接下来，模型从**当前时间已经推进后的状态**出发，对这份新理解作出新的评价。[^16]

首版对 PAD 和 pulse 不做历史回滚。误会中的烦躁曾经是人物的实际感受；澄清可以让她缓和，也可能仍留一点疲惫或短时余波。旧原因不再被当作仍然成立的事实，也不再作为同一刺激重复结算，但系统不要求所有余波立刻归零或按相反方向奖励一次。[^16]

如果这次误解还产生过不应成立的信任扣分，下一篇会说明怎样以有效证据重建信任。信任修复与感受继续变化各有一条路径。首版无法精确还原“这场误会从未发生”的情绪轨迹；若变化来自程序重复写入，则按幂等或版本故障处理，不把它混成人物的正常误会。[^16]

## 已选择的基础与仍要验证的部分

EE 提供了可查的身份、状态、证据、结算和恢复接口。原方案引用的 96 项指定离线测试只支持相应代码路径，并未证明这种适配能产生自然的中文人物表现。首版需要修改时钟、多人作用域和宿主持久化接线，完整函数保留清单、修改点和原测试适用性都要记录。[^4][^17]

上游 PAD 范围、人物基线、波动档位、证据权重和结算上下限保留原值与修改记录。它们是工程默认值，参数应通过固定时钟回放及以后获准的盲评校准，不能被当作心理测量结果，也不在提示词里无记录地改变。[^10]

相关研究用于明确借鉴边界：FAtiMA 提供原因与重新评价的检查视角，WASABI 提醒状态可按时间演化，Yuralume 展示有原因的事件怎样进入回复；首版不运行第二套情绪推导器，也不复制已经发现重复计入风险的混合更新链。Eros 与 BetterSimTracker 的短时感受、持久关系及文字材料分离，分别落在本篇、关系篇和表达篇；各项目未采用的规则及证据限制集中保留在[决定与来源](B-决定取舍与来源导读.md)。[^18]

后续验证先检查同一时间反复读取、同一事件重试、跨对象余效和纠正后的状态是否正确，再比较纯文字状态与 EE 适配。比较双方使用相同人物、事件和可见历史；若表达僵硬，先检查评价、实际输入和时钟。受控对照仍没有收益时，保留事件、来源、关系证据与时间能力，停用对应数值消费者。现在的基础选择和这个后续退出条件同时有效。[^19]
