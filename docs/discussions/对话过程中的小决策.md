### 建议内容（整理，非逐字原话）

1. **把运行语境与记忆查询目标分开。** `DecisionRun` 可以记录启动缘由和当前联系人；当前联系人是记忆检索的默认目标，不应成为禁止同一人物主动读取其他联系人记忆的硬边界。处理与甲的会话时，模型仍可根据需要选择查询同一人物与乙有关的记忆。这里提出的是记忆读取范围的调整，不是切换正在处理的会话或发送对象。
2. **记忆查询目标可选，省略时沿用当前联系人。** 记忆查询工具（现行拟议工具为 `memory.search`）可提供目标参数：未传时，从当前 run 上下文取得当前用户 ID；显式传入其他用户 ID 或名字时，允许模型主动选择查询对应联系人记忆。这里的“提取记忆”按本次语境指查询已有记忆，不是回合后的记忆候选提取；参数名称、具体 schema 和返回结构尚未确定，也不自动把同样变更推广到所有工具。
3. **在工具说明中明确两种用法。** 说明参数可以不传、默认目标来自哪里，以及显式提供 ID 或名字时会查询什么。查询目标不再被无条件锁死为当前会话联系人；这仍不等于自动注入全部联系人的记忆。名字歧义、找不到名字、没有默认联系人时怎样处理，以及跨联系人查询与后续对外表达权限如何衔接，仍待细化，不在本记录中补成决定。

### 整理后的用户原意（去口语整理，非逐字原话）

每次唤醒人物时，可以根据当时的情况重新准备上下文，例如重新组织当前背景。用户认可这种准备方式，但同时要求：交给大模型的对话列表，也就是消息列表，要接着这个人物与该用户上一次的真实聊天。当前背景可以重新组织，双方实际说过的话仍要作为可以承接的消息序列提供给模型，保留原来消息之间的顺序和来往关系。

用户用 coding agent session 作类比：其中有用户消息、助手消息，以及工具调用和工具结果组成的消息列表。这个例子要表达的是，后续处理能够接着前面的来往过程，知道已经说过什么、做过什么。这里借用的是消息列表承接上下文的意思，并没有要求把 coding agent 的内部工具日志搬到 IM 聊天界面，也没有授权向用户展示内部提示词、模型输入或诊断。

Between 要模拟的是人物与用户通过微信、QQ 这类 IM 软件交流。人在打开聊天窗口时，能直接看到上次聊到哪里；即使距离上一次聊天已经过去几天、几个月，之前的消息仍在那里。因此，人物再次与同一用户交流时，模型应该能够看到过去一段真实聊天原文，并从那里继续。最后一条消息是这段聊天接续的位置，但用户随后专门澄清：**不是只保留或只看到上一次的最后一句，而是要看到此前一段消息。**

用户担心，后续实现可能把“重新准备上下文”理解为每次先将过去聊天压缩成一段总结，然后只把总结交给模型。这样的处理不符合这项要求：可承接的原文消息序列不能全部被摘要替代。需要落实的是本轮实际提供给模型的消息列表中仍有那段原话；仅在数据库中保存原文、让模型之后有机会检索，不能等同于已经提供了这段可直接承接的聊天。摘要仍可以承担其他取材用途，但不能替代这里要求保留的消息序列。

用户提到“几十条、甚至上百条”，是说明真实 IM 中能够看到一段过往消息的体验，没有据此确定窗口大小。**模型究竟能向上看到多少条，目前未定，留给后续修订方案时继续思考。** 不能把它落实为只能看到一条，也不能把几十条或上百条固定成参数；同样，这不要求每轮无限加载全部聊天历史。具体窗口、加载及预算处理仍需要在保留一段真实原话的要求下细化。
