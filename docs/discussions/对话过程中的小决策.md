### 建议内容（整理，非逐字原话）

1. **把运行语境与记忆查询目标分开。** `DecisionRun` 可以记录启动缘由和当前联系人；当前联系人是记忆检索的默认目标，不应成为禁止同一人物主动读取其他联系人记忆的硬边界。处理与甲的会话时，模型仍可根据需要选择查询同一人物与乙有关的记忆。这里提出的是记忆读取范围的调整，不是切换正在处理的会话或发送对象。
2. **记忆查询目标可选，省略时沿用当前联系人。** 记忆查询工具（现行拟议工具为 `memory.search`）可提供目标参数：未传时，从当前 run 上下文取得当前用户 ID；显式传入其他用户 ID 或名字时，允许模型主动选择查询对应联系人记忆。这里的“提取记忆”按本次语境指查询已有记忆，不是回合后的记忆候选提取；参数名称、具体 schema 和返回结构尚未确定，也不自动把同样变更推广到所有工具。
3. **在工具说明中明确两种用法。** 说明参数可以不传、默认目标来自哪里，以及显式提供 ID 或名字时会查询什么。查询目标不再被无条件锁死为当前会话联系人；这仍不等于自动注入全部联系人的记忆。名字歧义、找不到名字、没有默认联系人时怎样处理，以及跨联系人查询与后续对外表达权限如何衔接，仍待细化，不在本记录中补成决定。

### 整理后的问题与用户倾向（非逐字原话）

用户希望把“聊天发生 → 产生记录 → 持久化 → 后续检索 → 放回模型输入”接成一条可以执行、可以验证的完整链路。说明记录将来能够用于回顾、状态更新、记忆或查询，只解释了它的用途；即使字段、结构和 ID 已经定义得很漂亮，也还要说明记录怎样产生，以及后来需要时怎样真正被取用。这里要解决的是机制的落地细节，不是据此断言整个项目做不出来。

生成记录时，先区分可以机械记录的事实与需要理解内容的材料。例如“十点收到甲的一条消息”，程序在收件时就有接收时间、对象和原文，可以直接保存消息及相应发生记录，无须先让模型理解正文。它证明收到了消息，不证明消息里的每句话都是真实事实，也不表示人物已经阅读。若要从聊天中提炼“甲最近工作压力大”，则涉及对已允许读取的内容作语义理解：这是甲明确说过的内容，还是模型根据几段话形成的暂定判断，需要保留区别与依据。不能把收件事实、说法、推断和为以后取用而整理的记忆统称为 Event，也不能说所有记录都必须由模型生成。

对于这类语义处理，现有原则还需要落到具体执行过程：在已经允许提取的时机中，何时实际建立或领取任务，由哪个模块组织输入、哪个模型处理，怎样提出值得保存的候选，服务按什么具体契约接受或拒绝；候选怎样关联原文，重复任务怎样抑制，错误或新更正怎样影响旧记录和索引，怎样核验保存确已成功。这些问题应沿用已经确定的模型与服务分工继续细化，而不是把已有分工重新写成全无约定。未读正文的语义分析仍受现行实际提供契约限制，机械收件记录不能成为绕过该边界的入口。

取用端也要同样具体。知道某个 ID 后能取回对应记录，与聊天再次涉及某个话题时能找出相关经历，是两件不同的事。例如后来又谈到工作，系统怎样想到去找甲之前的压力、相关原话和适用时间，而不是仅仅保存了“以后可以查询”的接口？需要明确哪些检索由程序准备，哪些由模型主动调用，怎样从当前问题形成查询，怎样筛选、排序和限制结果，以及选中的哪些材料最终进入了哪次模型输入。数据库里有记录、检索返回了候选、模型实际获得了材料，也要分别核对。

验证应覆盖这条链的两端和中间衔接：记录是否按应有触发产生、来源和保存结果能否回查、后续问题是否能召回相关材料、是否带入无关或过期材料，以及模型最终输入是否包含应提供的内容。漏检与误检需要具体检验，不能因为按 ID 查询成功或回复听起来连贯，就保证相关经历永远能找齐。用户认可的核心问题是：缺少生成端和取用端的可执行衔接，数据结构本身还不构成完整落地机制。

用户补充的倾向是，这部分最终可以通过一个合适的开源记忆库来落地，关键在于选择能承接这些需求的基础。后续可以围绕记忆产生、保存、检索及放回模型输入的实际需求评估它，而不只比较字段名称。这是用户的想法和未来评估方向，目前没有选定具体项目，也没有确认某个记忆库能够承担全部 Event、原始事实或审计记录职责；不能由此推导所有事件必须放进同一个记忆库，或把它写成已经确定的新架构。本轮没有启动这项评估。
