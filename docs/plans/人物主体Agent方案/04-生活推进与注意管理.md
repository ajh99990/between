# 生活推进与注意管理

更新：2026-10-26。状态：**本轮获授权作出的首版设计，待实施与效果验证**。本文负责“她何时做事、何时看消息、怎样继续未完成的事”，不定义情绪算法、平台接入或完整数据库。共同事实、时间和数据含义以[事实时间与数据约定](03-事实时间与数据约定.md)为准；目标原文见[愿望 1–4、8–10](用户愿望原文.md)。下文例子均为设计推演。

## 1. 首版采用的主线及取舍

**每个人面对同一份持续更新的当前处境。模型决定做什么；生活服务保存决定及进展，定时器在需要的时候再唤醒。** 新消息、活动检查点、实际工具结果与承诺到期都可以触发一次人物运行。普通私聊不能各自重新创造“她刚才去了哪里”。

| 本文选择 | 直接借鉴、适配或自主补充 | 采用理由与明确放弃的部分 |
| --- | --- | --- |
| 共享 `CurrentSituation`，计划与实际进展分开 | 适配 Eros 持久生活底稿与常驻近况；补充我方多人共享状态、时间和来源约束 | 重要当前信息不能依靠向量检索；不照搬全量重写人生底稿或重置世界时删除历史。[^e-story] |
| 滚动粗日程，加上有复核时间的当前活动 | 适配 Yuralume 已存日程、前后活动查询；共享当前活动是我方补充 | 有爱好就能提前安排时间；没有下一项计划时仍先确定此刻活动。放弃“填满日程即可证明已经发生”以及“各私聊即兴后追记”。[^y-schedule][^y-gap] |
| 持久化到期任务推进生活 | 适配 Yuralume tick 的生活、目标、公开行动分离，以及待办到期执行 | 没人发消息仍能推进；不每隔几秒调用模型，不要求每次醒来都发内容。[^y-tick][^y-pending] |
| 未查看与已看过后延办并存 | 已看延办改造 Yuralume；自主未读隔离是我方补充，参考 Eros 时间边界但不搬离线强制规则 | 忙碌只是判断材料；不以忙碌数值自动静音，也不因新消息来到就自动取消旧责任。[^y-busy][^e-offline] |
| 聊天中直接调用日程工具，回合后提取仅补漏 | 改造 Yuralume 逐回合后处理与日程变更服务 | 同一轮答应改期后立即有保存结果；放弃依赖异步后处理才能让下一轮知道新安排。[^y-adjust] |
| 开放发展类型的前向虚构生活生成 | 适配 Eros 生活事件及 Yuralume 活动收尾；按U17放开发展类型，保留我方共享提交规则 | 普通起点不锁定一生；先观察而不预设重大事件禁区或发生配额；不代演现实用户或捏造工具结果。[^e-story][^y-close] |

这些都是本轮方案选择，不是用户过去逐项批准过的实现细节，也不是自然性已经优于上游的实测结论。原样复用的提示词须另存固定版本；本篇解释与伪代码不是上游提示词替代稿。

## 2. 一次运行前，必须知道“现在采用哪份处境”

`ActivityPlan` 回答准备做什么，`CurrentSituation` 回答系统现在采用的活动与已知进展，`Event` 留下发生记录。三者独立；事件可发生在任何日程之外，时间重叠也不自动成为同一次共同经历。

当前活动可以是休息、通勤的虚构过程、真实浏览或等待导出结果。它不必等于一个日程条目，也不意味着只能做一件事：她可以在刷视频时聊天；后台导出可以继续运行。共享处境说明主要活动、适用时间和已知并行事项，具体动作执行状态仍由 `ActionIntent/ActionResult` 管理。

本文只消费以下最小信息，不另复制完整数据定义：

| 对象 | 这条流程必需知道什么 | 写入与下一位消费者 |
| --- | --- | --- |
| `CurrentSituation` | 当前活动、来源、何时确定、何时复核、最近已知状态是否过期 | 生活服务提交 → 每次人物决策与私聊上下文 |
| `ActivityPlan` | 起止、时区、内容、修订版本、约定引用 | 日程服务 → 当日安排、时间冲突视图与唤醒器 |
| `Event` | 发生时间、记录时间、来源类型、可见范围、必要的对象/结果引用 | 入口、生活服务、执行服务 → 状态重建和按时间取材 |
| `InboxItem` | 收到时间、正文位置、何时实际提供给模型、处理进度 | 通道入口与读取工具 → 该对象的后续交流 |
| `Commitment` | 尚未说出口的意图、已看后留待处理、已发出承诺三种责任含义；复看时间及关联来源 | 模型提议、服务保存 → 到期重新判断与履约 |
| `ActionIntent/ActionResult` | 想执行什么、正在做什么、实际取得什么、失败或结果未知 | 人物模型与执行服务 → 续跑和对外结果表达 |
| `WakeJob` | 为何醒、关联哪件事、到期时间、是否仍有效、处理状态 | 服务与调度器 → 人物运行入口 |

选择“接下来休息”证明选择已成立；模拟生活记录“休息后感觉稍好”属于虚构生活来源；平台返回“关注成功”才是外部操作结果。这三者不得因都有一个时间戳而混用。

一次有效生活变更，将事件、当前处境的新版本和必要唤醒在同一事务中保存；模型生成在事务外完成，提交时校验版本。服务拒绝“活跃生活已改变，却既无下一次复核也无关联到期任务”的半成品，返回具体缺项让模型补齐，不擅自补一个活动。管理员明确暂停人物运行属于另外的运维状态。

### 日程空白怎样处理

首版不要求预先把 24 小时精确排满；**要求每次对外回复前，有一份仍适用的共享处境，或者明确保留未知，不能各自补写。** 这解决的是上下文依据，而不是用数据库填表数量代表人物活着。

1. 有有效处境：直接沿用，不为每条消息重新规划生活。
2. 到了检查点：先检查实际结果、已知中断和后续约定，再由模型选择继续、结束、转向另一件事或休息。
3. 没有当前活动且没有计划：先运行一次只读共享生活材料的生活决策，模型从习惯、兴趣、关切、当前时间选择下一步；提交后私聊才能引用。
4. 处境缺失且模型/存储不可用：保留最后已知及“当前未知”。可以处理不依赖当前活动的交流；不得自动声称在休息、空闲或完成某事。

初次启动必须有经设定的起始处境，随后从当前时间向前推进。模型可以选择平淡的一天；不以“日程为空”惩罚人物或强迫制造活动。代价是增加一次可复用的生活决策及过期检查，比全靠回复临时发挥多一道提交过程。

## 3. 谁唤醒，醒来后做什么

采用持久化 `WakeJob` 与人物级单写入队列。数据库可以定时查到期任务，但只有真实到期、可见通知、有效结果或恢复事项才调用模型。定时扫描的频率是工程参数，不是人物思考频率。

| 触发 | 给模型的内容 | 不自动推导什么 |
| --- | --- | --- |
| 活动检查点 | 当前时间、计划、已知进展、变化事件 | 活动已成功完成 |
| 暂不查看结束 | 当下处境、收件箱概况 | 所有消息已读或必须回复 |
| 留待处理/承诺到期 | 该对象已读材料、自己曾说的话、期限与当前条件 | 自动发送原定模板或原问题已解决 |
| 工具结果到达 | 结果及实际接触的内容、关联意图、等待期间的状态变化 | 旧计划仍有效或必须继续下一步 |
| 生活复盘 | 当前关切、未完成事项和近期自己的生活变化 | 必须产生新目标、动态或主动私信 |

```text
处理一次触发(person, trigger):
  领取任务；读取最新人物版本；丢弃已被取消或替代的触发
  整理到期检查点、已返回结果和仍适用的承诺
  若当前处境缺失或过期，先完成共享生活决策并提交
  根据任务范围组装上下文；未查看正文不在其中
  运行人物模型，可查看消息、改安排、调用工具、延后或不行动
  每个写入由服务检查时间、权限和版本；成功才反馈给模型
  保存下次复核/唤醒；任务完成或记录可恢复的失败
```

只合并不带联系人私密材料的共享生活检查。每个私聊 `DecisionRun` 固定一个对象范围，不在同一 run 内从甲切到乙；调度器切换对象时领取该对象自己的 run 并重新组装材料。不同联系人的私聊正文不能因任务同时到期而混入同一上下文，只沿用允许共享的生活状态。

晚到任务先读当前时间和版本，不逐一重播已过时的生活检查。例如 14:10、14:20 两个检查点在 14:25 才取得执行机会，只需处理当前恢复判断，不伪造两次当时已经发生的决策。不同承诺仍逐件保留，不能通过合并丢掉欠谁什么。

## 4. 未查看、已看延办、自己的念头分别处理

人物可选择“现在允许通知”“到 14:40 再查看”等注意安排。作用范围必须明确：全局普通消息、某个通道或某段关系。缺省允许通知机会；这不表示所有正文自动进入模型。

未查看时只给允许的通知概况，如来源对象、通道、收到时间和条数；不含正文摘要、关键词、图片识别或基于未读内容算出的情绪。正文在 `inbox.read` 之后才可以参与理解。单凭发送者自称“紧急”不能突破既定不查看安排；首版不另设读取未读正文来替人物判断紧急程度的暗门。

| 情况 | 人物知道什么 | 服务保存什么 | 下一次怎样继续 |
| --- | --- | --- | --- |
| 选择半小时不看手机 | 自己的注意决定，不知道新正文 | 注意安排与复看 `WakeJob`；新消息仍存收件箱 | 到时模型决定查看哪些对象，再读取对应正文 |
| 已看到问题，想稍后认真处理 | 原问题、当下处境与自己的理由 | 对该对象的 `Commitment`，必要时关联已发短回复 | 到期取原话和最新处境，重新决定处理或改期 |
| 想发一张图，但现在不适合 | 自己尚未表达的动机 | 私有意图，带复看时间与失效条件 | 重访时可以放弃，不写成已经欠用户一张图 |
| 明确说了“八点发给你” | 自己已对外表达的责任 | 发送成功的原话、目标、时间与履行条件 | 没完成就继续保留；失败、改期和告知分别记录 |

借鉴 Yuralume 的原问题、短答、理由、复看时间及到期重新组织回应；不照搬“新消息自动取消 busy_defer”的规则。新来一句“那算了”是否取消旧请求，必须在实际读到后由模型判断；一句无关闲聊不会消灭先前责任。[^y-busy][^y-pending]

模型可以看过但不回复，也可以不发短答而留待处理；这时只是内部待办，不冒称已向对方承诺。对外短答和内部待办应协同保存，投递失败时待办仍在，但“对方已收到以后回复的承诺”尚未成立。

## 5. 聊天怎样立即改变生活

首版提供同一运行内的 `schedule.propose_change` 与 `schedule.commit_change`，先返回影响范围，再按人物选择提交。名称为方案接口，不宣称上游已有；服务中复用 Yuralume 的读取已有安排、按日期变更思路，重写历史保护和重叠处理。[^y-adjust]

改安排的输入至少带当前版本、目标时段、变化内容与依据。程序返回已有占用和对其他责任的影响；模型决定保留、改期、并行或取消。时间重叠不是数据库一律禁止的行为，但不得静默裁剪别的安排。

所有入口遵守同一规则：

- 过去已发生的时间段、原有安排版本与实际事件不可覆盖；管理员、模型工具、导入和整日重生成没有例外。
- 改正在进行的活动，变更从服务端当前时间生效；保留之前的实际经过和原计划，通过新修订改变剩余部分。
- 未来计划可以调整；已经对某人作出的承诺不会因为删除日程自动取消，应由人物处理改期或告知。
- 版本冲突返回最新状态，模型重看后再决定；不把旧模型输出直接覆盖到新版本。

例：14:12 甲建议一起看视频。她原本打算 14:30 整理图片，选择推迟至 15:00。工具先返回“15:00 没有占用”，提交成功后她才可说安排改好了；若提交失败，不能先说成功再依赖回合后提取修复。

回合后提取仍可发现漏记的邀请、时间和承诺，但只能提出变更候选。重用同一服务的版本、来源和时间检查；若新状态已变化，交回下一次判断，不能晚到后静默改写。上游 post-turn 是一次回复后的处理，并不是整段聊天结束，本设计进一步缩短已作决定与保存之间的间隔。

## 6. 开放的虚构生活如何持续产生

**按2026-10-26的U17，不再只准普通小事，也不要求重大变化经过管理员批准。** 生活可以向前发展，之后依据实际样本改进；普通人物是初始设定，不是永远不能换工作、搬家、发展虚构社交、遇到挫折或发生转折。保留一个生活生成与提交入口，不为每类经历新增一套导演Agent。Eros已有依既有人生资料、近期事件和关系材料生成新生活，再保存近况与事件的基础；我们适配为共享人物的前向修订，不照搬全量替换和按用户分人生。[^e-story]

### 开放发展，与事实来源分开

| 可由生活模型根据已有处境提出并提交 | 仍不能用模拟结果代替 |
| --- | --- |
| 休息、做饭、兴趣练习、拖延，也可以没有明显进展 | 真实工具尚未完成的文件、搜索、观看、关注、发帖或收款 |
| 换工作、搬家、家庭变化、新的虚构朋友、失败或重大经历 | 现实用户或现实第三人从未说过/做过的事，以及虚构的双方同意 |
| 兴趣、想法、生活习惯或虚构人际关系逐渐改变 | 把既有过去改成另一个版本，或把回复草稿当作已经发生的经历 |
| 虚构兼职中的邀约、选择、拒绝或拍摄过程 | 冒称真实摄影师、品牌订单、现实拍摄或实际返图存在 |

上述右列是既有的来源规则，不是重大事件审批。新虚构人物须有独立标识并标明虚构身份，不能随手套用真实账号，把对方编成朋友或恋人。虚构关系若涉及当前排他承诺，沿用[06的关系规则](06-情绪关系与表达.md)，生活生成器不能绕开同一人物已有的承诺。

### 模型怎样推进，不预写剧情

每次提供：当前时间、初始底稿及已生效修订、最近生活事件、自己的关切、已定安排、可用资源、尚未处理的责任和相关已知结果。模型可以决定继续、改变、结束、引入新的虚构变化或暂不产生新事件；输出变化内容、时间、依据、影响哪些当前字段及下一次查看时机。理由是可审查的简短说明，不索取隐藏思维。

生活服务只核对来源、前后冲突、过去保护、版本及必要后续记录；不因为“这件事太重大”拒绝。缺前因时可以在当下开始一件新事，不能补造过去的铺垫。职业和居所等变化通过带生效时间的 `ProfileChange` 与生活事件共同保存；原始底稿和旧版本仍可回查。生效后所有联系人读取相同当前情况。

例如，初始设定的订单文员工作让她越来越厌倦。她可以今天决定尝试找工作，随后发生投简历、改变主意或离职等**虚构生活进展**；服务不弹出“重大变化待批准”。若实际要在真实招聘平台投递，则另走真实工具与其执行结果，模拟成功不能冒充现实录用。她也可以继续干原来的工作，没有规定几天内必须发生转折。

不设“每天一件新鲜事”“每周一个大事件”或自动悲剧/升职/恋爱配额；这些会让生活被任务表牵着走。这里只要求模型依据人物和当时环境作选择，不用新的硬性频率或事件白名单收回U17。验证中单独观察是否高频戏剧化、过快改变偏好、刚遇挫折就寻求用户拯救，看到样本后再讨论具体修正。

### 三次写入讲清过程

假设已设定她有虚构居所和插画爱好，今天休息：

1. **10:00 开始。** 生活模型得到时间、兴趣、既有生活和后续约定，选择画一会儿。服务写入带模拟来源的开始事件、当前处境和 10:30 检查点。此时只能说正在画，不能写完成作品。
2. **10:30 推进。** 模型得到这半小时的起点、有效中断、实际工具动作及仍待处理事项，可以生成“画了部分线稿，想换个构图”的普通虚构进展；也可以决定没进展。服务检查未与已确立事实冲突后提交为共享生活事件，并更新当前处境。
3. **之后读取。** 甲和乙分别来问，都读取同一份 10:30 近况；两人的私聊记忆各自保存。若她真要把作品发出来，必须通过真实素材制作/发布工具获得作品和结果，不能把文字里的线稿当成已有图片文件。

一个活动只有粗粒度开始、进展和结束，不补出每一分钟的动作。模拟结果可以描述已经开始的这段虚构活动，但记录时间、模拟来源和所依据的起点明确保留；它不能倒改已经向外确立的经过，也不能补写尚未开始的上午生活。

新生活细节先进入生活提交路径，再成为回复依据。回复模型若临时写出“刚买了咖啡”，却没有对应已确认设定、生活提交或工具结果，不得仅因这句话被说出就升格为共同生活事实；具体主张检查与来源规则见共用数据专题。模型可能表达误解，系统不得把它和实际发生混成一类。

代价是更开放的发展可能失去普通人的节奏，需要保留完整变化轨迹观察；目前没有效果验证。收益是人物可真正改变，而共享提交仍避免各私聊各编人生。早期“只准普通生活”的规则已撤销，不以固定语气或事件上限暗中恢复。

## 7. 长任务、停止与恢复

### 浏览与内容制作不会独占人物一小时

一次 B 站浏览是一个可含多次模型和工具调用的 run。模型可以搜索、选择视频、读取可得内容与评论、继续或结束；不是固定搜索几个标题后强行总结。运行预算是服务上限，模型仍有机会自行决定结束，超限则明确保存为暂停，不能写成“她不想看了”。

外部耗时动作先保存 `ActionIntent`，执行服务异步工作。人物写入队列不因等待上传/导出/网络返回而一直占住；结果回来产生新的触发，人物读取当前状态再续跑。来信可以入库，按注意安排决定是否查看；工具执行中的每个安全交接点都可重新取得人物最新版本。

同一 run 的私有上下文不能直接拿去回答另一人；切换对象需重建范围。公开内容任务也不能继承私聊全文。对外效果已发生但回执丢失时先核对平台，不以重试重复发布；执行与幂等细节由平台执行专题统一定义。

### 角色睡觉与服务停机是两件事

- **角色睡觉：** 模型选择的活动与注意安排仍有效，留下一次起床检查；普通消息入箱。程序无需在睡眠期间不断问模型“醒了吗”。若另有已经承诺的定时事项，需在入睡决策时处理，不能自动消失。
- **服务正常但定时任务稍晚：** 合并过时检查，模型从已存起点处理当前进展，记录真实执行时间，不伪造准点执行。
- **服务中断：** 原始输入、未完成意图、承诺和唤醒持久化；停机不是人物主动冷落。恢复时核对仍在运行或已完成的真实任务，再进行一次恢复判断。
- **停机跨过活动期限：** 不批量补演错过的计划，不编造期间已浏览、发布或发生的一串新事件。保留最后已知与中断，模型从现在恢复普通生活；没有结果的动作仍未知或待核对。

恢复并不要求人物永远说技术故障，也不能靠捏造“刚开完会”掩盖缺失。可以处理仍有充分依据的内容；依赖缺失经历的问题保留不确定，并等待当前处境恢复。情绪随时间的数学演化可以按已选情绪系统计算，不等同于补造新的外部刺激。

## 8. 一段贯穿流程：刷视频、被打断、留待处理

以下均为自拟行为，不是推荐台词或模型测试结果。平台动作以未来实际适配器返回为前提。

| 时间 | 输入与人物选择 | 服务写入、下一轮读取 |
| --- | --- | --- |
| 14:00 | 自己的兴趣、下午安排；选择浏览 B 站，允许通知 | 保存当前活动、浏览意图、复核时间；日程只表示预计持续一段时间 |
| 14:03 | 真实工具取得 V1 的字幕片段及评论；选择继续看看 | 保存取得范围与结果；对内容的理解关联来源，不宣称全片已看 |
| 14:10 | 甲来信，先出现通知概况；她选择查看，获得甲发来的 V2 链接 | 原文首次进入甲上下文，保存实际提供时间；V2 浏览任务与甲私聊范围关联 |
| 14:14 | 取得 V2 的部分内容，双方讨论观点 | 甲相关的对话/事件独立保存；不强行改日程正文，也不进入乙的私聊上下文 |
| 14:18 | 她觉得资料要再看，短答后留下 14:40 再处理甲的事项；另外决定到 14:35 不看新消息 | 留待事项与注意安排分别保存。14:35 查看、14:40 处理是两件事 |
| 14:22 | 乙发来消息，注意安排仍生效 | 只入收件箱；正文不进入模型、摘要或情绪计算 |
| 14:35 | 复看到时，当前仍在浏览；她选择先看乙 | 重建乙上下文，沿用自己的活动及可共享已知进展，不带甲的视频请求和观点 |

这里的连续性来自共用当前活动和明确读写；不是把所有人的经历写进一篇总记忆。对甲的后续承接依靠甲自己的材料与相关时间；乙能知道适合分享的自己近况，但不会因为同一时间聊天就获得甲的私事。

## 9. 必须验证的失效情况

本文设计可通过确定性服务测试与授权后的真实模型试验分别检验，不用两个人物聊得很久替代这些检查。

- 同时收到甲乙的“干嘛呢”，不得生成两份互斥当前活动；检查共享版本及回复引用来源。
- 暂不查看期间给乙正文放一段独特内容，人物决策、摘要和情绪输入不得出现它；到实际查看后才可使用。
- 已看后留下事项，再收到无关闲聊，旧事项不应凭空消失；明确取消应保留取消依据。
- 调整当前活动时不能修改已过去部分；未来重叠必须返回给模型，不静默裁剪其他承诺。
- 虚构活动正常推进要产生可用近况；真实浏览失败不能生成“已经看过”，模型临时自述不能直接变成生活事实。
- 延迟回执、重复唤醒、并发版本变化与重启不得重复发布、重复解决责任或复活已取消安排。
- 没有消息的一天仍有休息、兴趣与关切的正常推进；不能每次检查都制造新剧情、发动态或主动找人。

若真实对话仍频繁即兴补写，优先检查当前处境是否实际注入、是否过期及写入是否先于回复；不能只不断加“不要编造”提示。若生活毫无变化，检查是否所有检查点都只做程序扫描而没有运行生活决策。
