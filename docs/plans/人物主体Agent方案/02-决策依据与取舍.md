用户认可并要求记录的研究起点，继续原样保留：

> 接下来研究人物行为，应先问：她正在做什么、在意什么、注意到了什么、愿意投入多少，再看这条消息怎样影响她。她也可以主动改变安排、处理自己的事情，或者暂时什么都不做。这样才能讨论一个持续生活的人，而不只是每轮怎样接话。

## 本轮依据授权作出的设计选择

这里解决旧方案的未决项。理由和取舍概括在此，具体读写、来源和反例只在责任专题维护，避免两套规范。

| ID | 选定方案 | 比较与取舍 | 细节、来源、验证 |
| --- | --- | --- | --- |
| D01 | 滚动粗日程 + 共享当前处境；过期先更新或明确未知 | 全天填表不能证明实际发生；逐聊即兴会分裂近况。增加生活提交和有效期检查，换取统一依据 | [04](04-生活推进与注意管理.md) §1–3；T01/T13 |
| D02 | 允许有限、前向的普通虚构线下生活 | 纯真实工具会让人物没有身体日常；自由导演又容易生编重大经历。仅在既有底稿内模拟普通进展，与真实平台分开 | [04](04-生活推进与注意管理.md) §6；T05/T13 |
| D03 | 到期/事件触发的持久唤醒，不每分钟固定跑模型 | 没人来信也可继续；按需启动降低空转，不强迫每天发帖 | [04](04-生活推进与注意管理.md) §3/7；T13/T14 |
| D04 | 默认允许通知机会，正文经读取；主动不看与已看待办独立 | 不复制忙碌分数强制静音，也不复制新消息自动删延期。更细的状态是代价，换来可解释责任 | [04](04-生活推进与注意管理.md) §4；T02/T03 |
| D05 | 同run显式日程变更，回合后提取只补候选 | 让说定的改期马上可查；模型需处理失败，后台不得静默晚改历史 | [04](04-生活推进与注意管理.md) §5；T04/T07 |
| D06 | 来源/含义/时间/范围分别保存，不设万能真伪分 | 用户自述可以有价值却不能改写共享历史；多些字段，避免“系统给的都是真” | [03](03-事实时间与数据约定.md)；T05/T06 |
| D07 | 记忆先持久化，索引异步；对象过滤先于检索 | 不复制索引失败就丢新记忆；结构化/全文降级增加索引状态管理，保留来源和回查能力 | [05](05-记忆与上下文.md)；T02/T05/T14 |
| D08 | EE单一核心；生活感受+逐人感受+显式受限余效 | 单一情绪会被多人搅乱；完全逐人又无法延续严重冲突余味。保留局部、不全量求和；FAtiMA仅借原因/对象语义，WASABI不叠加 | [06](06-情绪关系与表达.md) E01–E03；T10/T11 |
| D09 | 信任用有效证据结算，关系理解/边界/承诺另存 | 不用互动量、礼物和缺席驱动分数。需修时钟、批次和纠错，不能声称上游直接满足多人场景 | [06](06-情绪关系与表达.md) E04；T10/T11 |
| D10 | 先理解交往目的，再按语境取正反例；保留自然不完美 | 情绪标签不是台词模板；不全局词语替换、不第三次必发火、不拒绝所有识图求助 | [06](06-情绪关系与表达.md) E05；T12及人读对照 |
| D11 | 首版允许亲近但不提供秘密排他的恋人承诺 | 共享公开人物无法合理地向每个人保证唯一；保留真实共同经历，放弃用隐瞒多方承诺制造投入 | [06](06-情绪关系与表达.md) E06；T05/T09 |
| D12 | 三平台目标不缩水；读取和写入窄适配，短完整探索有硬上限 | Agent-Reach/CLI/上传器各有能力缺口；不整体开放shell，不拿内建feed代替平台 | [07](07-社交平台与内容生活.md) P01–P03/P06；T07/T08/T16 |
| D13 | 兼职模特保留为虚构背景，真实产物从数字创作和观后内容起步 | 不凭图片生成证明现实拍摄/品牌合作；行业知识缺口承认并补查。相比实体职业更容易形成可验证成果 | [07](07-社交平台与内容生活.md) P04；T09/T16 |
| D14 | 私人资源经检查、自愿采用、实际产出、许可后公开 | 不是收到就奖好感/发帖；公开作品与私人来由分开。增添许可及可识别性检查，保持微妙体验而不泄密 | [03](03-事实时间与数据约定.md)、[07](07-社交平台与内容生活.md) P05；T09/T15/T17 |
| D15 | Python模块化单体+PostgreSQL；人物短决策步骤、持久任务/outbox | 便于适配Yuralume与EE；不用旧栈约束，也不堆微服务。慢工具让出机会，版本冲突只重决未执行部分 | [08](08-运行架构与工具契约.md)；T07/T08/T14 |

## 为什么不将旧讨论简单删掉

此前担心空日程导致人物随口编经历，进一步担心自述被提取成记忆、不同用户看到不同生活；D01/D02/D06/D07共同处理这条链，不仅补一句提示。此前担心情绪拆分导致变量暴增，D08保留每人一份关系感受和一份生活感受，只有明确余效跨场景，不建立任意人物组合矩阵。

用户指出事件不必属于日程、也不该把所有私聊汇成总经历，U03/U08保持这一修正；D01维护当前活动并没有撤回事件解耦。用户认为工具过程通常不必进入聊天记忆，D07只确保结果能查，不把全量工具返回注入记忆。

原方案的候选讨论与此前核查范围可在[固定历史版本](https://github.com/ajh99990/between/blob/d5febdc6b276a8611de03a7f64d2531cf9f7c484/docs/plans/人物主体Agent设计方案-v0.1.md)查看。外部机制细节仍保留在研究资料库，不用本轮选择重写上游事实。

| 原文条目 | 设计落点 | 后续怎样判断没有做偏 |

| 7 理解交流意图 | 06/08窄审查 | 正常帮忙与测试挑衅分别理解；虚拟身份真实 |

| 10 关系与测试 | 06证据/边界、09验收 | 可解释关系发展，完整记录让人评判；双Agent不替代真人反馈 |

## 当前仍缺什么

缺的是实施与效果证据，而非继续搁置架构选择：EE适配后的数值校准、主模型与表达材料的同条件比较、三平台真实接入/可见性验证、微信项目与账号、兼职模特一手知识都尚未取得。它们分别有09的门槛及07的资料范围，不影响本次文档定稿，也不能在定稿时称已解决。

在接入真实用户前还须确定部署成本、容量、数据保留期及最终人物设定。这些属于实例配置与实施输入，不把目前候选年龄范围、首轮探索预算或未经核实的行业情况写成永恒产品事实。
