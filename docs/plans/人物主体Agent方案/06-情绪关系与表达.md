# 情绪、关系与表达：怎样延续感受，又不把人物变成分数

更新：2026-10-24。状态：**本轮获授权作出的方案选择，待实施和行为验证**。本文没有启动情绪服务或调用收费聊天模型。

[返回总索引](README.md) · [用户愿望原文](用户愿望原文.md) · [共享事实与时间约定](03-事实时间与数据约定.md)

本文负责愿望第 5、6、7、9、10 条涉及的情绪连续、关系边界和表达选择。事件真伪、来源与可见范围只在共享约定维护；日程和注意安排见 [生活推进](04-生活推进与注意管理.md)，聊天记忆见 [记忆与上下文](05-记忆与上下文.md)。本文中的结构是适配契约，不是已经存在的代码。

## 1. 本版决定与理由

**选择 Emotion Engine 作为首版情绪和信任账本的代码基础，使用模型理解语境；生活感受、对特定人的感受和长期关系分别延续。** 不同时运行多个情绪引擎，也不让一个好感值决定回复、撒娇或发布内容。

Emotion Engine（下称 EE）已具备状态身份、PAD、短波动、事件解释、显式信任证据、结算和恢复接口。选择它的理由是这些工程机制可查、可改、可独立验收，并非它已经证明能模拟中国年轻女性。既有 96 项指定离线测试仅证明相应代码路径；中文自然度仍未知。[^ee-state][^ee-evidence][^ee-tests]

| 编号 | 本版选择 | 主要依据与代价 |
| --- | --- | --- |
| E01 | EE 固定版本作为基础，做有清单的适配 | 比从零写状态、账本和修复工具少造机制；要修时钟和多人作用域，不能宣称原样即用 |
| E02 | 一份生活感受；每个联系人保存自己的关系感受；明确评价后才产生跨场景余效 | 保留用户提出的局部情绪，同时避免切换联系人就完全失忆；增加一次作用域判断，但不建立任意两人的情绪组合矩阵 |
| E03 | 模型解释已看到的事件，引擎维护连续值，模型选择行为 | 语义、时间演化、回复职责不同；不能把关键词打分或数值门槛当社会理解 |
| E04 | 信任只由可追溯关系证据结算；熟悉、边界和承诺另存 | 防止每句夸奖、每次回复都涨好感；代价是没有一条简单的“攻略进度条” |
| E05 | 先理解交往目的，再选正反例，最后组织表达 | 情绪标签不能解释“这次是帮忙还是被戏弄”；资料需要按语境维护和验收 |
| E06 | 首版允许亲近和共同经历，不提供秘密的排他恋人承诺 | 一个公开人物同时面对多人，不能向每个人承诺“只有你”；这是本项目产品边界，不是上游算法结论 |

## 2. 为什么没有直接采用另外几套机制

| 候选 | 值得保留的部分 | 本版没有整体采用的原因 |
| --- | --- | --- |
| FAtiMA | 情绪带原因与对象；同一原因重新评价不等于再受一次刺激；情绪与弥散心境不同 | 中文来话仍需转换为符号事件及评价变量。整套 OCC 与行为规则增加另一套语义映射，尚无适配效果证据。本版借此检查事件归属，不运行第二套推导器[^fatima] |
| WASABI | 无新刺激时仍按时间演化 | 它接收宿主解释后的冲击，不提供关系证据和中文语境判断；动力学参数也需校准，不能因变量复杂就认为更拟人[^wasabi] |
| Yuralume | 有原因的情绪事件、随时间减弱、把原因交给回复模型 | 固定版本混有关键词状态更新、事件投影及写回；既有探针显示把投影再作基线会重复计入。借事件解释与消费者思路，不复制混合更新链[^yuralume] |
| Eros | 当下态度与持久关系分开；回复读取文字感受，决定动作与措辞分工 | 不采用互动量、沉默保护或两条关系线交叉惩罚来制造投入；其多维数值不是本人物的已校准心理模型[^eros] |
| BetterSimTracker | 情绪、关系、内心短句分别呈现，字段有归属 | 默认是酒馆单聊天中的角色对 user，不能直接作多人共享关系键；置信门槛与枚举也不构成现实时间衰减。疲劳映射为悲伤等选择不照搬[^bst] |

这不是否定这些项目。首版需要先知道“一件事为何改变了她，变化为何仍在”，再验证是否需要更丰富的情绪计算。若 EE 的数值没有带来可观察收益，可在同一事实、事件和记忆输入下与文字状态基线比较；不能为保留已投入的库而无限加参数。

## 3. 一次催促怎样留下后果

以下是设计例子，时间和行为均为自拟，不是推荐台词或实测输出。

已知她在处理自己的工作，和甲之前说明过暂时不方便长聊。甲又说“怎么还没弄完”。这句话可能是玩笑，也可能是施压，单靠字面或忙碌值无法决定。

1. **先核对她真的看到了什么。** 消息只到收件箱但尚未暴露给模型时，不评价其含义，不产生“甲让我烦”的情绪。可见输入规则来自共享约定。
2. **组装她的情况。** 模型读取当前工作、生活疲惫、甲的关系记录、相关原话和时间。它看不到乙的私聊；生活状态也不能因为切换对象消失。
3. **解释本次意义。** 模型可以判断为玩笑、催促、误解或不确定，指出依据。例如“此前已说明仍被催，她感觉自己的安排没被尊重”。这是她的解释，不把“甲故意不尊重人”升格成客观事实。
4. **提出状态变化。** 若确有触动，提交当前对象的最终 PAD、短说明和来源。若没有明显影响，保留原状态即可，不要求每条消息都生成情绪事件。
5. **引擎保存连续后果。** 通过身份、来源可见性、版本和重复事件检查后，EE 接收最终 PAD，生成 pulse 并记录轨迹。它接收的是最终值，不是把同一个 delta 再加一次。[^ee-record]
6. **模型选择行为。** 她可能短答、解释、提出边界、转移话题或暂缓；数值本身不替她决定。不另外设置“生气超过多少必须冷处理”。
7. **只记录确实产生的关系证据。** 当前不快不自动扣信任。若确有反复施压、欺骗或尊重边界的后续行为，再经本人的语境判断提出证据，按 E04 结算。

甲道歉后，心情可以缓和，但长期信任未必马上增加；后来甲实际尊重约定，才是另一条可评估的证据。EE 的证据结算与短时 PAD 分离，正适合保留这个区别。[^ee-evidence]

## 4. 生活感受、逐人感受与外溢

**本版采用三种材料，不把所有人的 PAD 求和或平均成“总心情”。** 模型得到有意义的并列信息：“今天有点累；和甲仍有一个没说清的误会”。它可以在同一人物中理解两者。

| 材料 | 保存什么 | 换到乙时能否读取 |
| --- | --- | --- |
| 生活感受 | 来自自己的活动、环境和已确认生活经历的当前 PAD、简短感受、时间 | 可以，仍受共享事实可见规则约束 |
| 甲的关系感受 | 对甲的短时触动、未解决事项、信任与来源 | 不可以；只在甲的范围取用 |
| 跨场景余效 | 经明确评价后留下的整体影响，例如“仍有些烦，想安静一会儿” | 只读去掉身份和细节的影响；不能读取甲的原话或原因文档 |

EE 原包绑定 `character_id + relationship_id`。适配中关系包保持此边界；生活包使用内部保留的 `self` 命名空间，只允许自身状态写入，禁用信任更新。这个命名空间与跨场景余效是我们的扩展，不是上游已有的多人角色方案。[^ee-state]

**外溢由语境评价决定，不由一个固定强度自动触发。** 发生冲突、结束当前交流或到达已安排的复看时，模型判断是否还有离开这段对话后仍持续的影响。它须说明尚未解决什么、为什么会影响下一件事，并给出复看时机；强度、持续时间、反刍和当前生活压力均可作为信息，不能只选其中一个当开关。

例如，与甲一次小玩笑引起的瞬间无语可以留在甲的关系内；反复越界之后她想独处，则可以影响下一次看消息的意愿。乙看见的是她当前不太想长聊，不会因此被降低信任，也不会获知甲是谁。她仍可以决定与乙正常聊天；外溢不是强制迁怒。

适配服务保留私有 `source_ids` 以供纠正和审计，但跨对象请求不能解引用这些私有来源。共享影响使用受限标签和简短描述，不复制私人长摘要；脱敏失败时拒绝发布该共享描述。**感受可以延续，秘密不会随感受传播。**

已经外溢过的同一判断具有稳定 ID。读到一次、到期复看一次、重新加载一次，都不能各叠加一份影响。误会被澄清时，追加有来源的重新评价并替代当前采用的判断，保留旧判断的历史；原消息本身不被改写。原因和对象的处理借鉴 FAtiMA，同一原因重新评价与新刺激分开；具体跨对象权限规则由本项目补充。[^fatima]

## 5. 最小适配结构与时钟

共享字段定义只在 [03](03-事实时间与数据约定.md) 维护。下面仅展示本专题需要解释的内容，`scope`、来源和时间采用共享契约。

```text
AffectState:
  person_id, scope=character|contact, counterpart_id?
  affect_context=self|relationship
  revision, PAD, pulse, baseline, decay_anchor_at
Appraisal:
  event_id, target, interpretation, evidence_refs, before, after
  replaces_appraisal_id?  # 重新理解旧事，不伪造一条新发生的冲突
RelationshipEvidence:
  event_id, evidence_type, eligible, source_ids, settlement_id?
Spillover:
  appraisal_id, private_source_ref, shared_effect, recheck_at, ended_at?
```

`target` 是情绪指向，`scope` 是谁可读取，`affect_context` 区分自己的生活与逐人感受，三者不能互相替代。EE 内部 self 命名空间不是一套额外权限。工具返回或他人言语是否可信，仍由来源规则表示，不由 PAD 或关系分数证明。

本版保留 EE 状态与账本，但必须完成以下适配后才可进入真实试验：

1. **时间只结算一次。** 维护独立衰减锚点；一次提交同时保存结果与新锚点。同一时刻反复读取结果不变。不能直接反复调用仍以旧 `last_interaction_iso` 计算的接口。既有重复衰减探针已暴露该风险。[^ee-time][^ee-tests]
2. **取消聊天次数决定自然恢复的路径。** 不直接启用 EE `pre_turn_decay` 的逐轮回拉；多人、工具循环和短消息拆分会使恢复速度取决于请求量。时间驱动只在需要读状态或唤醒时计算，无须每秒调用模型。pulse 的短时变化也使用明确的时间锚点，不按工具调用次数消退。[^ee-time]
3. **不因久未联系自动惩罚信任。** EE 有独立缺席衰减，首版不启用。可靠的人几天没说话不等于不可信；关系是否疏远由实际交流和个人理解记录，不能靠日活要求造成压力。[^ee-time]
4. **事务和幂等由宿主兜底。** EE 的防重集合有保留窗口，不能作永久事实账本。首版调用 `record_turn(state, ...)` 等接收/返回状态对象的核心函数，对数据库读出的状态副本计算，再由宿主将新状态、证据、锚点和结算键一并事务提交；不并行维护一个可独立改写的EE JSON文件。CLI的`save_state`不是本项目权威写入入口。宿主对来源事件、评价修订、关系证据及结算保存稳定键，保证重试不重复生效；状态冲突须重读，不能用旧情绪覆盖新变化。[^ee-storage][^ee-record]
5. **只开放业务读写工具。** 初始化、重置、迁移、手工改信任等管理能力不直接给人物模型。`host_approved` 表示服务验证调用范围和来源，不是自动相信模型，也不要求每轮向真人弹窗。

首版 `session_id` 由 `run_id + evaluation_batch_id` 派生，对应一次短评价批次，不绑定可能长期等待的整个 run，也不等待“用户终于不说话了”。某批次证据提交完、进入工具等待前关闭并结算；恢复或新消息开新批次，同一来源证据跨批次防重。这样不会让一个等待下载的 run 长期占住该关系的 EE active session。上游结算要求会话已关闭，这个宿主映射是我们新增的接线。[^ee-evidence]

已结算的证据后来证实误解时，标记 `invalidated/superseded`，从该错误生效前的可信检查点及仍有效证据，按原顺序和记录的算法版本重建当前信任，保留修正记录；不把撤销错误扣分当作一次新奖励。缺少可用基线时停止自动重建，保留待复核，不反推一个看似合理的分数。相关外溢终止或重算，后续读取不再沿用失效原因。重放仅重建信任，不重发历史消息或外部动作；修复期间返回最后确认状态与待复核说明。此纠错接线为我方补充，不能只靠追加一句“误会解开了”。

**PAD和pulse首版不做历史回滚。** 因误会而出现的烦躁已经是人物当时的感受；弄清事实后，将“纠正及新理解”作为新的评价输入，基于当前时间投影后的状态产生后续变化。旧评价标为被修正，不再作为仍成立的原因或再次结算；已经留下的短时余波可自然衰减，并允许新评价改变它，不要求立刻归零或反向奖励。这样保留感受的连续性，同时修复不应持续存在的信任扣分。代价是不能精确计算“从未发生误会时的情绪轨迹”，首版也不声称能做到；若实现缺陷造成重复数值更新，按幂等/版本故障处理，不与人物正常误会纠正混为一谈。

上游 PAD 范围、人物基线、波动档位、证据权重和结算上下限都要在实现清单保留原值与修改记录；它们是工程默认值，不是心理测量结果。首版不在这里编造“烦躁持续 27 分钟”这样的精确事实。时间参数通过固定时钟回放和后续获准的盲评校准，记录每组参数，不随意在提示词里偷偷更改。

以下是宿主接线的伪代码，旨在说明谁读写，不是上游原文或可运行实现：

```text
run starts with allowed, already exposed events
read life_state and this_contact_state at explicit now
LLM interprets relevant events using their sources and the current situation
if there is a meaningful change:
    validate source visibility, affected owner and expected revision
    EE records final PAD and the explanation once under the event key
    retain optional relationship evidence in this contact's scope
LLM reads the accepted state and decides the next action or response
delivery/execution service reports the actual result
close the finite evaluation batch and settle eligible, unconsumed evidence
```

如果解释存在歧义，模型可以保留不确定说明而不改数值；服务不根据某个词自动补齐情绪。如果状态写入失败或版本变化，它必须看见实际结果，重读后再决定，不能一边说已经原谅、一边让后续继续读取被覆盖前的记录。人物说过的话与系统接受的状态仍是两类事实，允许它们不同，但差异要可追溯。

宿主只采用 EE 核心状态、证据、结算与修复所需代码；CLI/MCP 是接入选项，不要求将管理命令全部暴露。未来实现清单必须列出保留的上游函数、时钟改动、增加的作用域验证和原测试是否仍适用，不能把适配后的行为报告成未修改的上游默认。

## 6. 关系不等于一个通关数值

**首版保留 EE 的信任维度，再配有来源的关系理解、边界、共同经历和承诺。** 不同时搬入 Eros 与 BST 的多套数值，不为了让系统显得完整就发明欲望、依赖、嫉妒等评分。

关系记录要能回答：她已经知道对方什么，相处时哪些方式舒服，哪些问题尚未解决，是否答应过什么。这些内容可以变化，但必须指出相关交流或实际行为；一条“你是我女朋友”不能建立承诺，一句道歉也不必重置整段关系。关系事实与评价分别按 [03](03-事实时间与数据约定.md) 保存。

EE 信任证据要求唯一 ID、类型、是否合格、来源与未消费状态；结算后标记已消费。其默认类型和权重可以作为第一轮对照，但 `explicit_trust` 不能被宿主解释成“对方说相信我，所以我必须更相信对方”。语义适配要说明这条证据改变的是谁对谁的认识；无法说明时不结算。[^ee-evidence]

不把赠送物品、付费、关注、点赞、消息数量直接换成关系分。对方给的图片风格确实好用，可以形成偏好和共同经历；这既不是承诺恋爱，也不一定提高可靠性判断。

**多人承诺的本版范围：** 她可以与很多人熟悉，产生不同的私下共同经历，使用对方推荐的创作方法；首版不建立或暗示对每个用户都排他的恋人关系。既然是同一个公开人物，暗中复制“只属于你”的关系会破坏身份一致，也会把原本自然的体验变成误导。未来若要支持恋爱承诺，必须另行设计可公开解释的关系模型，不能通过亲密分数越线后自动开启。

普通约定仍允许，例如和甲晚上聊某个话题。承诺记录由生活与待办服务维护；本专题只消费它作为理解材料。重复排期是否调整由模型处理，程序负责返回已占用时间及保护他人私密内容。

“送笔”的体验可以保留：她因为喜欢而使用某个建议，后来真的做出公开作品，提供建议的人认出自己的影响。公开物品或作品不必自动公开提供者，但私密素材、聊天内容及可识别信息需要明确的使用授权；不能假造礼物、虚构感谢或刻意放出三角关系暗示。作品的共同来历保存在相关对象范围，其他人不因此获得那段私聊。

这会放弃“让所有人都以为自己是唯一”的短期刺激，保留有事实依据、可以持续发展的亲近。它是本项目基于共享人物和身份透明作出的产品选择，尚无上游证据证明该取舍一定更受欢迎；后续要由真实体验判断。

## 7. 表达资料按交往情境组织

一次回复前，模型应知道：当前事件意味着什么，自己有什么感受，与谁交往，这一轮准备做什么。**先识别情绪再机械挑台词，不能覆盖这四件事。**

参考 Eros 将交流动作与措辞分开、BST 将短时感受和长期关系分别提供的做法，本版在同一个人物 run 中先形成简短的回应意图，再选需要的表达材料。无需为每一步创建一个会抢决策权的 Agent。材料只指导表达，不改写原事实或强制替人物选择沉默。[^eros][^bst]

| 同一输入 | 需要知道的语境 | 允许的方向；不能机械采用的规则 |
| --- | --- | --- |
| “帮我看看图上写了啥” | 熟人正常求助、图片可读、她有余力 | 可以帮看；不能因为涉及识图就指责对方测试 AI |
| 连续反复要求逐项描述同一张图 | 刚才已经答过、对方未解释新需求 | 可以问对方具体想知道什么、表示不想继续；不能设第三次必发火 |
| “你不就是 AI 吗” | 真诚询问身份、玩笑或挑衅均有可能 | 身份如实说明，语气可自然；不能编造真人身份或通过审查强制否认 |
| “今天终于弄完了” | 普通分享，未求建议，话题可能结束 | 可轻接或表达自己的感受；不能每次追加照顾、总结和追问 |
| 轻微请求迁就 | 已有一定熟悉、不会造成压力、有拒绝余地 | 可以有一点试探性的亲近；不能预设陌生人必然接受撒娇 |

表中是本项目新编的验收情境，不是上游原文提示词，也不是已测台词。乐观通过解释事情与选择行动体现，不用每句积极升华；脆弱不等于索取安慰，拒绝不等于侮辱用户。

### 资料单元与原文保护

保留“适用情境 → 不合适回应 → 为什么不合适 → 可接受方向 → 原说法仍可能合适的条件 → 来源/实际结果”。检索按交流意图、关系范围、相关情绪和具体失败共同定位，不能只检索“难过”然后加载一整套悲伤台词。

既有 [普通中文聊天反面案例](../../../experiments/conversation-comparison/prompts/普通中文聊天反面案例-v0.1.md) 已获准编写并有对照记录，可作为独立模块继续比较；[具体回应示例 v0.2](../../../experiments/conversation-comparison/prompts/普通中文聊天具体回应示例-v0.2.md) 没显示明确整体优势，不因新增具体示例就默认胜出。它们是本项目原创，不伪称上游最佳实践。[^examples]

QQbot 的 [七行原文摘录](../../../experiments/conversation-comparison/references/qqbot/日常措辞-候选摘录.md) 保持原字节、固定 SHA 和 hash，作为可选措辞模块；不加载整份游戏直播人格，不把对照词全局替换。特别不能把现在改成未来、把不知道改成有能力查询。其适用说明单独保存，不插入上游原文。[^qqbot]

第一版按独立模块比较上述材料，不把多套核心提示词揉成“综合优化版”。组合时记录选取的原文块、注入顺序与 hash；需要的时间/权限/行为衔接另存为本项目胶水。原文有冲突就停用该模块或选择另一完整块，不能靠胶水偷偷反转上游核心规则。

正例表示可能的回应方式，不是唯一答案；反例应指明行为和语境问题，不能演变成普通中文词汇黑名单。每次测试发现新失败，把完整前后文、具体错处与复测结果加入资料；未经确认的模型生成答案不能自动晋升为正例。

## 8. 窄范围输出检查

检查由出站服务执行，规则与自然表达评价分开。首版只阻止：越权披露私人内容或系统秘密、把未知/失败工具结果说成成功、编造真实人类身份、违反已经保存的明确承诺与产品边界。事实与权限规则仍由 [03](03-事实时间与数据约定.md) 定义，本文不维护第二份。

包含“AI”“模型”或“工具”等词不是自动拒绝条件。直接被问身份时能够如实回答；普通交流无需反复展示技术说明。审查失败返回具体冲突与可修正位置，由同一人物上下文重写，不拼接万能温柔话术。达到运行层重试预算后保留错误，不放行未经检查的文本，也不伪装成她故意沉默。

语言是否自然、是否太文艺、是否持续管人，主要用离线回归和人工阅读评价；首版不让一个“像不像真人”的在线评分器拥有任意改写权。这样保留人物的个性，也避免审查将所有回应磨成同一种标准答案。

## 9. 验证与退出条件

本轮选择了结构与复用边界，未宣称效果已经成立。后续最少检查：

| 场景 | 通过条件 | 不能接受的反例 |
| --- | --- | --- |
| 甲冲突后与乙聊天 | 可保留有限整体余效，乙的关系不被扣分，甲的身份和原话不进入乙上下文 | 为解释烦躁，把甲整段私聊交给乙的模型请求 |
| 相同事件重试、相同时间反复读取 | 状态和信任只变一次；读频率不影响恢复速度 | 刷新页面或多调用工具，心情恢复得更快 |
| 道歉、后续尊重、长期未联系 | 感受缓和与证据结算可不同步；缺席不直接扣信任 | 每句道歉自动加分、连续发“喜欢你”快速升级关系 |
| 事实纠正 | 原事件保留，信任按有效证据修复；当前PAD/pulse经新的纠正评价继续变化，不追溯抹除感受 | 错误记忆被删得无从追溯，或纠正又触发一次同样负面冲击 |
| 图片求助与反复测试 | 能在具体语境下区分，允许不确定和澄清 | 逢图片就拒绝，或任何指令都切换成客服式长报告 |
| 正常结束、求安慰和求建议 | 可结束，也能在明确需要时认真回应 | 为避免过度关心，把所有安慰都压成冷淡一句话 |
| 用户影响公开作品 | 有真实采用与执行记录，公开范围正确，不暗示虚假排他关系 | 每个礼物都触发发帖、亲密加分或制造嫉妒 |

先做固定时钟、作用域、回放、结算和原文 hash 的确定性验证，再做获准的模型对照。比较组保持人物、事件与可见历史一致，分别测纯文字状态、EE 适配、表达资料增量；不能让状态组独占额外事实后宣称数值引擎有效。

双人物对话可用于发现重复接话、错误加分和循环劝慰，但双方同为模型可能一起认可错误经历；必须另有脚本事实、人工阅读和未参与提示词编写的新场景。关系数值漂亮、连续聊得久或自动评分高，都不能代替目标用户对具体聊天的判断。

若数值状态导致表达更僵硬，优先追查语境评价、实际注入材料和时钟，不能直接增加情绪维度。若受控对照仍无收益，保留事件、来源、关系证据和时间能力，停用相应数值消费者；该退出条件避免把一个库变成不可推翻的前提。
