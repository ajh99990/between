# 事实、时间与数据约定

状态：2026-10-26 方案决定，尚未实现。本文是各专题共同的数据语义；具体数据库迁移以后依据它编写。这里的英文名是我方拟议契约，不冒称上游字段。返回[总索引](README.md)。

## 先用一次聊天说明区别

14:10，甲说“你昨天答应做我女朋友了”。系统可以确定的是**甲在此刻说过这句话**。检索没有找到那次承诺时，人物可以存疑、询问或表达自己的判断；不能把这句话直接写成“双方昨天确定了关系”。若她回答“我不记得答应过”，也不能把这句回复当成过去绝无此事的证明。

同样，“下午发小红书”是计划；“已请求发布”是一次尝试；平台返回受理只是提交结果；能读回对应帖子才支持相应发布状态。虚构人物设定中的“上午参加拍摄”可以属于模拟生活，但不能证明现实摄影师、订单或平台动作存在。

选择把这些材料分开，是对 Yuralume 回合后提取、Eros 分层画像和 BST 状态账本的适配；它们各有可借机制，却没有直接提供我们需要的多人公共人物事实体系。[^y-post][^e-profile][^bst]

## 统一称谓

| 名称 | 含义及写入者 | 谁随后读取 |
| --- | --- | --- |
| `PersonProfile` / `ProfileChange` | 初始虚构底稿单独保留；后续变化保存旧值、新值、生效时间、依据事件、来源及版本。生活服务可提交前向变化，无重大事件审批；管理端录错更正另留原因 | 生活、私聊、公开创作的上下文构造器 |
| `CurrentSituation` | 此刻活动/意图、地点或环境的已知范围、最近确认时间、复核时间；生活领域服务提交 | 所有涉及此人物当前生活的决策 |
| `ActivityPlan` | 打算何时做什么；日程服务提交和修订 | 生活推进、约定冲突检查、上下文 |
| `Event` | 某时收到、观察、尝试、决定或模拟发生了一件事；各领域服务追加 | 回顾、状态更新、可选记忆提取、排障 |
| `Claim` | 某人或模型关于某件事的说法，保留说话者、来源与适用时间 | 事实查询、人物理解、矛盾复核 |
| `Memory` | 为以后取用而选择或整理的材料，必须指向来源 | 范围内的历史检索与上下文 |
| `InboxItem` / `Exposure` | 来信及一次实际提供给人物模型的记录 | 注意管理、同对象历史与后处理 |
| `AttentionPlan` | 此刻愿意查看哪些渠道/对象，何时复查 | 入站调度与上下文构造器 |
| `Commitment` | 待处理事项的统一查询对象；`kind=private_intent / known_pending / expressed_promise` 分别表示未表达意图、已看待办、已对外承诺 | 到期提醒、下一次人物决策；只有第三种有实际发送原话与对外责任 |
| `PublicationIntent` | 稳定作品、账号、目标、动作类型及显式重发代次；由发布服务预留，载荷版本另存 | 08的跨run发布去重与结果核查；草稿修订不生成新发布意图 |
| `ActionIntent` / `ActionResult` | 已提交的动作请求与工具实际结果 | 工具执行、后续决策、完成声明检查 |
| `WakeJob` / `DecisionRun` | 未来处理机会及一次可暂停、恢复的运行 | 运行协调器 |
| `PublicArtifact` / `Contribution` | 公开作品及资源贡献关系；发布/资源服务维护 | 创作、发布、关系回顾；不同范围读取不同视图 |
| `RomanceAssessment` / `RomanceCommitment` | 前者保存人物当前意愿、相处依据和未解疑虑；后者保存提议版本、双方原话、当前承诺/发送状态。关系服务提交，具体流程见06 | 当前对象的关系上下文、关系动作校验及恢复 |
| `RelationshipAvailability` | 人物级、去身份的承诺可用状态及版本（available / reserved / committed / reconciliation_required）；从各阶段提议、有效承诺和未结案对外消息推导 | 所有涉及恋爱承诺的决策与发送前检查；不暴露伴侣身份或私聊 |
| `TrustCheckpoint` / 结算记录 | 关系作用域、算法版本、状态版本、截止证据序号、基线值；每次结算保存输入证据和结果，修复时旧结算标记被替代 | 06的信任纠错；只重建内部状态，不重放历史外部动作 |

这些是业务对象，不要求一对象一个服务或一张表。首版同一数据库可使用关系字段和 JSON 正文；禁止一个可任意覆盖的“大人物 JSON”绕开各领域的权限与时间规则。

### 关系记录的最小契约

`RomanceAssessment` 保存 `person_id / counterpart_id / assessed_at / willing / reasons / evidence_ids / unresolved_concerns / read_set / policy_version`。两次评价必须有独立实际时间和情境引用；不能复制同一轮输出当作两次。

`RomanceCommitment` 保存稳定ID、人物与私有对象ID、`counterpart_kind=contact / fictional_person`、`proposal_version`、提议方向、`proposed_terms`、当前状态、双方同意/撤回的原话ID、成年依据引用及复核状态、虚拟身份披露与知情回执引用、评估引用、出站动作ID、`effective_at / ended_at`、乐观锁版本及撤销原因。成立、送达、已读、撤回与通知责任分列，不能用一个布尔值互相代替。真人联系人使用上述双方消息和真实回执。虚构对象另记录其参与方式：尚未独立运行的背景人物可用`simulation_event_ids`、虚构底稿版本与时间记录模拟关系，未发生的消息/发送字段为空；已独立运行的虚构人物必须引用各自实际决定和交流记录，通过真实微信交流时保留真实消息/发送字段，不能用一方模拟代替另一方同意。`counterpart_kind`区分人物身份，不决定是否有真实渠道结果。42天/7天仅适用于真人联系人，不因虚构人物使用真实微信自动扩大；两类虚构关系均遵守唯一承诺与前向历史规则，独立人物还须分别检查双方的承诺约束。未送达的真人提议只代表意图，不是恋爱事实。`RelationshipAvailability` 的共享投影不含对象ID、昵称、消息或理由详情。

真人的“相识起点”单独保存 `acquaintance_started_at` 和双方交流依据：取首次来信实际提供时间与首次人物回复**可确认已送达时间**的较晚者。送达可由平台回执/已读或对方针对该回复的实际回应确认；无精确送达时刻时，保守取后续确认的接收时间，不编造更早时间。引用`KnowledgeReceipt`并保留更正版本。账号创建时间、用户自称旧交情都不能回填起点。

用户最先提出的恋爱意向先存为带版本和原消息ID的`Claim`（关系提议），不占人物承诺位置；不能靠抢先一句话冻结她与所有人的关系。人物愿意进入确认时，另创建对应`RomanceCommitment`并引用这条提议；正式条款由当前版本保存，不把几周前的泛泛表白当作当前确认。

`RelationshipAvailability`按下表推导，所有写入更新版本。它是资格/边界视图，不能被直接显示为“恋爱状态”：

| 当前记录 | 共享投影 | 能说明什么 |
| --- | --- | --- |
| 仅有私人意向/用户单方提议，且无其他占用 | `available` | 无排他承诺占用；不意味着愿意恋爱 |
| `reserved`、`offered`，含提议/接受发送未知 | `reserved` | 当前不能向别人承诺；尚未确立恋爱 |
| `active`，真实联系人或虚构伴侣 | `committed` | 已有排他承诺；不含对象身份 |
| `withdrawn/ended`，但旧承诺消息或必要解除通知未核清 | `reconciliation_required` | 关系已撤回/结束，旧消息仍待核查；不能解释为仍恋爱 |
| 已拒绝/撤回/结束，发送链路结案且无其他占用 | `available` | 没有当前占用；历史仍保留 |

同一人物在任一时刻只能有一份尚占用承诺资格的记录；`reserved / offered / active` 和未结清的旧承诺消息均占用。已结束关系的历史保留，未决发送另阻止新的排他承诺，不把结束改回“仍恋爱”。唯一约束作用于人物而非聊天；原子更新承诺、可用状态、事件和需要发送的outbox。具体状态含义和双向成立路径只见[06 §6](06-情绪关系与表达.md)。

## 来源和含义分别保存

`source_kind` 记录材料从哪来；`statement_kind` 记录它能说明什么。不使用一个“可信度分数”替代这两个问题。

| 来源 | 允许表达的含义 | 不得自动升级为 |
| --- | --- | --- |
| `channel_message` | 某联系人在某时作出的陈述 | 人物已发生的共同经历、已接受的约定 |
| `tool_receipt` | 指定工具在指定账号/目标上返回的实际结果 | 工具未读取的内容、整个现实世界的真相 |
| `character_decision` | 人物选择、意图、接受/拒绝及主观感受 | 动作已经完成 |
| `simulation` | 经生活服务提交的虚构人物生活进展 | 真实用户参与、真实消费/发布、现实第三人的行为 |
| `profile_revision` | 初始虚构底稿、明确作者补充或带生效时间的前向设定变化；三者分型并保存依据 | 过去任意时刻都已知道这一新设定 |
| `model_inference` | 基于所列材料的推测 | 已核实事实 |

对应的 `statement_kind` 为 `reported / observed / planned / decided / simulated / inferred`。事件发生本身与事件正文的真假要分开：收到一句谎话是实际发生的收信事件，谎话内容仍是 `reported`。主张正文另保留 `asserted_by`、稳定 `subject/predicate` 与原话；转述另指向被转述来源。承诺作为言语行为有独立 `Commitment.kind`，不靠 planned 标签判断已经对外答应。

不存在统一的“工具总比人可靠”。“我最近很累”是对方的自述，通常可以据此体贴回应；无需联网证明。帖子是否公开、人物是否发送过某句话，则分别查对应平台结果和出站记录。事实查询工具返回原文、来源、适用时间及冲突，不返回一个包办所有判断的真伪标签。

## 所有专题沿用的记录外壳

下例是**我方示例，不是实测**。真实 ID 使用无身份含义的随机标识。

```json
{
  "event_id": "ev-example-1",
  "person_id": "person-example",
  "scope": "contact",
  "counterpart_id": "contact-a",
  "group_id": null,
  "occurred_at": "2026-10-24T14:10:00+08:00",
  "recorded_at": "2026-10-24T14:10:01+08:00",
  "valid_from": "2026-10-24T14:10:00+08:00",
  "valid_until": null,
  "exposed_at": null,
  "source_kind": "channel_message",
  "statement_kind": "reported",
  "source_ids": ["message-example-1"],
  "activity_id": null,
  "revision": 1,
  "payload": {"claim": "我正在开周会"}
}
```

- `occurred_at` 是所知的发生时间；不知精确时刻时保存区间和精度，不能补造秒数。`recorded_at` 是系统实际写入时间。
- `valid_from/valid_until` 表示说法或状态的适用范围。未知结束时间不等于永远有效；当前状态另有 `recheck_at`，过时后按最后已知呈现。
- `exposed_at` 表示内容已在某次模型调用中提供，不等于模型理解正确；详细投喂记录归 `Exposure(run_id, item_id, exposed_at)`，外壳字段只是查询摘要。
- 日程另存 `planned_start/planned_end` 和生命周期 `planned/in_progress/closed/canceled`；安排关闭不证明工作完成，需另查实际结果。安排时间、实际发生时间、获知时间不可复用一列。
- `source_ids` 连接可核对材料；读取引用仍检查人物身份、实际所知、当前查询范围与材料权限。D21允许同一人物明确查询自己与其他联系人的已知记忆；引用本身不能绕过未读、跨人物或被撤销的访问限制。
- `activity_id` 可选。事件不依赖日程存在；时间接近也不能自动推断某用户参加了某活动。

存储统一 UTC，显示与日程解释使用人物时区，首版 `Asia/Shanghai`。截止点采用半开区间 `[start,end)`；“今天/昨天”在输入进入系统时绑定日期，不随后续摘要重新解释。

## 作用域、公开权限、对方知情是三个问题

Yuralume 区分 `audience` 与 `player_knowledge`，值得采用这个区别；其 owner 模型及未分类默认值不能直接移植到多人场景。我们选择缺少公开许可时保留私有，不沿用旧资料未分类时可能进入公开候选的兼容行为。[^y-memory]

| 维度 | 我方约定 |
| --- | --- |
| 保存归属与读取 | `character` 保存人物自身材料；`contact` 按联系人分别保存，默认取当前对象，明确跨联系人或主题查询按05读取同一人物已知材料；`group` 保留群归属和可见限制；`system` 仅运行/管理。存储归属不等于对外分享许可 |
| 公开使用 | 通过 `PublicationGrant` 或已确认自有材料规则允许特定作品、用途和范围；重要度不能代替许可 |
| 对方接触过什么 | `KnowledgeReceipt(person_id, counterpart_id, artifact_or_fact_id, basis)`；basis明确区分送达、平台已读、对方确认。送达不证明已读或理解，公开可访问不等于所有人看过 |

`character` 也不等于自动可公开，例如人物自己的未发布草稿。乙能够访问公共作品，不因此有权访问甲的私聊。许宁在与乙交流时可按05主动回想自己的相关记忆；检索到不代表可以转述，来源用户不得对外点名，保密内容及可识别隐私也不能因代称而放行。共享心境只默认提供去身份的影响，不自动附上甲的私聊全文。

首版群聊记录用群作用域，不把甲在群中的一句话抄入所有人的私聊记忆；未来将其中信息用于私聊时，只提供该接收人确实可见的群事实或另获许可的内容。删成员、撤销授权后重新计算可读范围。

## 纠错与历史保护

过去日程不可改是用户硬要求。所有入口在**提交时**检查权威时钟：已过去部分不可重写，进行中活动只能从提交时刻创建未来修订；整日重生成、管理员、批量导入、MCP 走相同服务。保存旧版本与修改原因。技术录错可以追加纠正说明，不伪装成历史当时就不同。

事件、主张和修正保留来源关系：新认识 `supersedes_id` 指向旧说法，原记录仍可查。撤回错误自述时，派生记忆标记待重算，不继续当成独立证据；已据此结算的关系证据和外溢同步失效/重建，具体规则见 [06](06-情绪关系与表达.md)。已经公开的帖子只能通过实际更正/删除动作处理，不能删除数据库行就声称外界没看过。借鉴 BST 的显式清除标志避免旧值复活，但不复用“编辑旧聊天就改写人生”的权威模型。[^bst]

相互矛盾的说法只在同一主体、同一事项和重叠适用时间内比较；“上午在家”和“下午外出”不冲突。遇到缺证，返回“未知/两种说法”及出处，由人物依据语境决定是否询问。来源校验失败的记忆候选隔离，不凭语言相似度吞掉冲突。

## 初始资料缺口与人物所知

作者尚未定义、人物不知道、人物不愿说，是三种不同情况；不能把它们合成一个“未知”。

| 情况 | 含义 | 如何进入当前交流 |
| --- | --- | --- |
| 作者未设定 | 底稿没有这个事实，例如父母具体生日、许宁前恋情 | 标明资料缺口及现有精度，不推导“从未恋爱”“忘了生日”或“这是隐私不想说” |
| 人物不知道或不确定 | 有依据说明她没获知，或只听过一种说法 | 提供她实际知道的来源及不确定处；检索失败不能伪装成她失忆 |
| 人物知道但选择不说 | 事实可查且她有相应认识，当前选择不透露 | 依据关系、话题和边界作选择；不以隐私措辞长期掩盖作者缺口 |

实例启用前，作者可以明确补充初始虚构经历，保存版本和参照日；这正是11及亲友资料当前所做的事，不是向已经运行的历史补事件。启用后若确需补足尚未定义的初始背景，只能走**显式作者修订**，记录实际写入时间、理由、适用精度和新增事实；核对既有底稿、对外陈述及生活记录，保留旧版。发现矛盾时先保留冲突提案，不默认新稿比旧事实正确。只有具有明确错误依据时，才按上节规则追加更正；否则不把冲突提案作为初始缺项补入。例如原来已确定是独生女，后来新增弟弟就不是普通填缺，不能借作者修订改变已经成立的运行历史。

该作者修订不是聊天工具，也不是让回复模型先编、管理端随后为它背书。不得倒造过去的日程、Event、Exposure、私聊、平台回执或“某用户早已知道”的证据。新事实由哪一版资料开始提供应可回查；事件发生时间、作者写入时间和运行中提供时间仍分别保存。`profile_revision`在这种情形明确标为作者补充初始背景，不与生活前向变化混记。

组装上下文时先提供已知部分与精度；缺了精确生日仍可说已设定的出生年，不能每次机械拒答。确实无法回答的具体过去保持缺口，交资料维护处理。不能同时承诺“回答任何自传问题都完整”与“永不补造过去”；本方案优先保持一致的已有依据。未来生活照04向前发展，不需要因为底稿有缺项就暂停。

亲友资料同样遵守此规则；作者定义的全部资料、某人物初始知道的条目、后来获知的新消息分别处理，具体组织见[12](12-亲友资料与真实联系.md)。

## 共同事实如何从私聊影响中形成

以甲提供图片风格资源为例：私聊事件与贡献来源留在 `contact:甲`；先检查资源用途许可和执行安全。她决定试用后，生成一份实际作品。经过针对这份作品的可公开检查，创建新的 `character` 范围作品记录，只带允许共享的内容和实际生成结果。公开上下文不读取甲的私聊。

贡献归属由 `Contribution` 保存，人物可按05回想自己的相关来由，有权限的管理流程可回查；乙本人不能读取甲的私人来源。涉及由其他用户记忆取得的来源身份时，D21的对外不点名限制优先，不能用署名许可绕过；独立取得的作品作者信息仍按素材许可署名；仅在具体公开载荷无法同时满足来源用户禁名与必需署名时换用其他材料，不省略必需归因。`PublicationGrant` 至少记录授权人、材料、用途、公开范围、署名约定、期限和撤销状态；人物的公开选择另存，获得许可不等于必须发布。去掉姓名不自动等于匿名，私密截图、独特措辞、定位、EXIF 及细节组合仍需要检查。公开作品描述应脱离私聊仍可独立成立，私人来由不被顺手复制。乙可以看到作品，不因此知道甲参与过。这个“分别保存、明确投放”的组合是我方适配，不能冒称 Yuralume 已解决公共人物的全部隐私。[^y-disclosure]

## 完成状态与事件记录的粒度

人物能理解的每次外部动作记录一条稳定事件：搜索关键词与时间、读取哪个对象及覆盖范围、生成了哪份作品、请求发布及结果。内部 HTTP 重试、向量批次和每个 token 属于有期限的执行记录，不逐条进入人物事件或长期记忆。

原始消息、事件与材料先可靠保存，向量索引异步建立；索引失败不丢原文，标为待重试，仍可按对象/时间/关键词检索。与 Yuralume 新记忆依赖向量成功才写入的路径不同，这是为可追查性作的适配。[^y-post]

真实平台结果分开表示 `submitted / published / failed / unknown`；其中 `published` 必须带平台对象标识、读取方式及可见范围。工具回执确认成功并不自动完成对人的承诺：例如帖子确已发布，但尚未按约告诉甲，告知责任仍存在。执行状态机详见[运行契约](08-运行架构与工具契约.md)。
