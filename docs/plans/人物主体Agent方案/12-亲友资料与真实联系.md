# 亲友资料与真实联系

更新：2026-10-26。状态：**知识库组织方式已写入方案；资料仍为原创候选，查询服务、亲友运行和真实微信均未实现**。用户明确要求先集中亲友资料，并希望将来亲友也活过来、通过真实微信联系。原话见[新增愿望](用户愿望原文.md#后续新增愿望)，采用状态见[02](02-决策依据与取舍.md)。[总索引](README.md) · [首批亲友资料](人物资料/许宁亲友知识库/README.md)。

## 1. 从资料卡开始，保留成为独立人物的可能

当前先解决许宁“查这个人是谁、和我有什么共同过去、我知道哪些事”的问题。资料按人集中，共同家庭背景单独维护；许宁底稿引用它们。将来亲友独立运行时沿用同一个人物身份和既有事实，不再另外创造一位名字相同但经历不同的母亲或室友。

需要分开六种关系；下列是我方设计概念，不强制各建一张表：

| 内容 | 记录什么 | 不自动说明什么 |
| --- | --- | --- |
| 人物资料 | 稳定 `person_id`、初始底稿版本、背景事实及有效时间 | 已经有 Agent 运行或现实账号 |
| 人物间关系 | 两个主体之间的关系、共同过去、来源和时间；一方看法另列 | 双方感受相同、对方已答应新邀请 |
| 某人知道的资料 | 观察者、所知人物/事实引用、获知依据与时间或初始版本 | 能读对方全部底稿、私聊与当前想法 |
| 运行实例 | 是否启用该人物自己的生活推进、收件箱、注意安排及决策 | 自动有微信账号或朋友权限 |
| 平台绑定 | 人物使用的实际账号、允许动作、核验状态及凭据引用 | 模型可自行认领现实中的同名账号 |
| 联系目标 | 该发送账号下已核验的接收对象标识及其人物关联 | 姓名相同就能当作同一个接收人 |

首批卡片只完成设计层的人物资料和初始关系，并明确许宁初始知道的范围。运行标识、账号与联系人在实际初始化/接入时建立。部署者确认自己有权使用账号及其联系人绑定；模型不能修改绑定，不按姓名搜索现实人士并把对方当作虚构家人。

## 2. 集中资料，但不让人物全知

作者底稿与人物所知不能混成一个查询结果。资料卡可完整保存作者设定；许宁查询时，只返回初始明确已知的条目，以及后来通过实际交流、可见行动或有效模拟生活获知的材料。启用后的亲友当前状态由其自身生活进程维护，不能因“在同一个知识库”直接提供给许宁。

例如，初始卡已明确许宁知道母亲的工作；后来母亲正在为一件事烦恼，但尚未告诉她。母亲自己的上下文可包含这件事，许宁的查询不能得到这段内心状态。如果母亲实际发来“今天有点烦”，先是收件，只有许宁查看后才进入她的认识；她可以产生理解，却不能因此知道母亲没说出的全部原因。

沿用[03](03-事实时间与数据约定.md)的来源和时间语义：初始认识引用 `profile_revision`；实际告知引用消息与 `Exposure`；她对他人的推测保存为有来源的 `Claim`；分享权限与对方知情仍分别记录。初始知道可直接指向卡片条目，例如陈佳F01，不复制一段单独可修改的身份正文。引用固定版本，后续更新不能静默让她知道新事实。

拟议的 `people.lookup` 查询只需接受对象线索和问题，例如“我的室友是谁”“陈佳为什么还没确定练车时间”；查询者由当前run确定，不能由模型任意填别人的身份。返回稳定对象引用、可见事实正文，另列来源、适用时间、获知范围和缺口；作者维护注释不作为人物记忆返回。称呼有歧义时返回候选或要求定位，不猜。先过滤再检索，不能全文召回后只靠提示词要求保密。与当前聊天对象无关的私人材料仍按05隔离，不因查询的是亲友就解锁跨联系人读取。

这种集中主要减少重复事实，**不是把所有人与她的私聊汇成总记忆**。过去共同经历、自己对朋友的认识、朋友未告知的秘密以及不同用户的聊天继续分开。

## 3. 亲友真正活起来以后，微信怎样发生

未来目标是让亲友各有自己的生活、注意范围和选择。许宁可以主动联系他们，亲友也可以主动联系她；不是每轮由许宁的模型兼演母亲，并编出一来一回。各自复用04—08的生活、记忆、关系和执行机制；共享服务可以复用，私有状态不能混在一份模型上下文里。

一次真实联系应走完：

```text
许宁决定联系母亲
→ 核对许宁的实际微信绑定和母亲的联系人标识
→ 保存出站 ActionIntent 与 outbox
→ 微信适配器实际发送，保存平台返回
→ 消息经母亲账号的实际入站链路到达
→ 母亲的 InboxItem，按她自己的注意安排提供给模型
→ 母亲结合自己的生活与关系，决定回应、延后或不回应
→ 若回复，再走母亲账号的真实出站与许宁账号的入站链路
```

即使两个 Agent 部署在同一后端，也不能直接调用母亲模型、把回复塞入许宁收件箱，并声称已在微信交流。内部通道可以做明确标注的测试，但不能作为这项愿望完成的依据。母亲回复的内容也不由许宁的发送任务预定；邀请室友拍摄时，室友可以拒绝或另约，不能先替她写“答应了”。

发起、受理、确认送达、实际提供给收件人模型、发送者知道对方看过、对方答应请求，是不同状态。适配器只能报告平台实际支持的范围；微信链路没有已读回执时就保持未知，不能将收件人内部 `Exposure` 自动泄露给发送者。出站去重、unknown核查、取消与迟到结果统一按[08](08-运行架构与工具契约.md)执行，不在这里重写一套状态机。

## 4. 先有虚构背景，再有真实联系，怎样衔接

家庭群、旧同学关系、毕业照片册可以作为明确的初始虚构背景存在。它们不要求补造启用前的真实微信消息，也不证明现在账号已经可用。

运行时须按人物及动作区分写入权限：

- 亲友还只有资料卡时，可按04维护明确的虚构背景与向前生活；未定义为真实渠道的虚构往来标为 simulation，不能装成微信收发。
- 亲友启用自身运行后，其决定、安排和感受由自己的运行维护。许宁可提出邀请和理解，但不能替另一位运行人物同意、改日程或产生情绪。共同事件引用双方实际记录，不分别编两套过去。
- 一项联系被定义为真实微信动作时，无论亲友是否启用，都必须有真实结果。未绑定、离线、失败或结果未知就保存未完成状态，不能由生活生成补一句“刚和妈妈聊过”结束任务。
- 从资料卡转为独立运行时，明确启用时间、采用的底稿版本、已成立共同背景和双方初始所知。之后停止旧生活生成器替该人物写决定；旧虚构经历不重标为真实平台事件。

这是人物写入职责与实际动作来源的区别，不是重新增加重大生活事件审批，也不限制她们以后改变人生。新人物是否启用和账号接入属于部署工作；启用后通常如何生活、联系谁、怎样回应，仍由各自模型结合状态选择。

先做资料组织和可知范围，日后再接可用的微信项目和授权账号；不擅自缩成永久只在系统内部模拟，也不把未来愿望加入本轮已完成项。暂不承诺开源适配一定支持好友、群聊、回执等所有功能，待实际项目交付后核查。

验收场景集中在[09](09-验证与实施路线.md)的亲友补充用例；资料、查询、独立运行、真实发送、实际收件与自然相处须分别验收。
