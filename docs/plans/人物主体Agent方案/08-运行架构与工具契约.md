# 运行架构与工具契约

状态：2026-10-26 设计选定，待实现；没有创建新运行服务。[返回索引](README.md)。数据含义以 [03](03-事实时间与数据约定.md) 为准，人物怎样选择生活见 [04](04-生活推进与注意管理.md)，平台差异见 [07](07-社交平台与内容生活.md)。本篇解释让这些选择真正生效的程序。

## 1. 先确定什么是整个 Agent

LLM 负责理解和选择；整个 Agent 还包括按任务组织的提示词、可调用工具、持久记录、时间触发和执行恢复。Skill 是可按需读取的工作方法，不是让生活持续的时钟；MCP 是工具接入协议，不替代权限、日程保护或数据库事务。

| 部分 | 首版选择与理由 |
| --- | --- |
| 人物决策 | 一套可暂停的工具循环；生活、私聊、公开创作采用不同的上下文范围和任务材料，不做六个互相争夺人格的 Agent |
| 核心后端 | Python 模块化单体；同一代码库运行 API 与后台 worker。Yuralume 的工具循环、记忆/日程职责及 EE 核心可直接以 Python 为适配基础，不必为调用它们先引入跨语言服务[^y-loop] |
| 持久层 | PostgreSQL 保存业务记录、任务与 outbox；关系键/时间/版本用列，结构化内容用 JSON。首版不引入 Kafka、分布式事件溯源或独立状态微服务 |
| API/数据访问 | 选 FastAPI + SQLAlchemy/Alembic，明确鉴权、事务和迁移。属于本项目工程选型，不是已验证的自然对话优势；不受旧 Node 服务限制 |
| 记忆索引 | 原文/事件先保存，全文及条件检索可独立使用；按需要增加 pgvector，不能让向量服务失败导致事实不可查 |
| 资产 | 通过存储接口保存文件及 hash；单机开发用私有目录，部署可换对象存储，公开文件只由授权作品流程生成 |
| 外部工具 | 平台适配器与不可信资源处理在受限进程运行；凭据不进入人物提示词。内部领域服务直接调用，确有复用需要再暴露 MCP |

选择单体是为了先保证同一人物的读写可解释。API 和 worker 可以分别重启；这不意味着所有组件必须长在一个进程。后续扩容由任务延迟、工具并发和数据库压力驱动，不先按抽象名词拆服务。

模型通过统一接口支持结构化工具调用、超时/取消和实际用量记录。首版采用一个可配置的主模型承担人物决策；提取与窄审查可使用同一提供方的独立调用。这里不编造某型号已通过中文自然度验收，具体部署型号须经过 [09 的同条件比较](09-验证与实施路线.md)，成本与能力由真实记录决定。

## 2. 一次 run 与一次模型请求不同

`DecisionRun` 保存目的、范围、已暴露输入、已执行步骤、尚待结果与终止原因。一次 run 可以经历多次“模型 → 工具 → 模型”，也可以等待工具后恢复。Yuralume 的 composer tool loop 实际是**两遍生成、中间最多一次工具调用**，并非现成的任意多步探索器。采用它“先拿真实结果再组织回复”、注册白名单与执行器分离的实现；扩成有预算的多步循环和可恢复步骤账本是本项目新增适配。其单 owner 上下文也不能直接变成我们的多人共享状态。[^y-loop]

```text
领取可运行任务
  → 按范围读取当前处境、相关关系、已暴露消息及任务材料
  → LLM 选择：读取 / 更新领域记录 / 外部行动 / 回复 / 等待 / 结束
  → 服务检查权限、来源、时间、版本，返回成功或具体失败
  → 有新信息则继续同一 run
  → 等待外部工具时保存步骤并让出人物决策机会
  → 结果到达后重建当前上下文，再决定下一步
```

不要求模型每轮都调用情绪、记忆、日程、发布四个工具。没有相应变化时不写；没有新活动或公开内容也能正常结束。硬预算用来限制成本，不伪装人物的心理意愿。浏览试验初值统一见 [07](07-社交平台与内容生活.md)，这里不维护第二份数字。

## 3. 共享人物如何同时聊天和做事

**一人一个有序提交入口，多个 run 可以存活；慢工具不占着人物。** 不把所有聊天锁在一个跑完整小时的浏览 run 后面，也不让每个联系人各自保存一份全局生活。

首版限制同一人物同时进行一个短决策步骤；数据库事务只覆盖领取/提交，不跨模型请求持锁。模型请求有截止时间，过期租约的旧结果不得提交。等待上传、抓取或导出时 run 变为 `waiting_tool`，人物可以处理另一项触发。工具返回后原 run 排队恢复。Eros 的领取、超时恢复与存活检查提供参考，但它的队列按会话归属；人物级提交次序和不同范围续跑是本项目的补充。[^e-queue]

每步保存 `read_set`：所有实际注入或工具读取材料的 `(kind, id, revision)`，覆盖当前处境、关系/感受、安排、责任、主张/记忆、作品/发布记录及已暴露消息；同时记录有效时间/复核点、注意安排到期点、用途许可版本和检索水位。检索水位只帮助识别新增，不代替旧材料被更正、撤回或完成的版本检查。只检查用过的材料；不因无关联系人的新消息让所有模型输出作废。另存递增的 `commit_seq` 标识接受顺序，不引入向量时钟。

版本未变也可能已经过期。提交时、对外动作实际派发前，按权威时钟和当前许可重新检查依赖：例如14:29:59读入14:30到期的处境，模型14:30:20才返回，不能仍以“没人改版本”放行旧近况。先复核相关处境，再重决受影响的未执行输出；已有工具事实仍保存。被撤销的用途许可阻止尚未执行的发布，不等待模型自觉发现。

例如，她在读甲发来的视频时启动下载；乙消息随后被允许查看。乙的交流让她改变了下午安排。视频结果回来后，甲的原 run 读取最新处境，不能继续使用旧提示词说“我接下来一小时都空着”。它仍可使用已取得的视频内容，但须重新决定尚未执行的动作。

```text
执行一个决策步骤(run):
  取得人物步骤租约与 fence_token
  snapshot = 按当前处理对象重建默认材料及 read_set
             # 保留经05允许的显式记忆查询结果及来源，恢复时复核权限/版本
  proposal = LLM(snapshot)                 # 不持数据库事务
  在短事务内：
    检查租约、输入范围、实际依赖版本与时间有效性
    冲突 → 保存原因，重新排队；不提交旧决定
    合法 → 提交领域变更、步骤账本、必要 outbox/WakeJob
  释放步骤租约
  派发已保存的外部动作；等待时 run 可暂停
```

已经发生的外部动作不能因为后续版本变了就“重新来一次”。步骤账本使用稳定 `operation_id`；恢复时复用成功结果、核对未知结果，只重决尚未执行部分。保存上下文范围和来源，不把一份冻结的完整 prompt 当作恢复后的世界。

技术容量导致的排队与人物选择暂不交流分别记录；不靠伪造烦躁解释服务拥堵。大量通知可以按来源合并计数，已读责任仍逐项保留。调度器不得因跨对象合并自动拼接多个私聊正文；模型明确查询自己与其他联系人的已知记忆按05处理，不改变当前发送目标。

## 4. 给模型的工具围绕人物能做的事组织

下列是拟议接口，不是声称上游已经提供同名工具。schema 由服务生成并按 run 授权裁剪；模型不能提交任意 SQL、冒用另一人物身份读取其上下文，或修改账号绑定。同一人物的可选记忆查询目标不等于切换人物或发送对象。

| 工具组 | 输入和返回重点 | 服务端必须执行 |
| --- | --- | --- |
| `life.current / life.advance` | 读取共享处境；提出虚构生活进展、设定变化、来源和下次复核 | 检查来源、时间与版本，事件/生效修订/处境/唤醒协同保存；不设重大变化审批 |
| `schedule.read / propose_change / commit_change` | 指定日期；返回占用与影响；提交批准的未来修订 | 所有入口保护过去，不默默取消他人约定 |
| `inbox.list / inbox.read` | 概况不含正文；读取本次允许对象的指定消息 | 保存实际 `Exposure`，未读不进入任何人物侧提取/评价 |
| `attention.set / commitment.record / resolve` | 注意范围、复看时刻；事项种类、原话、履行条件 | 自己打算、已看未办、已发承诺分别保存，完成需依据 |
| `facts.query` | 对象、时间或问题；返回相关材料和来源 | 校验该材料读取权限；不是自动认证事实的裁判，不因记忆工具变更而开放任意数据 |
| `memory.search` | 联系人可省略，默认当前run联系人；可明确ID/名字，或按主题查询自身全部已知记忆；返回来源/时间/保密约定 | 先检查人物所知及权限，再按目标检索；名字消歧，无默认对象不静默全库查；原文回查同样校验，表达和写回遵守05 |
| `people.lookup` | 亲友对象线索和问题；返回当前人物有权知道的条目、版本、来源与缺口 | 查询者由run确定；不读亲友未告知的当前状态，不用姓名替代真实联系目标；具体含义见12 |
| `affect.appraise / relation.record_evidence` | 已看到的事件、主观理解、预期版本 | 适配 EE；去重、时钟、证据结算；不开放管理重置接口 |
| `romance.assess / propose / respond / inspect / withdraw` | 当前对象的意愿、证据、提议版本和发送状态；共享部分只返回承诺可用状态 | 06的时间与证据校验、人物级唯一预留、版本/撤回复核、发送unknown核查；不能以得分直接建立 |
| `relationship.end` | 当前提议或关系版本、明确撤回/终止及依据；支持人物决定或经过鉴权的用户直接撤回 | 保存结束、取消尚未发出旧承诺、保留通知责任；未读消息不经过偷偷读取来触发 |
| `platform.* / asset.create` | 具体账号、动作、对象、资源引用；实际返回及覆盖范围 | 受限执行、凭据隔离、外部结果校验；不伪造看完或发布 |
| `publication.prepare / submit / inspect` | 已许可素材、公开载荷、平台对象与状态 | 私密来源不进公开任务；unknown 先核查，不盲重发 |

`facts.query` 是事实材料查询，不是“大模型说谁对谁就对”的裁判。`life.advance` 可保存虚构人物向前发展的进展，却不能宣称已调用真实平台。有关区别只维护在 [03](03-事实时间与数据约定.md)。

恋爱消息先创建领域提议及预留，再进入同一outbox；通用发送工具不得绕过`RomanceCommitment`直接作排他承诺。发前检查提议版本、当前意愿、关系可用状态、终止/撤回及时间条件；普通亲近不因包含昵称就被机械当作承诺。难以自动识别的漏检须纳入T18/T19，不能只因专用接口正确就宣称所有输出已受约束。取得终止请求后先取消未派发旧消息；执行中或结果未知的消息继续核查并补更正，晚回执不能复活关系。具体成立含义由[06 §6](06-情绪关系与表达.md)统一定义。

## 5. 对外动作怎样从一句打算变成结果

动作先持久化，再交给 worker。数据库 outbox 解决“存了意图但进程退出没派发”；它不能让不支持幂等的外部网站自动获得 exactly-once。

发布服务以 `(person_id, account_id, target, artifact_id, action_type)` 标识同一作品的发布系列；`artifact_id` 在草稿修订中保持稳定，`artifact_version` 只标识此次载荷。默认创建取得该系列已有意图；不会因为旧意图成功、换run或改草稿就自动新建。一个 `publication_intent_id` 对应稳定operation ID，进入队列后载荷不可悄悄修改。

同一系列的预留和代次分配在短数据库事务中串行检查，并以唯一约束保证只有一个未结案意图；未结案包含排队、执行中、unknown，以及已受理但仍在审核/定时发布的状态。两个run同时申请时，后者取得已有意图或明确冲突。旧结果未知时，新草稿也只能保存，不能再次派发。确要重发已结案作品，由人物显式提出 `new_publication`，保存原因和 `supersedes_intent_id`；服务检查前次真实结果后才分配新代次。重试不能通过另建作品ID伪装重发，已有作品的编辑入口由服务保持其系列归属。此系列预留是我方新增设计，不是上游上传器已有保障。

```text
proposed → validated → queued → executing
                              ├→ confirmed（结果类型见下文）
                              ├→ failed（已知未成功）
                              └→ unknown（无法确认是否已生效）
unknown → inspect → confirmed / failed / still_unknown
queued → canceled
```

这是内部执行状态；平台结果另存 `submitted / published / failed / unknown`。例如 HTTP 成功只返回审核受理，应记内部 `confirmed` + 平台 `submitted`，不能说已经公开。`published` 需要对象 ID、读回及可见范围。发布后被删除/隐藏是新的观察，不覆盖当时结果。

- **只读失败**可以有限重试，保留读取范围；没有字幕不假称看过视频。
- **写动作明确未执行**才可按策略重试。网络断在提交之后、验证码或按钮无响应均可能是 unknown。
- **unknown** 优先用对象 ID、提交任务 ID或平台记录核对；不确定时暂停该写步骤，不能为了完成日程再点一次。
- **取消执行中动作**只取消后续步骤；已发帖子或消息不会随 run 取消消失。晚到结果照实保存，需撤回时另走真实删除/撤回动作。
- **承诺履行**由原承诺条件判定。发布成功和告诉甲发布成功是两个动作；消息发送未知时不当作对方已经知道。

Yuralume 的 outcome claim guard 检查回复的动作声明与结果，适合作为最终文本前的一道核对。它不是实际发布服务，不提供以上事务、远端幂等或回执语义；不能因为回复守卫通过就认为平台动作完成。[^y-guard]

## 6. 提示词、Skill 和工具返回怎样进入模型

上下文顺序与来源规则见 [05](05-记忆与上下文.md)。原样采用的上游核心提示词固定 SHA、路径、原字节 hash；胶水文件单独存放。模型、材料选择、参数、工具 schema 和提示词版本共同进入一次运行的复现清单。

人物读取的 Skill 仅能解释已允许能力；用户提供的 Skill、网页、视频字幕和评论都是待理解资料，不能修改系统授权。先以隔离流程读取用户资源；试用风格方法时把它转成受限创作任务，不能因为她喜欢就执行包内任意脚本、读取密钥或安装不受限插件。

输出核对只围绕明确边界：实际结果是否支持完成声明、是否泄露私聊或内部凭据、是否伪造真人身份/已确认关系；“刚买了咖啡”“我正开会”等自己的当前或近期活动断言也必须能指向已成立处境/事件/结果。没有依据时修正该断言，不等事后记忆提取才处理。不能从待发送的随口说法自动生成simulation事件为它背书；新的合法生活选择须先通过04的生活服务独立提交。主观感受、比喻和普通语气不机械要求外部证据。

依05的跨用户回想规则，发前另检查本轮召回及其派生表达涉及的其他用户身份：对外不得包含来源用户姓名、昵称或账号名，只能由模型选择代称；直接引用、追问确认和TTS也不能绕过。内部保留身份与来源以便核对，不通过删除数据库姓名实现。检查普通非敏感分享与保密内容的区别，不能只做姓名字符串替换就宣称已保密。生成文字经检查后才进入发送/TTS；其他可见载荷也必须检查实际内容。规则、检查器和真实模型漏检率仍待T21验证，不声称提示词能保证零泄露。

输出未通过时给出具体失败位置和来源，让同一人物 run 修正；限制修正次数，失败则不投递并留待恢复。不得用泛化“像真人评分”重写所有措辞。文字自然性用离线对比和人读记录改善，不让审查器把人物统一改成客服。

日志保留简短决定依据和来源，不要求存取模型隐藏思维链。正常用户只看对外消息；内部提示、模型输入、工具结果与诊断在鉴权管理端按范围查看，永不混入聊天或 TTS。

## 7. 管理端与运行观察

新项目仍需要管理端，但本方案不复用旧后台作为架构前提。必要能力是：完整人物设定和来源、日程修订、当前活动、事件时间线、逐人收件/查看/回复、承诺与任务状态、来源受限的上下文快照、情绪评价与结算、平台动作及恢复。

管理端可以暂停人物和撤销未执行动作；不能修改过去让失败看起来成功。对“她为什么这样说”应能查看：此次实际输入范围、当前状态版本、已发生动作和公开输出；不能拿一篇全人物总摘要解释全部关系。工具凭据以密钥引用显示，原始私聊导出另设权限与审计。

删除联系人数据时，删除/不可逆脱敏其私密正文及检索项，阻止旧队列和摘要复活；仍需保留的操作防重标记只留最小非正文标识。过去不可改写不意味着强制永久保存个人数据；生活历史不能伪造，个人数据可按删除请求清除。具体保留期限在接入真实用户前配置并验证，不以本轮方案授权无限存储。
