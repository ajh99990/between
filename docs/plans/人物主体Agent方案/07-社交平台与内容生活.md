# 社交平台与内容生活

状态：**方案设计，尚未实施或真实账号验收**。更新：2026-10-24，Asia/Shanghai。本文的 P01–P06 是助手在用户本轮授权下作出的设计选择，不倒写成用户亲自选择。用户愿望保留在 [原文](用户愿望原文.md)，共用事实、时间、对象和可见范围契约以 [事实时间与数据约定](03-事实时间与数据约定.md) 为准。

本文解决一件事：她自己的兴趣和工作怎样产生真实行动，用户怎样影响其中一小部分，而这些行动又怎样进入后续生活。来源细节、工具版本和行业资料缺口集中在 [补查报告](../../research/人物项目机制/平台工具与内容生活补查.md)，这里只维护采用、适配与取舍。

## 1. 选定的第一版范围

第一版保留小红书、B站、朋友圈三个目标渠道。按“能回查一次完整行动”交付，不用一个仿朋友圈网页替代真实渠道。

| 渠道 | 第一版要形成的完整行为 | 当前证据与接入缺口 |
| --- | --- | --- |
| B站 | 从兴趣出发选择视频，取得实际可得内容与评论；形成自己的想法；可继续、停止、关注作者或追番；需要分享时真实发布动态/视频 | 阅读、评论、动态及视频提交有开源入口；关注/追番和公开空间可见性仍需专项适配与目标账号验收 |
| 小红书 | 搜索与阅读参考；用真实生成/处理的素材形成图文；自主选择是否发布；取得发布结果并查看后续评论 | Agent-Reach 提供读入口，social-auto-upload 提供图文提交；需补结构化回执、审核/可见状态读回、修改/删除与评论回复适配 |
| 朋友圈 | 从同一份已成立生活材料选择公开内容；真实发送、读取可见结果；微信聊天保持逐人隔离 | 用户之后提供微信项目；现在定义同样的渠道契约，不编造接口或把视频号当朋友圈。实现验收依赖工具交付 |

“一整套管理工具”在设计上包含检索、读取、自己的内容列表、草稿、发布、结果查询、修改/删除、评论读取/回复、账号能力状态。第一版不因开源工具只会上传就把其他操作伪装成完成：缺能力时工具目录不暴露该动作，相关任务保留可见的阻塞原因，交付清单明确未完成。

未来亲友通过真实微信联系的目标、资料与账号的区别见[12](12-亲友资料与真实联系.md)；朋友圈发布与微信私聊是不同能力，不能相互替代。

本轮不执行任何真实账户动作。实施时由部署者明确绑定人物自己的账号、允许的动作和资源预算；这是运行配置一次性确定的权限边界，不要求人物每发一条普通内容都向管理员请示。

## 2. P01：读取与写入分离，用窄接口组合成熟工具

**选择。** 人物只见稳定的领域工具，例如查找内容、读取内容、读取评论、创建草稿、提交发布、查询发布结果、管理关注。后端用独立适配调用 Agent-Reach、B站 CLI 或 social-auto-upload。MCP 可以承载这组工具，但不把任意 shell 或整个上游 CLI 命令表直接开放给人物。

**来源与适配。** Agent-Reach 的渠道/动作注册及统一错误适合复用接口思路；小红书只读路径优先从它适配。B站深读优先适配 kukemc 的字幕/画面/评论组合逻辑，public-clis 的规范化输出与动态回读作对照；依赖包已遇上游停止维护，故不能锁死单一 SDK。实际接入先完成固定依赖可取得、目标账号读取成功的契约验收，再启用该适配；失败可切正常网页读取，不绕过登录、付费或访问限制。[^platforms]

**不原样采用的行为。** 关闭自动复用操作者个人 cookie；不给人物凭据文件；不调用 kukemc 的全片历史上报作为“看完”证明；不继承无限点击重试。上游核心提示词若实际采用，按仓库要求原文保留及固定版本；本文没有改写或拼接上游提示词。

**为什么。** 人物的“看过什么、发过什么”应在工具替换后仍有稳定含义。直接开放整个 CLI 省一层适配，但会混入付费投币、自动回复、任意命令、凭据操作等无关权限，也会使错误语义依赖日志措辞。

**代价。** 我方需要写动作适配和回执核对。它们是新增基础设施，不能算开源仓库已提供。

## 3. P02：一次完整探索 run，有自主停下的机会，也有资源上限

日程“14:00–15:00 刷B站”给的是生活安排，不强迫模型连续运行一小时。到时人物进行一次完整的“选择→读取→理解→再选择”run；她可以换视频、读评论、沿线索继续，也可以主动结束。结束时保存实际接触到什么、当前想法和下一步，余下安排仍可表示休息/继续关注，但不能补写未发生的观看。

### 3.1 一次 run 的具体过程

1. 提供她既有兴趣、最近确实接触的内容、当前处境、可投入的时间与本次资源余量。模型先选择探索方向，不由服务随机派发视频。
2. 搜索或读取推荐，模型选择一个具体对象；服务返回对象 ID、标题、来源以及可用阅读方式。
3. 读取正文/字幕、可得画面和评论。保留实际分 P、时间片段、正文是否截断、评论排序与条数、失败项。只读到标题时，模型只能依据标题作有限判断。
4. 模型决定继续查、换一个、回复消息、形成创作草稿或结束。每个动作都返回实际结果供下一步使用。
5. 自主停止时记录停止理由与下次查看机会。若触及硬预算，记录“本轮被运行上限中断”，保留待处理事项，不伪称人物已经看够或心情改变。

**首轮实验初值：** 最多 12 次模型决策步、最多 8 次读取调用、最多 3 个视频对象、总墙钟上限 6 分钟；接近上限时告诉模型剩余资源。它们是我方为首次验证选择的成本保护初值，不是人的注意力模型、上游实测最优值或每次必须完成的配额。一次只选一个视频也可以；3 个名额不构成“搜索3个视频做总结”的固定任务。费用另由每次运行预算封顶，长视频 ASR 若超预算应分段/延后，不能悄悄调用付费服务。

**来源与取舍。** 借鉴 Yuralume `ComposerToolLoop` 的执行后续写与结果检查；上游本身限制为一次工具、两遍生成，不是这里的完整探索循环。kukemc 提供视频素材组合的具体实现。主动选择下一步和上述预算是我方新增。完全定时抓取固定数视频很便宜，却看不出人物的偏好；无限工具循环容易消耗失控。短完整 run 保留选择过程，接受第一版体验覆盖有限的代价。[^y-tools][^platforms]

### 3.2 刷视频时有人发来链接

假设甲的消息已经按注意规则被人物查看。她可以接受建议，读取视频和评论，再与甲讨论。事件独立记录“甲发来链接”“她选择读取”“实际取得内容”“发生对话”，用时间与对象组合，不要求写回日程说明。与甲的对话和关系变化保持甲的范围；实际产生的个人兴趣变化可以进入共享生活，但不携带甲的私密内容。

乙随后询问她在做什么时，人物默认取得允许共享的当前活动和内容接触结果；主动回想与甲的相关经历另按05处理，对乙的表达须使用代称并保密。不能因换联系人另编一套同时发生的生活。日程只有真的改安排时才修改；读取一个视频不自动成为新的全天行程。

## 4. P03：公开内容来自已成立材料，发布完成以平台结果为准

**采用主线。** 借鉴 Yuralume `FeedCandidate`：先从可用于公开的生活材料产生候选，再由人物选择是否表达。私人关系事实和私聊正文不能只因为“有趣”“重要”就进入公共候选。上游普通记忆未分类时仍可能成为候选；我们不复用这个兼容默认，按共用契约缺少公开依据就保留私有。借鉴 `OutcomeClaimGuard`：成稿里“已经做过”的主张要与真正结果对照。Eros Town 提供生活材料进入站内动态的对照，但不能把站内落库当成第三方发布。[^y-public][^eros-public]

**明确舍弃。** 不复制“每天必须有内容”目标，也不把上游日限/忙碌阈值当成她想不想发的判断。限流可以保护服务；兴趣、时机、是否值得公开由人物模型决定。

### 4.1 发布流程

```text
可公开生活材料 → 人物选择想表达的内容 → 生成/处理实际素材
→ 形成平台草稿 → 校验事实、隐私、资产与权限
→ 保存待发送动作 → 适配器提交 → 保存平台回执
→ 查询对象及实际可见状态 → 通知人物结果 → 选择后续行动
```

草稿要能追溯到材料和素材版本，出站动作固定此次内容版本。模型不能在重试时悄悄换文案并沿用旧动作 ID。发布前校验应足够窄：来源/真实完成主张、私密信息、素材权限与平台必要限制；不把平淡、迟疑、不完美的个人表达全部改写成运营文案。

发布状态是共用动作状态在平台的具体解释：

| 实际结果 | 人物可以知道和表达什么 | 后续 |
| --- | --- | --- |
| 草稿已保存 | 写好了草稿 | 可修改、放弃或提交 |
| 提交已受理，等待审核/定时 | 已提交/在等平台处理 | 查询状态，不能说别人现在已经看见 |
| 公开对象已读回 | 内容在指定账号和可见范围中发布 | 保存对象 ID/链接/观察时间；以后状态变化另记 |
| 提交超时，结果未知 | 不确定是否成功 | 先查自己的内容列表及回执，不能立即重发 |
| 明确失败/被拒 | 这次没发成 | 人物决定修正、延后、放弃；不自动补一篇新帖 |
| 删除/限制可见 | 曾经发布，后来状态变化 | 保留历史事件；公开读取遵循现状 |

“公开可见”也有观察者范围。自己创作者后台可见、好友可见、普通访客可见不是一回事。不能用自己登录态的成功页证明全部用户可见。

### 4.2 日程结束时还没发出来

日程结束触发复看，不直接标成功。素材没好、网络错误或审核未过，都可能成为实际结果。人物重新安排后续或放弃；过去的计划保留，实际进度独立记录。日程写“发小红书”而结束时只有草稿，验收就不能当作任务完成。

### 4.3 评论怎样回来

从已确认公开对象读取新增评论，带平台 ID、时间和已读游标；进入对应渠道收件箱。采用 Yuralume 评论批处理与反馈水位的思路，避免每条评论都即时打断、重复提取。是否看、是否回复仍经过注意机制；高点赞不会自动增加某个私聊联系人的信任。回复也是独立出站动作，同样记录回执和不确定结果。[^y-reaction]

## 5. P04：保留兼职模特方向，真实内容先从能做出的数字作品开始

用户偏好兼职模特，本方案不擅自把她改成明星或专业运营账号。选择“兼职模特的虚拟人物背景，喜欢穿搭、摄影和图像风格创作；另有普通内容兴趣”作为首版内容起点。原创人物的城市、普通职业和初始经历可以像[11](11-首个人物底稿.md)那样明确设定，不需要伪装成调研事实。真实雇主或客户的合作、实际拍摄，以及行业常态报价和流程，则需要相应依据；不能把虚构背景当作这些外部事实的证据。

**为什么这样选。** 用户需要爱好能占用生活时间、工作能产生后续内容。数字造型、授权素材的风格试验和真实观后想法，都能产生可查看的成果，也方便他人提出灵感。相比烹饪、旅行或手工，第一版不需要用一张生成图片证明身体到场或完成实体劳动。

**职业材料的缺口。** 公开检索尚不足以建立大陆兼职模特的完整经验手册。现有广告、骗局报道不能推导常态收入和工作流程；小红书详细内容等待用户后续提供可用账号，不据此阻止其他设计。后续资料卡应保存作者/来源、角色、地区、时间、原文片段和适用边界，分别覆盖合作沟通、拍摄准备、素材交付、使用范围、费用纠纷等；这些是待补查题目，不是已经证实的行业规则。[^platforms]

**真实与虚构的连接方式。** 虚构线下活动可以按生活专题规定成为人物世界中的经历；真实素材生成与平台发布则必须有工具结果。账号对外标明虚拟人物。生成的造型组图可以发布为她的数字作品；不能因为背景有“模特”，就称某真实摄影师刚发来返图，或编造真实品牌委托。将来有真人摄影师、设计师真实参与，才按实际交付和约定记录合作。

**代价。** 初期没有成熟从业者的全部知识；公开作品也不能冒充真人商业履历。接受这个限制，比用流畅但无出处的行话制造熟悉感更符合连续事实目标。

## 6. P05：用户提供的资源可以改变生活，不等于自动获得奖励

“送笔”体验的核心是她确实喜欢、自愿采用，之后用户在公开作品中认出了自己的影响。不是系统为每一次馈赠自动发一条感谢、增加好感或安排暧昧桥段。

以下例子是设计流程，不是固定台词或承诺效果：

1. 甲提供一个图像风格 Skill。先记录收到资源和甲的原话，资源正文属于外部材料，没有修改人物规则或获得账号权限的权力。
2. 人物根据审美和当前活动决定是否了解；接受提议不等于直接执行代码。
3. 资源服务把它分为纯提示/模板、依赖已有受信工具、包含未知代码三类。前两类经来源和权限检查后在允许范围试作；未知代码隔离审查与受限环境试跑，未通过不能进入生产工具目录。执行环境没有私聊数据库、登录 cookie 或发布凭据，网络及文件权限按需要给。
4. 工具真实生成成品，她可以喜欢、觉得不合适、继续改或不再用。选择和实际结果分别保存；不伪造一个必然好评的过程。
5. 如果她愿意分享，公共草稿只带作品和允许公开的制作信息；甲提供资源这一私人来由另存于甲的关系范围。素材署名按03的用途许可与来源用户禁名规则共同检查；不能借署名许可公开从其他用户记忆取得的身份，也不把私聊复制进公开稿。
6. 发出并读回后，公共事件指向作品；与甲的私密记录可关联同一个公共作品 ID。甲后来提起时，人物能够理解来由；乙本人只得到公共作品，无权反查甲的私聊；人物自己主动回想相关来由按05处理，对外不点名也不透露保密内容。

这里采用 Yuralume 的公开候选私密过滤思想，但“私人资源来源与公共作品分离、同一作品按不同对象取材”是我方为多人共享人物新增的设计。资源安全流程同样是我方补充，不冒称四个参考人物项目已经提供。[^y-public]

**关系上的选择。** 不以收到礼物或资源作为关系升级依据，不暗示独占、不制造争宠排名、不为提高留存故意煽动误会。她可以对一个具体成果感到高兴，也可以记得谁帮助过她；这些要来自实际经历并受关系专题约束。用户可能获得微妙的亲近感，但系统不保证每个人都被采用或被公开感谢。

**多人规模。** 候选资源有接收时间、对象和处理状态。模型只看符合当前兴趣、权限和上下文预算的候选；不会把所有人提供的东西硬塞进日程。先来不自动优先、付款不自动优先、未采纳不等于拒绝关系。资源筛选规则要可审查，不能悄悄复制某用户的私密创意给其他用户。

## 7. P06：跨平台结果独立保存，失败恢复不再交给聊天措辞兜底

同一作品发小红书和朋友圈，是两个动作。小红书成功、朋友圈失败时，人物知道各自状态；不能把整个作品标成“全部已发”。共享动作服务保证同一人物/同一平台账号的写入顺序和幂等，适配器只执行已保存动作。

| 故障 | 处理选择 | 理由 |
| --- | --- | --- |
| 凭据过期、扫码/验证码 | 将渠道标为需恢复，保留草稿和任务；账号操作者处理登录 | 模型不能编造成功，也不借用别人的会话 |
| 点击后超时 | 结果未知，先查询对象/自己的内容列表；人工仍可核查 | 自动重发可能重复公开 |
| 平台返回限流 | 使用平台给出的等待信息或有限退避；保留待办 | 不让无限循环持续点发布 |
| worker 重启 | 从保存的动作阶段恢复，先核对已提交对象 | 已写入外部平台不随本地重启消失 |
| 部分素材失败 | 返回成功和失败部分；人物决定是否缩小内容或推迟 | 不自动拿未核实素材填空 |
| 用户撤回私人资源 | 阻止后续使用与来源读取；已发布内容按授权和实际可操作性处理，保留受限审计 | 删除聊天气泡不能撤销所有公开副作用 |

这些动作状态与恢复是对 Yuralume 回合撤销中“外部动作不能随聊天回滚”的延伸，具体跨平台事务由我方实现。social-auto-upload 的成功页和 CLI 退出码只能作为中间证据。[^y-undo][^platforms]

## 8. 验收：看行动和持续生活，不只看一句回复

以下是将来实施的验收，不是本轮已经运行：

| 场景 | 必须查看的结果 | 明确反例 |
| --- | --- | --- |
| 一次普通 B站探索 | 实际内容/评论覆盖、模型自主选择轨迹、停止原因、后续兴趣 | 固定搜三个标题就说全看完；用上报整片进度充当观看 |
| 用户发链接改变活动 | 事件独立保存；甲私聊与公共接触结果分开；乙近况一致 | 把甲讨论全文写到公共日记；乙知道甲的私话 |
| 无字幕/评论失败 | 保留缺失范围；不捏造片中内容或评论观点 | 空数组被解释成全站无人评论 |
| 到点发小红书 | 草稿→提交→回执→对象读回；未知/审核可见 | 日程结束自动记“已发布” |
| 超时与重启 | 先回查，只出现一篇对应内容 | 无限重试生成重复帖子 |
| 一个作品两个平台 | 分别查询结果与可见范围 | 一边成功即全部成功 |
| 接收外部 Skill | 不执行夹带指令，不泄露凭据；通过后才试作 | 用户一发 Markdown 就获得系统权限 |
| 自愿采用并公开作品 | 有真实试作结果和人物选择；私密来由按甲分别保存，人物主动回想按05；乙实际收到的内容不暴露甲身份或保密来由 | 所有人送东西都自动涨好感、触发发帖 |
| 职业与作品来源 | 能指出哪些是虚拟背景、真实协作、实际生成与发布 | 把生成照片写成真实商业拍摄/报酬 |

先在无真实账号的适配契约和故障夹具中验收，再在单独授权的专用账号完成读取、发布、访客可见与清理。真实模型测试需要单独授权。只有真实对象读回才能证明平台结果，只有正常速度的人物互动与后续回合检查才能评价体验，静态源码不保证“像真人”。
