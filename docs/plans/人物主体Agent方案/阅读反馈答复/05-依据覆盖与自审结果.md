## 5. 审查怎样进行，哪些意见采纳、哪些没有

本轮先按主题并行查源码、建立问题覆盖表，主Agent整合后又做一次独立交叉审查；同时使用 **OpenCode同一会话两轮讨论**：第一轮审查整体框架，第二轮阅读实际01—04草稿并质疑接线和来源。OpenCode使用`opencode-go/deepseek-v4.1-flash`，未让它运行项目或操作账号；审查意见是待核查建议，不作为事实权威。

### 已修正的具体问题

| 草稿或审查发现的问题 | 修订与落点 |
| --- | --- |
| message ID拼入revision，更正后旧新可能同时入窗 | 02改为稳定逻辑ID，版本进metadata/manifest；原存档修订与模型投影分开 |
| 已发AI工作消息又从IM存档载入，可能像说了两遍 | 02按outbound关联去重，保留工具调用/结果配对与原始运行记录 |
| 默认材料漏列感受和人物级承诺可用性 | 02明确生活感受、对象感受、合法余效、RelationshipAvailability，不用“关系状态”含混替代 |
| 有共享通知却没写出谁调用框架；等工具时收到通知可能被误当结果 | 02增加worker到ainvoke/Command的接线、有类型恢复输入；通知不完成/重发原action |
| 重决到上限后永久挂起 | 02记录retry_at、持久WakeJob、退避与重启恢复，责任不因挂起消失 |
| “输出保存”被当成对外已经说过 | 03区分未发草稿、排队、sent/delivered/unknown；已获知的来信仍可独立整理 |
| 提取任务允许后续批次，但唯一键没有批次身份 | 03冻结来源批次与稳定身份，同批重试和新增来源分开 |
| 修订记忆参考旧摘要却可能丢掉其原始来源 | 03把existing版本及传递来源纳入依赖，目标逐项CAS，旧摘要不充当新证据 |
| 删除后旧索引任务重新写回或发送embedding | 03补worker执行/重试复核和撤销代次、在途请求/写入的清理边界 |
| 仅说checkpoint也要删除，却没有可用粒度 | 01补来源到thread依赖清单、粗粒度清除与generation重建；不假称上游支持source_id删除 |
| 从Tencent分区函数推断整个产品目标；混淆普通Store搜索与中文全文检索 | 03收窄实现结论，注明team缺省范围；关键词能力和向量能力各自验证 |
| D表、索引与路线图仍可被读成允许继续开发 | 更新当前状态、标明旧限制的替代关系；用户原始问题/愿望不改写 |

这些是文档设计错误与接缝的修正，没有自动生成一份“功能测试通过”记录。对应反例已经进入02/03验收表，后续实现应逐个证明。

### 没有原样接受的审查意见

1. **“现在必须把LangGraph写成已采用。”** 不接受其时点要求。用户本轮要答复、自审并暂停代码；已经给出明确推荐和恢复前置顺序，不需要为了显得可执行而混淆决定状态。正式采用时统一改02及08。
2. **“checkpoint只能存ID/游标。”** 部分接受：事实权威留领域库；但完全禁存工作消息会绕开框架已有能力、增加重建成本。允许有来源的工作副本，补删除/恢复机制；无法完整恢复的情况如实说明。
3. **“read_set只需版本”“只复核模型声明依赖的状态。”** 不作为首版替代。时间过期、权限、查询水位即使记录版本没变也会影响资格；模型漏报依赖也可能放行过时自述。保留现行保守复核，并把高频重决和延迟列成要测的代价。以后若证据支持再精细化依赖，不能现在声称正确性与低延迟都无代价。
4. **“所有普通聊天都不应被生活变化阻塞。”** 不接受绝对化。确实依赖旧处境的待发内容必须重决；不相关内容的优化需要更细的依赖证明，不能靠一句通用豁免完成。
5. **“同一事实在不同消息里出现，就必须自动合并。”** 部分接受语义去重需求，但同句话可能描述不同日期的经历，也可能只是重申或更正。比较主体/事项/适用时间并保留各来源，不能用一个claim_key抹掉不同事件，更不能多算关系证据。
6. **“关掉LangMem updates就无法更正。”** 不接受这个等同关系：库的自动更新关闭，我方候选schema仍可提出带旧记录引用的修订，领域服务决定能否追加版本。但模型是否可靠给出引用未测，因此明确列验证，不称已经接通。

同理，不能把别人的姓名在检索阶段一律删掉再声称准确回忆：内部定位、去重与来源核验需要稳定身份；对外称呼由模型选择，禁名与保密在出站继续检查。两种范围不同。

## 6. 仍需证据的事项与下一次开工顺序

这轮不需要用户替我们设计表字段或挑每个库API。现有证据足以给出上述推荐；不足的部分需要实施试验或后续资料，不应伪装成用户还没拍板。

后续获准继续时，建议顺序是：

1. 把承载/记忆采用结论合入正式02及03/05/08，统一修订ROADMAP依赖；保留用户愿望原文。
2. 先做01规定的框架切片：官方PG检查点、同run连续、跨run轮转、共享通知主动invoke、业务提交后崩溃、删除与恢复。使用脚本化模型和隔离数据，不调用真实平台。
3. 用fake extractor验证03的来源、批次、防重、CAS、索引失败/删除及实际入窗；再分别测中文检索和真实候选提取。确定性检查通过不代表中文效果通过。
4. 完成确定性接线后，再在授权的模型/预算下检验普通中文、EE收益、长期状态、跨联系人禁名和关系分寸。记录完整对话与实际输入，不能只读模型自己总结的表现。
5. 按既有C/D/E阶段逐步取得平台账号、微信项目、职业资料和真实作品证据；一条平台链成功不能替代三平台完成。

特别保留以下未测限制：40条/12k原话预算、10分钟活跃窗口、20→8检索候选、1秒扫描、一次修正等只是工程实验初值；串行下共享变化的真实p95等待、最大可服务会话数和超时策略尚无负载数据；记忆库没有完成我方语义/权限适配；没有新的人物运行、真实聊天或平台操作验收。参数应在相应试验中记录原值、变更理由与结果。
