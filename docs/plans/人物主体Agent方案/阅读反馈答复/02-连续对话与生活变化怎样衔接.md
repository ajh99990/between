# 连续对话与生活变化怎样衔接

更新：2026-10-28。状态：**阅读反馈的研究答复与建议，未实施、未通过模型或负载验证；不把讨论中的细节自动升级为用户已确认决定。** 本文回答上下文连续性、IM 历史、十点半复看与“饭好了”进入两段会话的问题。正式采用状态统一由[02 决策依据](../02-决策依据与取舍.md)维护；本篇补足为什么这样建议、具体怎样运作和哪里仍需验证。

原问题完整保留在[对话过程中的小决策](../../../discussions/对话过程中的小决策.md)。本文不改写受保护的用户原话，也不把旧方案已有的 `Exposure`、未读隔离、跨联系人回想规则重新列为未决。

## 1. 我建议怎样回答这几个问题

**保留这件事已经说过、读过、做过的过程；每次请求重新告诉模型“现在是什么情况”；发生变化时主动安排它重新看一眼；但不替它决定一定要向用户说什么。** 这四件事可以同时做到。

旧方案08使用“重建当前上下文”的说法，容易让人理解为每一步扔掉前面的对话和工具过程，再拿摘要重新开始。这个表述不够准确。建议具体化为：

- **同一任务继续：** 保留该任务的用户原话、模型输出、工具调用、返回结果及未完成事项；只在预算、失效材料或权限变化确实要求时整理。
- **当前背景刷新：** 时间、共享活动、注意安排、关系当前状态、尚未完成责任等每次模型请求都重新读取。旧背景可以留在审计快照，但不能继续被当作当前状态。
- **同一联系人隔了几个月再聊：** 新任务仍直接加载双方上一段真实消息，按原顺序、原说话人和原时间交给模型；不能只给“你们以前聊过某事”的总结。
- **新的生活进展：** 保存共享变化后，为正在进行的会话建立待处理机会，主动进入各自下一次模型请求。收到变化后可以选择继续原话题、不说话或提一句近况；程序不代发“饭好了”。

这不是让模型永久保留一个可被后台任意修改的脑内上下文。通常一次 LLM 请求发出后，输入已经固定；我们能做的是安排后续请求、停止使用已失效的未发送草稿，以及保存准确的前后过程。[^lg-graph][^local-runtime]

## 2. 先区分三个容易混在一起的“连续”

以下是建议的业务边界，不要求最终数据库恰好使用这些表名。本文新增的`RequestContext`、`ReconsiderationReceipt`、`ConversationContextNotice`等名称都表示需要保存和检查的逻辑记录；可以作为现有请求清单、步骤账本、WakeJob或outbox的字段/关联记录实现，不要求为每个名字新建表，更不要求新建独立服务。

| 对象 | 解决什么问题 | 内容和生命周期 |
| --- | --- | --- |
| `ConversationMessage` | 与甲上次究竟聊到哪里 | 真实收发消息、发送者、通道消息ID、顺序、时间、发送结果；跨任务、跨月份保存，遵守删除规则 |
| `DecisionRun` 的工作记录 | 正在帮甲看视频，这件事已经做到了哪一步 | 本任务已经取得的材料、工具调用/结果、可保存的短工作摘要、等待的动作与终止原因；不是模型隐藏思维 |
| `RequestContext` | 这一次请求看到的“现在”是什么 | 当前背景、选中的原话窗口、必要任务轨迹、本次新增材料、精确材料ID/版本和时间截止点；每请求产生新快照 |

**聊天存档不因任务结束而结束；任务记录不因每次换最新背景而清空；旧请求快照不因为恢复运行就重新成为当前世界。** 这正好对应用户认可的连续性方向与 IM 新要求。[^feedback-continuity][^feedback-im]

按本轮选型推荐，以 LangGraph OSS `StateGraph` + `PostgresSaver` 承载执行与恢复，LangChain提供模型/工具适配；建议让一个需要持续执行/暂停恢复的 `DecisionRun` 对应一个 graph `thread_id`，恢复时使用相同ID。此推荐尚未合入正式02，不冒充用户已经选定。跨月的 IM 原话由业务消息存档加载，不能把“是否还复用同一个 graph thread”当作消息是否存在的条件。框架的 checkpoint 保存图状态，业务的消息、生活和承诺另有真实存储者。框架不会自行判断什么是人物共同生活，也不会替我们完成未读隔离。[^lg-persist]

这一映射让视频探索、私聊和公开制作可以分别暂停，避免把全部联系人的私聊塞进一个巨型 graph thread。代价是需要一个明确的输入组装入口；它属于 Between 的业务适配，不是再造 checkpoint 或模型工具循环。

## 3. 同一任务怎样既保留过程，又看到最新背景

### 一个贯穿例子

10:25，甲发来视频链接，人物决定看看。她读取了标题、部分字幕，接着请求读取评论。10:27，评论工具尚未返回，她暂时处理别的事。10:29，结果回来；与此同时，她的共享生活已从“准备午饭”变成“饭已做好”。

10:29 的模型输入应同时包含：

1. 甲发来链接的原话，以及此前有关这件事的真实对话。
2. 本任务已经读过的标题/字幕、先前工具调用与这次评论结果，包含取得时间及覆盖范围。
3. **现在**已经饭好，不再沿用10:25的“还在准备”；待处理责任也按最新版本提供。
4. 当前发送对象仍是甲。乙的私聊不会因为这几分钟处理过而自动混入。

模型可以继续讨论评论，也可以说自己先吃饭；它不能因为恢复任务就重复读取已取得的同一份字幕，更不能把旧背景当成她仍在做饭的依据。是否需要重新读取网页由模型结合时间、结果有效性和任务决定，已经完成的写动作则有更严格的操作防重。[^local-runtime]

### 建议的最小状态

```text
RunState {
  run_id, person_id, conversation_id?, current_contact_id?,
  purpose, status,
  working_messages: [模型输出、工具调用与结果，均有稳定 message_id],
  source_message_ids: [已经纳入该任务的 IM 消息ID],
  pending_action_ids: [仍在执行或结果未知的动作],
  covered_opportunity_ids: [本任务已处理过哪些到期/变化机会],
  working_summary?: {text, source_ids, prepared_at},
  last_checkpoint_id
}

RequestContext {
  request_attempt_id, logical_step_id, run_id,
  now, cutoff,
  current_snapshot: {situation_revision, attention_revision, ...},
  dialogue_message_ids: [...],
  run_trace_message_ids: [...],
  added_observation_ids: [...],
  material_manifest: [id, revision, included_parts, hash],
  read_set: [实际依赖的记录版本、时间有效期与许可],
  status: prepared | dispatch_unknown | confirmed_provided | failed_before_dispatch
}
```

`working_messages` 是任务过程，不是第二个可以随意改写 IM 历史的来源。已经发送的文本以消息存档为准；尚未发出的草稿必须标出未发送，不能在下一请求中伪装成“她已经对甲说过”。

同一联系人并不意味着一条任务永远不能结束：上次已结束的看视频任务不因今天新消息自动复活；新run从真实消息存档接续。等待结果的旧run仍保留自己的目的；新消息适合合入旧run时由运行入口选择相同发送对象且仍有效的任务，否则单独处理，后续恢复旧run时纳入双方这段期间已经发生的真实交流。不同run不会各自生成一条互不相知的私聊历史。

每次模型调用前，生成一份新的当前背景，放在模型适配器指定的位置。不要每轮向列表追加一个互相矛盾的“现在正在……”系统消息，然后期待模型自己猜哪条最新。历史工具返回中带旧状态的内容保留其读取时间和版本；请求最前方明确当前权威版本，提交时仍复核实际依赖。

```text
准备下一请求(run):
  载入该 run 的 checkpoint 与必要任务轨迹
  读取当前时间、共享处境、当前联系人和相关责任
  复核已载材料的删除、撤权、更正与有效期
  固定 cutoff，确定允许的实际消息ID，不临时扩大到“数据库最新”
  合并本 run 已获准的新材料；保持工具调用与结果配对
  选择真实 IM 尾段 + 必要运行轨迹，按来源ID防止重复全文注入
  生成本请求的新背景、最终载荷、材料清单与 read_set
  持久保存准备记录，再交模型适配器派发
```

这里的“合并”不等于把输入变成摘要。只有超预算、旧材料已不再必要，或权限变化时，才按第4节整理；保存原文与其引用，不悄悄删掉尚未解决问题的依据。

**持久保存过的工具返回也不自动等于已经提供给模型。** `inbox.read`取得首次正文后，读取选择仍绑定原run的下一逻辑步骤；请求确认前，恢复器只可在同一有效读取选择下重试，不能把这份正文当作普通已知轨迹交给另一任务。记忆提取、语义查询、embedding、情绪判断等后台都要等待有效`Exposure`，不能以“已经存在checkpoint里”为理由提前处理。HTTP成功或请求已排队也不足以确认；具体状态继续执行03，不再另造简化版。[^local-exposure]

### 用框架时具体复用什么

LangGraph 的 `add_messages` 会按消息ID合并：新ID追加，同ID更新；没有ID时会生成新ID。**同一条来信每次重新产生随机ID，会在恢复时被当成新消息。** 因此输入适配器应使用稳定逻辑ID，例如 `im:<conversation_id>:<message_id>`，不把revision拼进ID。来源版本放在消息metadata与本次材料清单中；合法更正更新同一逻辑消息的模型投影，不把旧版、新版追加成两条来信。每次请求的旧清单仍保留当时实际版本，不倒改已发生的输入。接收端另用通道/账号/平台消息ID唯一键抑制重复Webhook。二者分别解决运行输入重复与原始收件重复。[^lg-source-message]

框架允许同ID更新，不等于授权修改已经发生的消息。消息更正、撤回、删除先由业务规则处理，再更新模型投影；保留允许保留的修订信息。`add_messages` 也不理解本文的“十点半复看目的”，不能以它代替机会去重。

同一来源若已经以 `inbox.read` 的工具结果全文进入本 run，就不再同时把它复制成一个新的 `HumanMessage` 全文。工具调用/结果的配对仍保留；以后新 run 可将已确认提供的真实原话按 IM 消息重新呈现。这个去重是输入编译器的来源ID规则，不靠字符串相似度，更不能为了省token删掉孤立的工具结果，留下无返回的工具调用。

角色已发消息也要去重：模型工作记录的候选输出经检查、出站成功后，以`outbound_id`关联实际`ConversationMessage.id`。之后输入组装只呈现一份真实已发文本及其发送时间，不能同时把原`AIMessage`正文与IM存档当作两次发言。工具调用与工具结果仍按`tool_call_id`完整保留；同一AI记录若同时有文本和工具调用，模型适配器生成合法的输入投影，去掉已由IM位置呈现的重复文本，但不删掉仍有返回结果的调用。原始运行记录不改，关联与实际渲染清单可回查。未发送/发送结果未知的输出也不能伪装成已发送IM消息。

## 4. 跨月聊天：原文窗口必须真正出现在请求里

日期间隔不参与“最近一段原话是否保留”的过滤。假设上次最后几句发生在7月，今天是10月，消息尾段就从7月的最后一段接到今天；每条带真实时间，模型同时看到当前时钟，避免把七月的“正在开会”当成此刻状态。[^feedback-im]

建议先设一个**可调整的实验初值**：目标取得最近40条双方原话，为其预留最多12,000输入token；模型上下文较小时按总输入预算缩小。数字是本轮工程建议，理由是覆盖多轮短句和连续指代、同时留出任务材料与生成空间，既非用户指定，也非已有实验结论。实际选择应按完整来往边界扩展或裁切，不能刚好从“嗯，好”开始而省略它回答的问题。

12,000只是IM原话的**子预算**，不能让各模块分别占满一份模型窗口。一次请求共用总预算：`系统与人物指引 + 工具schema + 当前背景 + IM原话 + 本run工具/模型轨迹 + 新工具结果/媒体 + 检索材料 + 输出预留 + 适配器安全余量 ≤ 模型上下文容量`。统一输入组装器按提供方计数规则估算并在派发前核验最终载荷；图片等不能仅按文本token计算。移出重复已发文本和旧大工具返回后，再按下面的原话保护规则分配。若仍不能容纳，使用适配的更大容量或明确分段/暂停，不由某个模块静默挤掉必要条件和原话。

必须一起落实以下规则：

- 正常短句场景保留多轮完整原文，不只最后一句，不用一段摘要替代全部原话。
- 最新消息与本任务未解决事项的原话优先；与当前事项无关的更老工具大返回先移出请求。长期摘要可作补充，原文按ID仍可查询。
- 极长的单条消息或媒体超过预算时，优先扩大该请求预算/使用合适模型；仍不够则明确分段和覆盖范围、提供继续读取工具。不能静默截断后标成全文已提供，也不能宣称所有极端输入都能一次看完。
- 未读新消息不因为处在“最近40条”之中就被加载。先取已有合法提供记录的原话；新来信按获准首次读取路径进入。输入窗口的时间跨度与可读资格是两件事。
- 重试、重启和跨run读取均使用稳定来源ID；重复读取不会重复产生“共同经历”或给关系增加一份证据。

工作记录超预算时，可把较早已结束的工具子过程整理为带来源引用的工作摘要，保留最近模型/工具往返和未完成动作的准确状态。压缩不是每步必经节点，也不是把前面的真实 IM 对话全部替换掉。具体阈值及对中文长文本的损失必须通过试验校准。上游 Yuralume 已有原话窗口加载器，但其窗口实现本身不证明上述跨月、未读和预算组合在 Between 已经成立。[^y-window]

## 5. 默认准备什么，什么留给模型自己查

程序负责把“如果不给，人物就不知道自己是谁、现在在哪里、正在跟谁说话”的材料直接准备好；其余内容让模型根据问题选择工具。这样避免人物每句话先查时钟和当前活动，也不把所有问题都做成固定的记忆→情绪→日程→回复流水线。该分工落实用户倾向，是否优于其他编排仍需同条件测试。[^feedback-default][^local-memory]

| 每请求默认提供 | 按需工具取得 |
| --- | --- |
| 人物核心资料与当前生效修订；当前时间/时区 | 亲友详细经历、职业细节、表达案例 |
| 共享当前处境及最近发生、对该会话可用的变化 | 更早生活事件、活动过程、资源与作品详情 |
| 当前联系人、双方关系当前状态、有效保密约定 | 旧聊天全文、特定主题记忆、明确跨联系人回想 |
| 按当前时刻投影的生活感受、该对象感受及仍有效的去身份余效；原因引用按权限过滤 | 更早感受的原因、相关事件与评价依据 |
| 人物级`RelationshipAvailability`，说明当前承诺可用状态，不泄露其他用户身份 | 有权限的具体关系依据和承诺详情 |
| 此会话真实原文尾段、已经处理到哪条、尚未发送的草稿状态 | 视频、网页、评论等新的外部读取 |
| 本次到期目的、相关未解决承诺/任务、已返回工具结果 | 是否调整未来日程、是否创作/发布等行为所需额外材料 |
| 当前注意安排、允许看到的通知概况、当前运行预算 | 模型明确选择读取的新收件正文 |

“原话尾段”必须默认给；“所有相关旧事”不默认全量给。默认材料还应带查询入口和来源ID，以便模型追问。当前联系人仍是记忆查询默认目标，模型可以显式扩大；扩大查询不切换发送对象，其他用户名字不得通过对外文字、引用或TTS说出。正式规则已经在05维护，本文不另改一套。[^local-memory]

## 6. 十点半复看时，已经在和甲聊天了，究竟怎样处理

**不能只检查“是否正在聊天”，应检查这次复看原本要解决什么，以及这个目的是否已经得到处理。** 正在聊天气，不代表此前答应看的视频已经看过；反过来，10:29已经重新决定“甲这边先聊着”，10:30就不必再单独问一次同样问题。[^feedback-wake]

建议把 `WakeJob` 看作一次调度机会，并保留它指向的业务目的。机会可以合并，责任不能因为合并消失。

```text
WakeJob {
  id, person_id, target_conversation_id?, due_at,
  purpose_kind: reconsider_attention | revisit_item | fulfill_commitment,
  subject_id, subject_revision,              # 注意决定/待办/承诺
  condition_key,                            # 这次为什么应再看
  status: scheduled | attached | consumed | superseded | retryable,
  attached_run_id?, handled_by_step_id?, completion_basis?
}

ReconsiderationReceipt {
  subject_id, subject_revision,
  conversation_id?, decision_step_id,
  observed_inbox_cutoff?, considered_at,
  outcome: continue | read | defer | cancel | no_action,
  next_wake_id?
}
```

`ReconsiderationReceipt` 记录模型确实处理过哪个目的，不能只凭“模型请求成功”就写。`subject_revision` 说明这次考虑的是哪一版注意安排/待办；`observed_inbox_cutoff` 说明当时看到的通知概况截至哪里。这里只用收到时间和条数就可知道后来有新消息，不准读未读正文推导“内容不重要”。

| 10:30的实际情况 | 建议处理 | 为什么 |
| --- | --- | --- |
| 10:29同一个注意决定已被明确改成现在查看甲，并有处理记录；没有新增未覆盖的目的 | 标原复看机会已满足/被新安排替代，关联实际处理步骤 | 无须重复问一次；要留完成依据 |
| 正在聊甲，但原来是“10:30回来判断要不要看手机”，尚无相应处理记录 | 把该复看机会并入甲的下一安全步骤，给模型一次重新判断的机会 | 当前聊天本身不是完成证据 |
| 10:29处理过旧通知，10:29:50又收到新来信 | 旧目的是否有效按其范围判断；新通知另保留机会，或合并进下一步 | 不用“之前已经聊天”吞掉后来收到的消息 |
| 原来欠甲“10:30发修改后的图片”，现在正与甲聊午饭 | 图片承诺继续存在；把该责任送入当前步骤，不能因闲聊标完成 | “重新看看”与“交付图片”不同 |
| 甲的当前请求已经发给LLM | 先附到待处理机会，不能改这个在途请求；在返回后的边界或下一请求处理 | 网络请求输入已经固定 |
| 期间人物另作注意决定，把复看改到11:00 | 旧任务标被新版本替代，保留新WakeJob | 不重播过时安排，也不擅自提前读取 |

目的满足条件应是有限、可检查的字段组合，不建立万能文本相似度判断器。对于“消息提醒机会”可以比较目标、注意版本和已处理通知水位；对于“完成图片”必须检查相关作品/发送结果。语义上“甲是不是取消了请求”仍由已读到该消息的模型判断，程序不能根据新消息出现自动取消。Yuralume的新普通来信可能取消旧busy_defer，是我们已经明确不照搬的分支。[^y-followup][^local-life]

```text
处理到期机会(wake):
  短事务领取并读取当前 subject / revision
  若 subject 已取消或被替代：记录 superseded，结束
  若同目的、同有效版本已有实际处理依据：关联依据并消费机会
  否则：
    找到同一目标会话可接手的 run；没有则建立 run
    以 wake.id 幂等附加机会，保留其原 subject_id
    准备中则一并纳入；请求已在途则放到下一边界
    只在模型实际处理并保存结果后标 consumed
    若模型决定继续延后，同时保存新的唤醒
```

`attached` 只表示交给哪个run，不表示人物已经知道；run失败或取消必须释放/转交机会，不能留一个永远不再唤醒的attached任务。多项欠办可一起呈现，但各项有各自的完成状态；既不每到一个闹钟都打断发消息，也不把多个承诺合成一行之后忘了其中一个。

## 7. “饭好了”怎样主动进入甲、乙两段会话

### 从生活变化到两次实际输入

假设11:50，人物正在分别与甲、乙交流。12:00，生活服务提交“饭做好了，准备吃饭”。这是已成立的共享变化，来源可能是明确标记的模拟生活进展；不是在甲的回复里临时编出后再当成事实。

建议使用现有数据库outbox的业务扩展，不另造一套消息中间件：

1. **生活提交事务：** 写事件、`CurrentSituation`新版本和`shared_context_changed`待分发记录。事件本身只存一份。
2. **分发器：** 找到当前活跃的甲、乙会话，分别创建待处理变化引用，不复制其他人的私聊正文。状态字段只是“待提供”，不是已看。
3. **运行调度：** 给甲、乙各安排一个处理机会。如果本来就在准备下一请求，合并进去；如果正在等工具，可以先处理这项生活变化；如果该会话暂时没有下一请求，也主动排一个轻量处理步骤，不等用户再发消息。
4. **输入组装：** 对甲带甲的对话尾段与关系，对乙带乙的。两边都读到同一个生活版本，另明确“这是自己的新进展，不要求一定通知对方”。
5. **模型选择：** 甲正在问吃什么，可以自然提起；乙正在说自己的事，可以继续听，或暂不回复。记录这个变化已实际提供、是否已被处理，是否对外表达另记。

第3步是与旧方案“下次读最新状态”最实质的区别：**即使用户没有再来一句，也主动创造处理机会。** 只更新数据库或给网页推一个通知，尚未让模型读到，不能算满足愿望。[^feedback-life-push]

具体调用者是运行worker：它从持久机会队列领取目标，取得人物短步骤资格，再调用已编译的LangGraph。分发器只负责写机会；worker必须持续消费，而不是挂在“下一次用户来信”的HTTP处理函数下。拟议接线如下，其中查询和路由辅助函数属于业务代码，`ainvoke/Command`是框架入口：

```python
# 接线伪代码，未运行；一次机会不是一条必须发送的回复。
trigger = claim_due_context_notice()  # 本例只演示共享处境通知，稳定ID
run = select_compatible_live_run(trigger)  # 同目标、同有效目的
if run is None:
    run = persist_new_run(trigger, purpose="shared_context_refresh")
    graph_input = initial_state(run, trigger)
elif run.invocation_in_flight:
    persist_pending_trigger(run.id, trigger)  # 不并发调用同一thread
    return  # 边界回调与恢复扫描继续消费，不丢trigger
elif run.parked_at_interrupt:
    graph_input = Command(resume=typed_resume_input(trigger))
else:
    graph_input = state_update_for_next_boundary(trigger)

async with acquire_valid_person_step(run):  # 非数据库长事务
    await graph.ainvoke(graph_input,
        config={"configurable": {"thread_id": run.thread_id}})
# 图在明确的让出/等待节点停下，再释放步骤资格。
# 成功调用不自动消费trigger；节点保存实际处理记录后才消费。
```

若甲、乙最近仍在聊天但两个run都已结束，分发会分别创建`shared_context_refresh`运行，主动调用模型；不等他们再发话。若已有任务在等评论，则用该任务的有类型恢复入口，规则见下节。图的每个模型决策步骤之后须有明确的让出点，不能一次`ainvoke`内部无限连续调用模型却声称已经公平轮转；具体中断节点及状态路由由01的框架切片验证。调度器重启扫描未处理机会，派发失败保留重试身份。

```text
ConversationContextNotice {
  id, person_id, conversation_id,
  source_event_ids: [...],
  latest_situation_revision,
  status: pending | prepared | confirmed_provided | considered,
  request_attempt_id?, decision_step_id?,
  created_at, provided_at?, considered_at?,
  outcome?: no_reply | continue_topic | mention | defer
}
```

`considered`需要模型返回并完成相应处理记录。返回无效时可能只有`confirmed_provided`，仍要按失败策略重试；不能为了仪表盘全绿把“收到有效模型输出”和“已完成业务判断”合成一个状态。模型输入确认复用03的材料清单原则，自己的已提交生活不伪造成未读来信Exposure。[^local-exposure]

`latest_situation_revision` 用于快速知道目前最新哪版；精确判断仍用事件/通知ID。若几秒内接连“饭好→端上桌”，可以一次提供最新处境和这两件变化，免得每个事件都调用两遍模型。原事件保留，真实承诺、对外动作结果与未完成事项不能被“只留最新状态”抹掉。

### 正在等工具的同一个任务，怎样先接住生活变化

`await_result`在这里是“还有外部动作未完成”的可持久业务状态，不是一段一直阻塞、只能接受工具结果的长函数。第8节的异步提交工具先已返回合法的queued回执，因而模型调用协议中的工具调用/返回已经配对；真正等待的是该回执中的`action_id`所指外部工作。后续恢复入口区分三种输入，不能看到任何恢复信号就当作工具成功：

```text
ResumeInput =
  tool_result {event_id, run_id, action_id, result_id}
  | context_notice {event_id, run_id, notice_id}
  | wake {event_id, run_id, wake_id}

恢复同一run(input):
  按event_id防重，载入同一run/thread的checkpoint
  tool_result → 检查action_id归属、实际结果及当前状态；记录结果可用
  context_notice → 仅附加生活变化引用；不改pending_action_ids或动作完成状态
  wake → 检查相应复看/承诺目的；不从到期推导工具成功
  在人物调度允许的下一边界，读取最新背景和仍待结果的动作
  把此次真实变化交给模型；模型可继续等、调整后续动作或选择回复
  没有完成或合法取消的action仍保留；继续等待时保存checkpoint
```

例如`run-A`在等`action-comments-7`，饭好通知先到，恢复输入是`context_notice`。模型得到“饭已好；评论仍未返回”，可以暂不向甲说话，然后回到等待；服务不再提交一次评论读取。稍后评论实际返回，执行服务发`tool_result(action-comments-7)`，仍回到`run-A`，携带其原任务过程与最新生活。若模型已经明确取消后续使用，晚到结果仍如实保存，不因此重新发送；若结果未知则走核查，不能在生活通知时自动改成失败或成功。

LangGraph承担保存、恢复和路由执行；以上带类型的输入及其业务判断由本项目节点负责。不能把所有信号都作为同一个“工具结果”的`resume`值塞给一个假定返回成功的等待节点。通知刷新不建立新的外部`operation_id`，不消耗或清空原`action_id`；只有明确新动作才经原工具契约建立新意图。

“活跃会话”建议由是否有可继续的聊天run，以及最近是否真实接触/发送过消息来确定。初版可把最近10分钟当实验窗口；它只是决定哪些会话值得主动刷新、控制模型调用量，不是人物感情或关注程度。后台刷新本身不延长活跃期，长期等待工具的run也不能永远算热聊；它保存待消费的新处境引用，结果回来主动安排续跑。几个月未聊的联系人不因饭好自动得到一次模型调用；其下次来信仍主动准备最新生活。窗口值需要在真实使用节奏与成本记录中调整，用户尚未确认此数值。

### 在途请求为什么不能被直接更新

DeepSeek Harness 提供了一个可直接理解的参考：`followup`排到下一turn并唤醒，`steer`排到下一step并唤醒，`inject`排到下一step但不单独唤醒；`preStep`才领取待处理输入、组织当前指引，`buildRequest`把本次消息列表冻结。这证明“下一边界进入”和“是否主动唤醒”可以分开设计。我们的共享变化更接近`steer`的意图，不能只用不唤醒的`inject`思路然后等下次用户来信。它的通用inbox不等于人物未读收件箱，不能直接拿`steer(用户正文)`绕过自主不看和Exposure。[^dsh-boundary]

如果12:00甲的请求已经交给LLM，它的输入仍是11:59准备的版本。更新 LangGraph checkpoint、内存对象或数据库，都不能令远端已经开始生成的那一次请求自动看到饭好了。正确处理是：

- 变化立即持久排入甲的待处理机会。
- 当前请求返回后，保存真实模型输出和输入确认，检查未发送的决定是否仍依赖旧处境。
- 旧处境已经失效时，未发送草稿先不派发；带新处境继续同run修正/重决。不能偷偷改它说了什么，也不能把无效草稿写为已发消息。
- 下一步明确带入新变化；取消旧请求只是减少浪费的可选优化，取消是否成功、是否计费要按提供方能力核对，不作为首版正确性的前提。

依旧方案08，提交检查当前已读的处境版本有变化时，首版可以保守地要求重决；不要自行假设能准确判断某一句与处境“无关”就跳过。将来若想减少无意义重算，可以把依赖拆细并单独验证，但那是后续优化。已经发出的消息和已发生的外部动作不会被回滚，必要时产生新的解释或更正。

### 串行与“几秒内两边知道”存在实际取舍

旧08选择同一人物同一时刻只有一个短模型决策步骤。**因此甲、乙两边不能保证在任意负载下同时于几秒内完成新输入。** 在途模型若用了十几秒，后一个会话就得等；模型耗时不能通过称呼“短步骤”变短。

本轮建议先保留串行，原因是它让人物生活和承诺提交顺序可解释，并符合目前的设计边界；用以下措施控制等候：

1. 工具提交后立即返回动作ID和queued状态，实际网络/下载在后台执行；不要把几十秒抓取包在占有步骤的同步节点里。
2. 每次模型输出或工具结果处理后让出调度机会；连续浏览run不能无限接着占用。
3. 同一目标会话只保留一个待执行的共享刷新槽，合并变化引用；相同通知不重复排无限多个run。
4. 轮流服务不同目标，等候时间增长时提高调度优先级；到期责任和共享刷新保留独立待办，不得被不断到来的普通消息饿死。优先级只决定技术执行次序，不替模型选择回复态度。
5. 设置模型请求截止时间，超时留待恢复；队列过载展示在管理端，不能让人物谎称忙碌来掩盖服务容量问题。

测量要拆成：`变化提交→机会建立`、`机会建立→请求派发`、`派发→确认提供`、`确认提供→处理完成`。没有授权的真实模型及并发测试前，只能把低负载几秒作为目标，不能承诺SLA。

轮转还不能单独解决“不断有新版本，使每次生成都失效”的问题。需要记录同一待办因状态变化重决的次数，达到单轮配置上限后标为`waiting_for_recheck`，保留原责任。保存这个状态时，在同一事务写入`retry_at`、阻塞原因/依赖版本和唯一的恢复`WakeJob`；已有wake则更新其到期条件，不每次再加一份。调度器到`retry_at`重新检查当前有效状态，相关依赖出现新的可用版本或工具结果到达也可提前合并一次恢复机会。它们先做便宜的状态检查，满足重新尝试条件才领取人物步骤，不因每个新版本立刻重跑模型。

若版本仍在持续变化，调度器保留下一次有上限间隔的检查，记录退避和累计等待；不会把任务留在无后续触发的状态。重启扫描同时恢复到期wake及发现缺少恢复wake的等待项，后者记为运行错误并补偿建单。管理员可看到持续冲突并介入，人工取消或明确暂停另有状态，不能暗中等同完成。退避间隔、单轮重决数和累计资源限额都属于待负载验证的工程配置。

分发只合并调度机会，不可为减少冲突吞掉真实变化；正确性所需的撤权、承诺变化等不能暂缓生效。此时无法及时回复应如实记为运行延迟，不能为了完成延迟指标把旧草稿放出去。恢复只重决尚未执行的部分，既有动作依然复用原操作ID，不因退避结束重新派发。

若实测两边延迟始终不能接受，后续候选才是“各会话可并行只读推理、人物领域写入串行且冲突重决”。它增加共享版本冲突、重复成本和出站过时风险；不能一面保留‘只许一个模型步骤’的原规则，一面声称已经采用并行解决。当前建议不偷偷改变这一架构。

## 8. 用 LangGraph 时，框架与业务各负责哪一段

本篇以 LangGraph 为具体可行路线展开，最终承载采用状态以同套答复的选型结论为准。以下不是说框架开箱即有 Between 的人物机制。

| 职责 | 复用框架 | 我方仍须实现/适配 |
| --- | --- | --- |
| 多次模型和工具往返 | 图节点/条件路由、消息状态 | 人物提示词、允许的工具、停止与等待语义 |
| 保存和恢复运行 | 持久checkpointer与thread ID | run和IM会话映射、checkpoint生命周期、删除联动 |
| 追加已知消息 | `add_messages`按ID合并 | 平台收件唯一键、稳定来源ID、原文窗口和未读资格 |
| 新背景进入下一请求 | 在模型节点前准备运行输入 | 当前背景读取、共享变化分发、各会话提供水位 |
| 重新执行节点 | 框架恢复节点/任务结果 | 操作ID、领域唯一约束、outbox、外部unknown核查 |
| 十点半复看 | 框架可承载执行步骤 | 时钟、WakeJob目的、责任是否满足、合并和唤醒策略 |
| 多个会话不饿死 | 不依赖图能并行就自动解决 | 人物级调度、公平性、截止时间和排队观测 |

官方明确 checkpoint 在步骤边界保存，恢复时节点可能从头执行；节点内已经做过的数据库/外部写入不会因此天然只执行一次。我们把每个领域变更与外部动作绑定稳定`operation_id`：重放读取已有结果，unknown先核查，不因为换了`request_attempt_id`就再次发消息或发布。任务结果缓存有助于跳过完成步骤，仍不能解决“外部成功、保存回执前进程退出”的窗口。[^lg-reexecute][^local-runtime]

首版不需要把一小时浏览写成一个长节点。模型节点返回动作，领域节点保存意图，立即产生合法的工具返回“已排队，action_id=…”，图保存等待/下一机会状态；后台结果通过持久事件到来。下次恢复模型时，先核对结果是否已有，再把结果和新背景交回。这样没有一个未返回的工具调用被遗落在消息列表里，也不需要伪造工具已经完成。

## 9. 失败场景和必须补的验收

以下是待执行测试，不是本轮已通过结果。

| 编号 | 可复现条件 | 必须检查的结果 |
| --- | --- | --- |
| C01 | 一个任务依次读字幕、评论，工具等待中共享活动改变 | 后续请求保留前面工具过程；当前活动为新版本；无重复读取/重复写入的假象 |
| C02 | 同一联系人三个月后再来信 | 实际模型载荷含上次多轮真实原文和真实日期；不能只查数据库证明存过 |
| C03 | 通道重复投同一消息、graph恢复重放同一输入 | 原收件只有一条；运行输入不重复；提取/关系证据不增加一份 |
| C04 | 原话窗口混有未读消息，后台同时整理记忆 | 未读正文及其摘要不进窗口/后台；首次读取确认失败不放行后处理 |
| C05 | 请求已派发但超时，后收到迟到有效输出 | 按03保留实际提供事实；失效租约不提交旧决定，不重放平台写动作 |
| C06 | 10:29已处理同一复看目的，10:30旧WakeJob到期 | 有完成依据则不多发一句提醒；没有依据不能凭正在聊天判完成 |
| C07 | 10:30仍欠图但正聊天气；又到一个普通提醒 | 调度机会可合并，图片责任保留，普通新消息不自动取消欠图 |
| C08 | WakeJob附到run后进程退出，或run被取消 | 机会可重新领取/转交，不因attached状态永久丢失 |
| C09 | 饭好时甲在途、乙正等待外部工具 | 两边分别有主动机会、请求清单及处理结果；未发过时草稿被挡住；不要求两边都说饭好 |
| C10 | 一秒内共享活动连续变化五次 | 事件保留，可合并上下文刷新；不发十次模型请求；变化不能错误标成已经对用户披露 |
| C11 | 甲不断发消息、浏览工具循环不停、乙有到期承诺 | 技术轮转保证乙和生活检查最终取得机会；记录排队延迟，不伪造人物拒聊 |
| C12 | 极长中文消息和大工具结果把窗口挤满 | 真实原话不是全部摘要化；载荷覆盖范围准确；未解决责任没有被静默裁掉 |
| C13 | checkpoint恢复时遇到已撤权/删除/更正材料 | 当前请求不重新暴露失效原文，旧摘要及任务轨迹联动处理；不会因持久保存而绕过权限 |
| C14 | 两边共享刷新后都选择不发消息 | 记录实际提供及处理；出站零消息是合法结果，不能把“不发”当系统失败重试到发为止 |
| C15 | 同一逻辑消息更正后再次载入graph | 消息ID不因revision改变；当前投影只有有效版本，旧请求清单保留原版本；更正不被算成第二条来信/独立证据 |
| C16 | 模型工作记录中的回复已出站，又从IM尾段加载 | 通过outbound关联只呈现一次已发正文；工具调用/结果仍成对；unknown草稿不冒充已发原话 |
| C17 | `await_result`先收到饭好通知，后收到同一action的实际结果 | 通知只刷新上下文，原action仍待完成且不重复提交；晚到结果续回同一run，取消后的结果不复活旧发送 |
| C18 | IM子预算未超12k，但背景、工具轨迹、媒体与输出预留使总量超窗 | 最终载荷受统一预算约束；不静默裁掉必要感受、关系可用状态或全部原话；覆盖与分段如实记录 |
| C19 | 连续状态冲突达到单轮重决上限，然后停更/工具返回或进程重启 | 有持久retry_at与唯一恢复wake；可恢复到同一责任，未丢失、未无限立即重决、未重放外部动作 |
| C20 | 生活感受变化、对甲的感受不同且存在有效去身份余效，另有人物级承诺状态 | 每请求默认材料逐项包含这四类当前条件及有效期；不会只传一个笼统关系状态，也不泄露余效来源用户身份 |
| C21 | 甲乙最近仍在聊天，但饭好时两个run都已结束且没有新来信 | worker主动创建/调用两个共享刷新run，实际模型请求含新处境；只写pending notice不算通过 |

确定性替身能验证IDs、顺序、去重、范围、排队和故障恢复；真实模型测试才能观察它是否自然承接、不重复唠叨、能否适当选择不发。两者需要分开记录。压力测试还应测最老等待年龄、各会话获取步骤次数、生活刷新延迟分布及超时比例，而不是只看总吞吐。
