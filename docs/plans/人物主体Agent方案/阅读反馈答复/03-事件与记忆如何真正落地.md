## 1. 先回答你的核心问题

**有可复用的开源基础，但没有核查到一个拿来便能同时满足我们全部人物规则的记忆库。** 我的建议是：用 **LangMem 的结构化候选提取部分 + PostgreSQL 中的来源与记忆记录 + LangGraph 的 Postgres Store 作为可重建的语义检索副本**。不要把人物事实、未读权限、日程、承诺和所有人的关系都交给记忆库接管。

这不是要求重新造一个完整记忆产品。LangMem 已经实现“给模型消息与已有记忆，返回新增/修订建议”；Postgres Store 已经实现命名空间、JSON 文档及可选向量存取；我们补的是本项目必须拥有的判定：这是谁知道的材料、从哪来、是否已提供给人物、是不是用户自述、能不能成为共享经历，以及某次输出能不能说出另一个用户的名字。后者无法仅通过更换记忆库消失。[^lm-manager][^pg-store]

Graphiti 的价值很明确：它能把材料抽成有时间范围和出处的关系图，支持之后沿关系查询。若后续实测证明“人物—亲友—工作—作品”的跨关系检索是主要瓶颈，可以加它作为派生检索层。**现阶段不建议把它作为唯一记忆底座**，主要代价是额外图数据库、抽取/消歧/冲突判断链，以及我们仍需保留的事实和权限服务。[^g-ingest][^g-driver]

TencentDB Agent Memory 有较完整的分层提取、管理和接入机制，值得学习；但当前核查到的 L2/L3 实现采用 `team + agent` 范围，有 team 时不再按单个用户拆开；team 缺省则回退用 user_id，之后才是 default。这是这条画像路径的具体设计，不足以概括产品所有模式。若我们把不同用户配置进同一 team/人物 Agent，再沿用这条路径，会与“不把所有私聊汇入人物总记忆”的边界冲突；不能只把 `agent_id` 改成人物 ID 就认为完成适配。[^t-profile]

这些是基于固定源码的**适配判断**，不是中文召回质量、模型效果、吞吐或成本已通过测试的结论。

## 3. 不要让一个“记忆”字段承包所有东西

用一个贯穿例子：

- 周一 10:00，甲发来：“最近项目上线，天天加班，周一上午还要开会。”
- 人物决定 10:30 才看消息。
- 10:31，她看到消息，和甲聊了几句。
- 周三 19:00，甲又说：“今天总算能早点走了。”
- 周四，甲纠正：“其实项目这周延期了，昨天是临时放我们早点走。”

这些材料分开保存：

| 记录 | 写入者与时间 | 能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| `Message(m1)` | 10:00 通道入口 | 甲发过这句原话 | 说法已经核实、人物已经看过 |
| `Event(e1: message_received)` | 与收件同一提交 | 系统收到 m1；发送方、渠道、时间可查 | 角色已经知道“甲在加班” |
| `Exposure(x1)` | 10:31 对应模型请求已确认提供 | m1 的哪些内容实际进入人物模型请求 | 模型一定理解、一定记住 |
| `Claim(c1)` | 已允许语义处理后 | 甲自述近期项目上线、经常加班 | 这是已核实的雇佣/项目事实 |
| `Memory(mem1)` | 候选通过校验后 | 为今后交流整理的“甲近期说工作赶进度”，带 m1/c1 出处 | 新增一个独立证明“项目上线”的证人 |
| `MemoryRevision(mem1,v2)` | 周四更正已知之后 | 旧总结已不适合作当前情况，保留更正依据 | 抹掉甲周一确实说过的话 |

**事件不必经过模型才成立；理解也不必一提取就成为事实。** 收到消息、发起搜索、平台返回失败，程序可以直接记。哪些话值得以后再想起、是否构成稳定偏好，则让模型提出候选。来源、人物身份、时间、已读及写入权限由服务检查。这延续既定 03/05，不是重新定义一套与它们并列的事实系统。

在 B 站例子中，搜索工具的请求词、时间、视频对象和读取范围可以产生 Event；是否把“我觉得这个剪辑很有意思”保留成以后可回想的印象，需要另作选择。没有要求把整个评论区、所有 HTTP 重试和全部工具返回都塞进聊天记忆。人物可以在未对用户复述时，记住自己实际接触过的内容；也不能只因工具执行过，就默认模型看到了完整结果。

## 4. 从收件到提取：具体谁做、什么时候做

### 4.1 收件时只记录机械事实

入口在一个数据库事务内保存消息、收件项和收件事件。防重键沿用本答复集04的 `(channel, account_binding, external_id_scope, external_message_id)`：平台消息 ID 如果只在某个会话内唯一，`external_id_scope` 必须包含该会话；不能一律假定账号下全局唯一。没有平台稳定 ID 的渠道，需要适配器根据其真实投递契约提供稳定接收键并说明局限；不能拿正文相同当作同一消息。

此时不调用记忆模型、不生成摘要、不根据正文建语义向量、不更新情绪。否则“10:30 再看”只剩 UI 效果，后台在 10:00 已偷偷理解完了。

### 4.2 人物读取以后才开放语义处理

首次接触使用现行03的许可与 Exposure 机制：读取工具选择材料；适配器保存最终请求的 ID、版本、片段、hash；收到相应有效模型输出或可核实处理回执，才确认提供。未知网络结果保持未知，不拿取出正文的时间冒充人物阅读时间。

**这里会约束自动检索。** 如果 m1 尚未确认提供，不能提前用 m1 正文调用另一个模型“生成回忆查询”，也不能提前算语义向量去查记忆。第一步可以提供人物当前条件、此前已知的同对象历史和获准首次读取的 m1；人物模型读到以后可以提出 `memory.search`。确认本次 Exposure 后，宿主再执行该检索工具。后续同 run 的已知消息则可用于预检索。这不是强迫每条聊天多调用一次模型：需要查时才有工具往返，不需要查时可直接形成回复。

### 4.3 提取任务何时建立

建议使用三个明确入口，避免只有“聊天彻底结束”才能记忆：

1. 一次对外表达获得可核实的发送结果时，按结果建立相应提取任务。**回复可靠保存只证明产生过草稿，不证明已经说给对方听。**
2. 新来信已确认提供，但本次决定不回复/延后处理时，可以独立建立来信提取任务；无需等待出站成功。
3. 一份工具观察已真正提供给人物后，人物明确要求记住它，或相应观察处理步骤结束时，建立观察提取任务。

出站材料使用下表，不能统称为“本轮对话已完成”：

| 出站状态 | 可以作为哪种来源 | 不得推断什么 |
| --- | --- | --- |
| 草稿已保存、出站检查失败、仅排队 | 草稿/失败/排队的机械事件；若确有业务需要，可另作内在计划材料 | 不进入“她对甲说过”的对话来源，不形成“甲已知/已同意” |
| `sent` | 适配器已核实的已发送正文；保留该平台的确认依据 | 不能只凭本地提交就标 sent；sent 不证明已送达或已读 |
| `delivered` | 已发送正文及平台可核实的送达状态 | 送达不证明对方看过、理解、同意 |
| `unknown` | 发送尝试及结果未知这一事件；正文如需引用必须标“发送是否成功未知” | 不进入已确认表达集合，不为了让记忆完整而猜成已说或重发 |

例如人物回复草稿写“周末一起去”，但出站检查拒绝，这不能变成双方约定。甲的来信若已 Exposure，仍可单独提取“甲提出周末见面”。稍后发送结果从 unknown 变为 sent，是新确认的一项材料，不能倒改旧任务的输入。

任务按**稳定批次**组织：唯一键建议为 `person_id + logical_step_id + purpose + extractor_version + batch_id`。采集阶段可以积累尚未封存的材料；入队前封存本批 `source_manifest`，领取后不得追加或换掉来源。每份清单分开记录本批新增的 `new_source_revisions`、仅用于理解的 `background_refs`，以及覆盖的来源序号/状态修订。`batch_id` 在重试时不变；每次模型调用另有 `attempt_id`。同批三次重试仍是一件事。

后续新消息、送达回执或工具观察进入新的批次，不撞用旧唯一键。覆盖游标只在本批处理结果提交成功后推进；采用按范围分区的来源序号与已处理清单，不能跳过失败/尚未处理的空洞。无值得保留的候选也可以记录“已处理但不提取”，而不是反复重读。复用的旧背景不占新增覆盖量，不因为再次送入模型就算一段新经历。来源撤销等使封存清单失效时，取消该批并明确记录未处理项；合法剩余项另建后续批次，不能偷偷改写正在重试的任务身份。
显式日程变更、给甲的承诺、平台发布成功等具有即时业务后果的写入，继续由本 run 的领域工具处理，**不等待后台记忆提取才生效**。

### 4.4 谁组织提取模型的输入

我方 `MemoryExtractionWorker` 领取持久任务，向 `SourceResolver` 取得本任务允许读取的原文和来源头，再调用 LangMem 的无存储 `create_memory_manager`。这里的名字是拟议模块，不是已有实现。

输入不是一段不分来源的聊天大串，而是：

```text
来源 m1：用户甲的原话；周一10:00发出；10:31已提供；contact:甲
来源 a1：已核实发送的回复正文；状态 sent及适配器确认依据；尚无送达/已读依据；contact:甲
已有记忆 mem_old:v3：甲以前说过某事；原始来源 m0:v1；scope与权限版本一并记录
处理目标：只提出与这些来源有关、未来可能有用的记忆候选
```

现有记忆的 ID、版本、范围、权限以及它依赖的原始来源，组成这次模型调用的读取依赖清单。若旧总结还引用另一个总结，服务沿来源关联追到原话/观察/事件，并保留对应版本；不能把摘要层层相传当成多份独立证据。新材料清单封存不等于可以省略这些旧材料的版本检查。

服务给的现有记忆也必须属于本次允许的范围。不能为了“对齐全局画像”，把乙、丙全部私聊交给这次整理器。跨联系人查询得到的材料带原来源标签；它们不是甲刚说的新话，不能再次提取成与甲的共同经历。

## 5. 模型候选与真正保存之间，还有一道具体的提交过程

### 5.1 候选结构

以下是**我方拟议结构**，不是声称某库已经具备这些字段。它刻意不给模型设置 `person_id`、`counterpart_id`、`exposed_at`、`verified=true` 的权力；这些由任务和服务绑定。

```json
{
  "operation": "propose_new",
  "summary": "甲周一说近期项目赶进度，经常加班。",
  "meaning": "reported",
  "source_refs": [
    {"source_id": "m1", "revision": 1, "quote": "最近项目上线，天天加班"}
  ],
  "relevant_time": {"from": "2026-10-26", "until": null, "precision": "recent_unspecified"},
  "use_as": "recent_context",
  "why_keep": "后续谈工作近况时有用",
  "supersedes_candidate_id": null
}
```

如果模型从几轮话中猜测“甲可能工作压力比较大”，`meaning` 应为 `inferred`，来源仍指向具体原话；不能因它给出一个 0.95 就变成核实事实。`until=null` 不表示“永远正在加班”，只是来源没给结束时间。

LangMem 默认 `Memory` 只有 `content`；`ExtractedMemory` 是 `id + content`。因此来源字段必须由我们的候选 schema 扩充，而**模型返回了 source_id 不等于它真的有这个来源**。框架支持自定义 Pydantic schema，但这只是输出结构能力，没有替我们完成来源真实性校验。[^lm-shape]

### 5.2 服务实际检查什么

| 检查 | 失败时如何处理 |
| --- | --- |
| 引用 ID/版本确实在本任务允许的材料集合内 | 拒收该候选，记录具体无效引用；不能让模型引用任意全库 ID |
| 来信/外部观察已确认 Exposure，且未删除/撤权；出站按实际结果分类 | 失效批停止并记录原因，合法剩余项另建批；未知发送不升级为已表达 |
| 引文确实存在于所引版本；片段范围可核验 | 引文不符就拒收；引文存在仅证明出处，不自动证明总结准确 |
| 候选意义和来源角色相容 | 只有助手自述不能直接变成共享已发生事实；用户陈述不能改写人物底稿、日程或排他承诺 |
| 所属人物、联系人、群由服务从来源推导 | 不能让模型把 `contact:甲` 改写成 `character`；混合来源的候选需拆分或保留受限范围 |
| 每个既有记忆及更正目标的 ID、版本、权限与原始来源仍有效 | 每个目标分别做版本条件写入（CAS）；任一读取依赖变更就放弃本次结果，重新读取后再提取，不能静默覆盖 |
| 合并总结保留仍支持新结论的旧原始来源 | 例如合并周一和周三的工作近况，应同时保留 m1、m3；不能只挂最新 m3，也不能把 mem_old 本身算作独立证据 |
| 总结语义足够受来源支持 | 不支持、矛盾或推断跨度大的候选留作暂定/拒收；需要模型复核时同样只送合法来源，不能声称字符串校验能判断全部语义 |

“是否重要”仍由模型依据任务和上下文提出；服务不靠固定词汇表规定人物只能记什么。服务检查的是**这份候选有没有资格这样保存**，不是代替她决定喜欢谁、想聊什么。

### 5.3 一个可执行的保存顺序

```python
# 伪代码；说明职责，不是本轮新增的可运行代码
job = claim_sealed_batch()  # 固定 batch_id、新来源版本清单、背景清单和覆盖范围
sources = resolve_allowed_sources(job.source_manifest)
existing = retrieve_existing_candidates(job.scope, sources)
read_set = snapshot_read_dependencies(
    sources, existing,
    include_memory_id_revision=True,
    include_transitive_original_sources=True,
    include_permissions_exposure_and_send_evidence=True,
)
attempt = save_attempt_manifest(job.id, read_set)
recheck_before_model_dispatch(attempt)  # 调用前已撤权/失效的内容不继续外发
proposals = await langmem_manager.ainvoke({
    "messages": format_sources(sources, new_vs_background=True),
    "existing": format_existing_with_original_provenance(existing, read_set),
    "max_steps": 1,
})

# 模型调用期间不持有数据库事务锁；提交时锁定/核验实际读取依赖
with transaction():
    lock_batch_and_read_dependencies(job.id, read_set)
    if batch_already_committed(job.id):
        return saved_batch_result(job.id)
    recheck_every_source_revision_permission_exposure_and_send_state(read_set)
    recheck_every_existing_memory_id_revision_and_scope(read_set)
    for proposal in proposals:
        checked = validate_references_meaning_and_scope(proposal, job, read_set)
        original_refs = validate_supporting_original_refs(
            checked.new_refs,
            checked.retained_old_refs,  # 从旧来源集合选择仍支持新总结的原始材料
            read_set,
        )
        # 旧摘要可帮助定位，但不是独立证据；不能丢掉支撑合并结论的旧原话
        if checked.target_memory_id is not None:
            target = checked.target_memory_id
            assert_target_allowed(target, read_set)
            revision = append_revision_and_cas_current(
                target, expected_revision=read_set.memory_versions[target],
                content=checked.content,
            )  # 每条目标独立校验；同一批不能重复更新同一目标
        else:
            revision = append_new_memory(checked, batch_candidate_key=checked.key)
        append_memory_sources(revision, original_refs)
        enqueue_index_projection(revision.id, revision.number)  # 与正文同事务
    mark_batch_committed(job.id, attempt.id)
    advance_covered_sources_without_skipping_gaps(job.coverage_manifest)
```

这里的 CAS 是“当前版本仍等于本次模型读取的版本，才允许追加并更新当前指针”。不是用一个全局 `expected_previous_revision` 检查全部记忆。目标版本、来源或权限改变时，事务回滚；重试沿用本批身份及新来源清单，重新建立一次现有记忆读取快照与模型尝试。若本批新来源本身已撤销，则按§4.3取消/重排，不能把被撤材料藏在旧摘要中继续用。

例如模型读了 `mem_work:v3`（依赖周一 m1），并结合周三 m3产生合并建议；提交前另一 worker已写入 v4或m1被删除，本次就不能直接保存。即使版本没变，新总结仍保留周一的判断，也要把 m1 与 m3都挂入新版本，不能只记录 m3。仅仅引用旧摘要 ID会使之后删除m1时漏掉这份新总结。

建议先配置 `enable_updates=False`、`enable_deletes=False`，让 LangMem 返回候选；需要更正时用自定义候选 schema 的 `supersedes_candidate_id` 和目标版本引用表达建议，再由服务追加修订。库不会因此保证模型自动理解这种更正协议：先用 fake 模型覆盖解析/版本冲突/来源保存，再用真实模型检验会不会提出正确更正；未通过前不能宣称这个组合已可用。目标 expected revision 最终以服务读取快照为准，不信任模型自行填写的数字。这里使用的是上游已有选项，不改上游代码中的提示词；schema 与必要任务胶水单列并留版本。现有记忆传入仅作比较材料；返回结果中未变化的既有对象不应再次写作新记忆。[^lm-manager]

保存成功依据数据库已提交的版本与来源关联，而不是模型说“已记住”，也不是向量返回了一串 ID。响应含 `memory_id/revision/persistence_status/index_status`；索引未完成明确是 `pending`。

### 5.4 哪些表承担什么职责

延续既有03数据语义，不在这里重列全部表。为接通本链，至少需要补齐以下关联：

| 记录 | 最小目的 |
| --- | --- |
| `memory_extraction_job` | 稳定 batch_id与唯一键、封存的新来源/背景清单、来源覆盖游标；每次 attempt记录既有记忆ID/版本及传递原始来源读取依赖；模型/提示版本、状态、失败原因 |
| `memory` / `memory_revision` | 当前版本指针与不可静默覆盖的候选/有效/失效版本；保留 reported/inferred 等含义 |
| `memory_source` | 某个记忆版本依赖哪些原始消息、观察、事件及其版本/片段 |
| `memory_index_job` | 按记忆版本建立/移除派生索引的 outbox任务；绑定预期版本、权限修订及删除代次，执行/重试前与落索引前复核 |
| `retrieval_record` | 查询的范围、时间、候选、被选中项、被排除原因、降级状态 |
| `model_input_manifest` | 最终进入某次模型请求的材料版本/片段/hash，与请求确认状态对应 |

来源表与记忆正文先提交；Postgres Store 的文档/向量随后按 `memory_id:revision` 建立。即使两者在同一个 PostgreSQL 实例里，也不假定跨库 API 自动构成一个业务事务。Store 只是重建得出的查询副本，丢失时可从有效记忆重建；原始消息、事件、来源和事实权限没有因此迁进它的通用 JSON 文档。

## 6. 去重、更正、删除不是“让模型覆盖一下”

**同一个任务重跑：** 唯一任务键和提交记录挡住重复保存。因为模型每次可能换一种措辞，不能只靠向量相似度防重。

**同一原话被多次总结：** 记忆来源组合相同，不增加“独立证据数量”。新摘要可成为新修订，但不把重复总结当作甲又表达了一次偏好。

**同一件事在新消息里又说了一次：** 新来源 ID 不等于新经历。例如甲周三再次提到周一那场会议，候选比较要结合主体、事项和适用时间；可建议合并并保留两条原话来源，目标带旧版本，仍须通过上述检查。反过来，两周都有相同周会，可以是两次真实经历，不能因措辞相同一律合并。语义判断由模型提出且允许拒绝/暂缓合并；服务保留原始来源和更正路径。重复谈论同一关系事件也不能当作事件又发生一次或自动累计关系证据；记忆合并本身不负责给关系加分。

**周四更正项目延期：** 原始周一消息仍在；新 Claim 记录“甲周四这样纠正”。服务将旧记忆版本标为不再可用的当前总结，追加修订并建立索引更新任务。若更正只是“这周延期”，不能自动判定过去所有“加班”均为假。比较主体、事项和适用时间，不用一句全局“更新的总是对的”。

**检索副本更新慢：** 从向量检索拿到旧 `mem1:v1` 时，结果必须回查当前数据库版本。已失效、撤回或删除就不进模型输入；如果没有足够候选，扩大合法集合的候选数或降级到关键词，不把过滤后空集解释为“过去从没聊过”。

**删除来源：** 先在权威库标记不可再读，立即挡住检索与下一次发送；再依 `memory_source` 找到所有派生记忆、索引、摘要和缓存，移除或从剩余有效来源重算。仅删除原文行不会自动删除摘要里的名字和内容。旧 checkpoint/输入快照也可能留正文；具体使用[01的checkpoint删除与恢复方案](01-Agent承载基础怎么选.md#checkpoint中的正文怎样删除而不是只在查询时藏起来)，按来源依赖找受影响thread并作废generation，使用上游粗粒度清理入口。不能假称框架有按source_id直接删除全部checkpoint正文的API。已经发送给外部接收方或模型提供方的内容不能通过本地删除变成“对方没收到过”，须明确保留范围和实际执行结果。

**延迟索引任务不能绕过删除：** 权威库删除记录（tombstone）、记忆当前版本、来源权限修订共同决定任务是否仍有效。每次领取、重试以及真正发出 embedding请求前，都重新检查，不能拿数小时前封存的正文直接调用 embedding。外发前的检查与向网络提交必须和删除入口处在同一串行协调中，仅登记“待发”不算已经外发：若删除先完成，这个旧任务不得发出新请求；也不得让Store在不经检查的自动embedding路径旁路发出。索引内容绑定具体记忆版本，旧任务不具备恢复当前版本或清除tombstone的权力。

若 embedding请求已交给网络后才发生删除，不能声称撤回已外发的正文。可尝试取消，但记录仍为“已经外发/结果待定”；结果返回后再次检查并丢弃，不保存为可用索引、不再次网络重试。删除流程要能列出这种在途请求和外部保留边界。

写入检索副本同样存在竞争，不能只“检查一次再upsert”。建议由每条记忆的串行投影写入器处理建立、替换和删除，与权威删除代次协调：开始写入前再次核验预期版本和tombstone；若旧upsert已在途，立即用权威库过滤挡住读取，等待其确定结果后补删，并在清理确认前保留 `cleanup_pending`。跨Store API没有事务时，不能把临时物理旧副本宣称已经不存在。完成后旧任务重试仍因版本/删除代次不符被拒绝，因此不能复活成可读记忆。该协调与清理是我方必须实现和故障测试的部分，并非 LangGraph Store 已提供这套领域保证。

提取模型的外发也遵循同一原则：调用前能发现的撤权必须阻止；已经外发后发生撤权，拒绝保存衍生结果并记录实际外发事实，不假称模型供应方从未接触材料。

这是本项目来源依赖的必需适配，三个候选都不能凭“有 delete API”宣称已完成整条删除链。Graphiti 在当前 `remove_episode` 中会剥离该 episode 对边的支持，保留仍有其他 episode 支持的边，并重建存活实体摘要；但重建异常会记录错误，不能将这条函数视为我们所有副本删除均完成的证明。[^g-delete] Tencent 的单条 L0 删除只在该路径删除 L0 元数据/向量/FTS；另有整份 memory clear 删除多层，不能把单条原话删除等同于对其所有 L1/L2/L3 推断做了来源级重算。[^t-delete]

## 7. 后来又聊到工作，怎样真正想起旧事

### 7.1 不只有“模型自己想起来才查”

建议分成三条读路径：

| 路径 | 谁触发 | 实际做什么 |
| --- | --- | --- |
| 必要当前条件 | 每次有新决策输入时由程序准备 | 人物当前处境、关系、未完成责任等按 ID/时间查询；不依赖向量 |
| 已知当前话题的预检索 | 已确认提供的新消息、当前任务目标或已知指代改变时 | 用当前联系人和这些合法材料形成查询；找少量可能相关旧事 |
| 主动补查 | 人物模型提出具体工具调用 | 指定对象/主题/时间/资源，再查；不够时可取原话或扩大合法范围 |

同一 run 正在工具循环里时，已确认提供的消息、检索结果和自身工具调用沿当前上下文继续保留；不能每次返回工具结果就丢掉它们，重新只拼“当前条件 + 最近几句 + top-k”。模型窗口不够时，压缩方案另外处理；压缩仍须保留来源索引和正在做的事。

### 7.2 贯穿例子的检索

周三 19:00 的“今天总算能早点走了”已进入人物本次处理后，模型或背景检索器可以生成：

```json
{
  "scope": "current_contact",
  "query": "近期工作加班、项目进度、为什么今天能早走",
  "time_window": {"from": "2026-10-19", "to": "2026-10-28"},
  "wanted_kinds": ["reported", "inferred", "conversation"],
  "limit": 8
}
```

日期区间是示例，不是所有聊天都硬查最近九天。查询器只能建议条件，最终可读集合由服务从 run 和明确查询意图构造，模型不能自行填 `all_users=true` 逃过范围校验。

执行顺序建议为：

1. 根据 `person_id`、当前联系人或本次明确扩大范围、材料权限/Exposure/删除状态，确定合法集合。
2. 若有资源/事项/明确日期，先查结构化记录；未履行约定优先保留。
3. 对合法集合做关键词检索与语义检索；融合排序、按来源去重，回查版本与时间含义。
4. 截取少量候选，保留原始来源入口、时间和 `reported/inferred`。不能只返回一句脱离语境的“甲工作压力大”。
5. 模型认为需要原话时，通过来源读取工具取得对应片段；权限不因知道 ID 而放开。

建议原始关键词路径先用 PostgreSQL 的结构化过滤及可核查的词句匹配实现，必要时加中文分词/检索扩展；Postgres Store 提供语义召回。**Postgres Store 的 `query` 并不是现成的中文 BM25**，没有向量配置时也不能把它当完整关键词引擎。两条召回能力分别测试，不能写了“混合”两个字就算已经实现。[^pg-search]

首轮实验可先每路取 20 条、融合后最多 8 条，正文限额单独配置；这些只是便于验证漏检和误检的起点，未测过，不能当作用户决定或经验最优值。若检索超时，仍可用已知原话和必要条件继续；不得把检索异常静默包装成“没有相关经历”。

### 7.3 跨联系人回想怎样保留灵活性

继续遵守 U20/D21：默认当前联系人；人物可明确选择其他联系人，或按主题查询自己全部已知记忆。这里扩大的是**内部回想目标**，不是发送对象，也不是把全部私聊汇进总摘要。

例如甲聊到加班，她主动想起乙也说过换工作：工具内部结果保留乙的真实 ID、名字、发生/获知时间、来源及保密属性，用于准确定位。但结果附明“来源联系人与接收人不同；对外不得输出该用户姓名、昵称、账号名；保密内容不能因换称呼而分享”。模型决定自然代称，出站检查继续兜底禁名；TTS 使用同一已检查正文，不能从原始工具返回另取文本。

这不能由 Graphiti 的 `group_id`、Tencent 的 `user_id` 或 LangMem 的 namespace 自动解决。它们是分区/定位工具，**没有哪一个字段天然表示‘人物内部可以想起，但此刻不能对这个人点名’**。如果来源混合多个联系人，出站检查要保留全部来源对象；不能合并完摘要后丢掉来源列表。

同理，检索到乙的事情不写回“甲参与过此事”，也不为甲建立看过完整乙原话的知情记录。只有实际对甲说出的允许部分，才形成这次表达/送达记录。

### 7.4 怎样证明真正放进了模型输入

需要保留三个不同的结果：

- `retrieval_record`：检索返回了哪些候选。
- `model_input_manifest`：预算和格式整理后，最终发给哪次请求的哪些材料、版本和片段。
- `Exposure`/请求结果：是否确认本次材料进入模型处理；不等于它真的记住或正确使用。

示例内部材料块：

```text
相关旧事 mem1:v1；来源 m1；人物已知；属于 contact:甲
原话时间：周一10:00；本轮当前时间：周三19:00
含义：甲当时自述，不是外部核实
材料：甲说近期项目上线、经常加班；没有已知结束时间
不可据此断言：甲现在仍在会议中、项目已经完成
```

假如预算最终只留了 mem1，mem2 虽然在召回结果里，却不能在清单中标为“已提供”。若模型调用失败、仅完成组装，记录 `prepared`，不宣称“模型读到了记忆”。这也让回归能够问清：这次答错是根本没查到、查到后被裁掉，还是提供以后模型理解错了。

## 8. 三个开源候选的实际取舍

### 8.1 Graphiti：长于时间关系图，不负责我们的人物事实资格

它的主线是 `add_episode` 接收正文、来源说明、参考时间和 `group_id`，读取同分区的近期 episode 作为背景，调用实体抽取、实体消歧、关系抽取/去重/冲突判断、属性与摘要提取，最后保存 episode、节点和边。单条入口明确建议按顺序等待摄入；这说明摄入不是“插一行向量”那么简单。[^g-ingest]

`EpisodicNode` 保留原始 `content`，`EntityEdge` 保留所依赖 `episodes`、`valid_at`、`invalid_at`、`expired_at` 等时间。新关系与旧关系是否冲突，先由模型从候选中判断，再由程序结合时间界限使相关边失效。搜索支持关键词、向量及可选图遍历/重排；直接 `search` 返回的是关系边，人物对话如何使用它仍由宿主完成。[^g-data][^g-resolve][^g-search]

值得采用的思路：把“原始材料时间”“处理/失效时间”“关系适用时间”分开；关系边能回溯产生它的材料。不能照搬为事实权威：用户说“你答应做我女朋友了”如果进入一般关系抽取流程，**图中抽出一条关系只是模型对这句话的解释**，没有证明人物真实承诺过。必须先保留 reported 与来源，并由我方领域记录判断是否真的成立。

对我们而言还需要：摄入前 Exposure/权限筛选；人物×联系人分区约定；更正权威；跨分区明确查询；原话读取与出站禁名；派生图删除及重建。默认 `previous_episode_uuids=None` 会由库查本组近期材料，若把全人物所有用户放同一 group，就有不合时宜的跨人混入风险；全部拆开又需要自行组合跨联系人和公共人生图。[^g-ingest]

核查驱动包括 Neo4j、FalkorDB、Kuzu、Neptune，没有发现现成 PostgreSQL 图驱动。新增图库意味着双写、恢复和监控成本；实体抽取/消歧/关系冲突/摘要也有多次模型及 embedding 开销，具体数量随内容变化。本轮没有测试，不能据宣传给每条消息报固定费用。[^g-driver]

**建议：保留为后续图检索实验候选，不作为首版唯一存储。** 优先证明普通联系人历史与工作/兴趣话题召回；只有关系图查询带来实际收益时，再增加部署复杂度。

### 8.2 TencentDB Agent Memory：链条较完整，L2/L3共享范围需要改造

核查到的具体过程是：L0 保存对话；L1 提取器从新消息与少量背景抽取场景和原子记忆；随后查既有候选，由模型给出 store/update/merge/skip；写入 L1；工作器还具有 L1→L2→L3 的级联处理。记忆带 `source_message_ids`、时间和版本，查询有 FTS/向量融合及降级，具备可借鉴的工程链条。[^t-extract][^t-search][^t-worker]

不过有四处不能直接沿用：

1. **L2/L3 的归属。** `buildProfileIsolationScope` 使用 `teamId || userId || "default"` 与 agentId：存在 team 时，同 team/agent 的不同用户会聚合；没有 team 时则回退到 userId，不能说任何配置都混合所有用户。session/task不参与该画像范围。Proxy 的实际实现把 L3 全文和 L2 场景路径/摘要直接放入 system；L2 正文按需读，L0/L1 由工具查。这适合共享工作经验，不适合未经改造就把多人的私聊汇入共享人物画像。不是否认它有隔离，而是隔离的目标不同。[^t-profile][^t-inject]
2. **保存语义。** `writeMemory` 在更新/合并时先移除旧检索记录，再追加 JSONL、写新检索记录。JSONL 失败可继续，向量/存储失败也被捕获；`upsertL1=false` 只记录日志，函数仍可能返回 record。不能把返回 record 当作我们要求的“权威正文与来源已可靠提交”，更不能把这条路径当跨两个存储的原子事务。[^t-write]
3. **默认身份的风险。** 核查的 `assertIsolation` 函数注释说缺维度会拒绝，但函数体对缺失字段填入 default；这不等于证明所有网关入口都绕过鉴权，却足以说明我们不能只看注释，或直接复用它作人物范围的最后防线。[^t-isolation]
4. **消息与指令的区别。** 它提取工作指令、经验、Skill 等对 coding Agent 合理；人物聊天不应因为用户说“忘了你的人设”就把它升级成全局指导。当前库需要由外层决定哪些来源允许进入哪种材料，不能透传自动资产化。也未核查到现成的 Exposure 首次提供与跨联系人禁名语义。

删除方面，单条 L0/L1、整份多层 clear 都有实现，但来源级撤回后全部派生总结是否重建，仍须另外核实；更正审计结构还明确不保存历史 content/旧值，不能充当我们完整的版本来源账本。[^t-delete][^t-audit]

后端工厂目前包含 SQLite、腾讯向量库和 MongoDB；接 Python 可经 HTTP 调它，但并非直接嵌入现有 PostgreSQL 的 Python 库。额外服务、分层提取模型和可选嵌入都有成本；本轮未安装或压测。[^t-backends]

**建议：借鉴分层、提取来源和降级可见性，不整体接入 Proxy/画像链。** 若以后需要跨开发 Agent 的工作记忆管理，它的适配价值会更大；我们本轮判断的是人物主体，而不是评价它一般用途的好坏。

### 8.3 LangMem：更适合拆出候选提取，不能直接启用自动写库

LangMem 有两个容易混淆的入口：

- `create_memory_manager` 返回 `MemoryManager`：输入 messages 和可选 existing，调用 Trustcall 结构化提取/修订，返回 `ExtractedMemory`；其 `ainvoke` 本身没有把这些结果写进 Store。注释中关于“自动持久化”的泛化说法应以函数实际行为为准。[^lm-manager]
- `create_memory_store_manager`：先找相近记忆，再调用上面的 manager，最后 `store.aput/adelete`，会直接执行改写。`create_manage_memory_tool` 也直接调用 store 写入/删除。这两个入口若不加领域约束，不适合让人物直接覆盖来源和旧认识。[^lm-auto]

**推荐复用第一个。** 它能够接受我们自己的结构化候选 schema，不要求先把整个 Agent 改成某个预制聊天循环。源代码依赖 LangChain、LangGraph、Trustcall 等，因此它不是零依赖的小函数；但与本轮评估的 Python/LangGraph 路线相容，比另启一套团队记忆网关更直接。[^lm-deps]

取用端，库提供主动搜索工具和可用模型生成多个查询的 `create_memory_searcher`；这些证明“模型形成检索词 → 调 Store → 返回候选”已有可复用机制。我们仍需在工具外绑定人物/联系人及已知范围，并处理准确时间/资源查询、原话与出站规则，不能裸露任意 namespace 给模型。[^lm-search]

**提示词处理必须遵守原文复用要求。** LangMem 默认提示鼓励归纳、压缩、推断和更新，未定义我们需要的事实层级、来源资格及未读边界。本文只推荐代码机制，不把这段默认提示词自动认定为已获准使用的核心提示词。后续若试用它，必须原样保存固定版本/hash，单独加入 schema/来源契约胶水并验证是否冲突；确实不适合则整段停用，明确记录改为我方持久化任务指令，不能偷偷改写后仍说“照搬了社区原提示词”。人物自身的核心表达提示词与这份后台提取任务指令分开，不用记忆框架顺便重写人物性格。[^lm-prompt]

### 8.4 为什么 Postgres Store 仍只作副本

其表是 `(prefix, key, value jsonb, created_at, updated_at)`，可选向量表按同一 key 关联，namespace 和 JSON filter 帮助搜索，提供持久化与 pgvector 能力。它不自带我们的 `source_ids` 外键、Exposure、报称/观察区分、旧版更正与其他用户禁名。[^pg-store]

所以可以用它存 `memory_id:revision` 对应的可召回摘要及内部过滤字段，读取后回权威表核验。来源/事实/业务提交继续在领域表完成。这样以后换 Graphiti 或其他索引，不需要迁走人物的原始人生；代价是一次索引投影和读回核验，收益是我们不会被任一记忆库的自动总结当成事实来源。

## 9. 怎样验证这条链，不再只写“有记忆功能”

以下是待执行的验证，不是已通过结果。先用脚本化模型结果测试服务边界，再获准运行真实模型，最后人工阅读聊天效果；测试输入使用独立明确标注的数据。

| 验证 | 必须看见的证据 |
| --- | --- |
| 10:00 收到、10:30才看 | 10:30 前有 Message/Event，但任何语义提取、embedding请求、情绪/画像调用均没有该正文；首次获准模型请求例外按现行契约确认 |
| 提取“甲近期加班” | 任务清单→模型候选→受检来源→提交记忆版本→索引状态可逐项串回；不能只有一句摘要 |
| 编造 source_id/引文 | 服务拒绝，不进入有效记忆；原任务与拒绝原因可查 |
| 回复草稿写“周末一起去”但检查失败/仅排队/发送unknown | 不出现已表达、对方已知或已约定记忆；甲的已Exposure来信仍可单独提取；sent/delivered也不冒充已读 |
| 助手确已发送“刚买咖啡”却无生活/工具依据 | 能查到她发过这句话，但不能检索成“已发生共享经历”；若只是草稿，连“说过”也不成立 |
| 同平台不同会话恰有相同消息ID | 按适配器声明的ID作用域分别收件，重投相同作用域的同ID才防重 |
| 同批重试三次，领取后又来一条新材料 | 旧batch身份/manifest不变；新材料进入后续批；覆盖游标不越过失败批；背景不算新经历 |
| 模型读取mem:v3后另一worker更新到v4或原来源撤销 | 提交逐条CAS/读取依赖检查失败，旧结果不写入；重试重新读取；合并成功时保留仍支撑结论的旧原始来源 |
| 向量失败 | 原文/记忆已提交；索引待重试；关键词或结构化降级可见；不报告整体丢失，也不假称语义可查 |
| 周三“今天总算能早点走” | 有关加班旧话能被话题检索找到，实际请求清单含相应记忆；结果仍标自述和时间 |
| 周四更正 | 旧版本即使仍在向量候选里也不以当前事实进入请求；历史原话可解释；自定义更正候选同时经过fake结构测试与真实模型语义验证 |
| 新消息重复谈周一会议，与下周另一次周会 | 前者可合并并增加原始出处，不增加经历/关系次数；后者可保留为新经历；歧义可不合并，不能只凭source_set或文字相似度硬判 |
| 删除一条来源 | 相关摘要/索引/可恢复上下文不能继续带出已删内容；多来源材料按剩余来源重算，而不一刀切伪造历史 |
| 删除后延迟索引任务才执行或重试 | 旧任务在外发前被版本/权限/tombstone检查拒绝，无新embedding请求、无旧版本复活 |
| embedding或upsert在途时删除 | 已外发请求如实留记录，返回结果丢弃；旧物理副本补删且全过程不可读，清理未确认不宣称删除完成；不得因重试再次外发已删正文 |
| 甲乙同时聊同一视频 | 默认各取各的私聊；明确跨人回想可查，但对外无另一个用户姓名/昵称/TTS泄漏，写回不制造共同经历 |
| 检索没找到 | 区分不存在、未索引、被权限排除、工具失败、预算裁掉；不一律让角色说“我忘了” |
| 同 run 多次工具调用 | 此前已提供原话/结果仍在或有可查压缩，不退回只剩最近几句；确认窗口压缩与记忆提取不是同一功能 |

话题检索需要一个小型人工标注集：每个测试问题指定应召回的原始来源、允许但非必需的来源、绝不能召回的来源；覆盖同义措辞、时间更正、同名联系人、长历史、中文口语及隐含指代。分别记录“候选召回”“实际入窗”“回答是否依据正确”三项。首次未达标时判断是提取漏了、检索漏了还是入窗被裁，不直接换提示词掩盖服务断链。

本轮没有跑这些测试，因此不能给出准确率、最佳 top-k、模型成本或“已成熟适配”的结论。用户要求的自然交流效果还需真实模型与人读评估；检索命中率高不等于人物说话自然。

## 10. 自查：这个建议有没有偏离愿望

- **时间是主线，材料零散可组合：** 原文、事件、计划和记忆仍各存，检索按时间/对象/主题组合，没有重新要求事件挂在日程下。
- **同一个人物面对多人：** 共用真实生活条件，私聊记忆分别保存；允许有明确目标的跨联系人回想，不靠一份全局画像把所有人混起来。
- **自主不看消息必须真实：** 提取、embedding、后台查询词生成都纳入 Exposure 边界，不能偷跑。
- **用户能影响人物与公开生活：** 甲提供资源、人物尝试、形成作品和公开结果之间可用来源连接；公开作品不因此附带甲的私密来由。记忆帮助回想，不替代真实行动。
- **模型负责理解与选择：** 模型决定哪些材料值得记、何时主动补查、怎样自然回应；服务阻止伪造来源、越界修改和已删内容复活。没有用模型提取结果替代领域事实。
- **复用开源，不假称直接满足：** 明确使用 LangMem 候选机制和 LangGraph Store，借鉴 Graphiti/Tencent 的时间、分层和检索；项目特有来源/权限仍须适配。默认提示词未擅自改写，部署和效果未假称通过。

本建议最大的代价，是我们仍需维护一层来源/权限/版本服务，不能只接一个 `memory.add` 就结束。但这层服务直接对应已确认的愿望和担忧；若省去它，库会更容易接上，却重新出现“随口编出的经历被保存”“未读先分析”“所有人的私聊变成一个总画像”的问题。
