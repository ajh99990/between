# 管理员内容编辑调研

调研日期：2026-10-16。本文为后台重写提供交互和字段约束；源码核验不代表已经完成浏览器体验验收。

## 结论

Between 的核心工作是查找一份角色或世界书、读完全文、修改具体字段、确认服务器保存成功。入口应围绕角色库和世界书建立内容工作区；列表用于选择，正文用于阅读，编辑器用于修改，来源和生效范围随内容可查。

SillyTavern 值得借鉴的是字段分组、长文本放大、条目目录、正文搜索及触发配置的结构，不能直接移植其保存机制。它的世界书普通保存会延迟发请求，默认调用返回不等于服务器已确认；Between 已有的显式保存、配置版本检查与新会话快照应继续作为产品约束。[^st-wi-save][^between-api]

字段完整性比页面是否像酒馆更重要。角色有 11 个正文字段；世界书既可能是 `keys/content` 单条模式，也可能包含 `entries`。已有条目的 UID、未知元数据、来源归因、`null` 继承值和未编辑字段必须保留。不能把“表单没展示”解释为“保存时可以丢弃”。[^between-types][^between-books]

## SillyTavern：能借鉴什么，证据在哪里

### 角色不是一个“提示词”输入框

ST 把描述、性格、场景、开场白、示例对话、系统提示词、历史后指令和作者备注分别存储和编辑；多个长字段有放大编辑入口。其角色搜索也覆盖描述、示例、场景、性格、开场白、作者备注等正文，而非只搜索名字。[^st-character][^st-html][^st-search]

因此角色列表可以只显示公开简介，但进入详情必须完整呈现全部正文，并允许从字段目录直接定位。对 `{{char}}`、`{{user}}`、`<START>` 等原始文本保留换行和字符，阅读时不能先执行模板或把原始 HTML 当作页面插入。

Between 的字段名与 ST 不完全相同。例如 `Role.detail` 才映射到模型角色描述，`Role.description` 是应用公开简介；`Role.persona` 是默认用户身份。字段标注应以 Between 实际写入者和读者为准。[^between-role]

### 世界书需要“条目索引 + 完整正文 + 条件”

ST 的 `displayWorldEntries` 在筛选、排序后分页渲染条目，并能用 UID 定位到对应页；`getWorldEntry` 分开处理条目标题、内容和条件。正文是完整 `content`，同时具备放大编辑和计数入口。分页只是减少一次渲染的条目数，不应成为正文截断。[^st-wi-list][^st-wi-content]

对 Between 建议采用持续可见的条目目录，当前条目正文占主要宽度，条件在正文附近概览。标题缺失时显示“未命名条目 · UID …”，让用户仍能辨认条目；切换条目不应改变它的 UID 或排序值。

“常驻/关键词触发”“已启用/停用”“概率”“注入位置”应直接可读。扩展配置可以折叠，但不能只给一块无说明 JSON，迫使管理员猜测数字和空值的含义。

### 管理搜索与模型触发是两个不同功能

ST 管理搜索 `fuzzySearchWorldInfo` 使用 `key/group/comment/keysecondary/content/uid/automationId` 等字段，并按相关度辅助排序；这条路径与生成时的关键词扫描不同。[^st-search]

模型触发的基本含义是：在扫描范围中满足主关键词和可选二级逻辑，再经过概率、停用、预算、递归等规则决定是否注入；实际进入上下文的是条目内容。官方文档特别提醒中文等不以空格分词的语言谨慎使用 whole-word 匹配。[^st-doc-wi]

因此管理员搜索框应写“搜索标题、关键词、正文”，并返回命中字段和片段；旁边的触发关键词输入写“在对话中匹配这些词时触发”。不要让用户以为在管理搜索中搜到某条，就证明模型会激活它。

推荐第一版使用可解释的大小写不敏感包含匹配：先查名称/标题、再查主次关键词和正文，结果显示命中位置。是否需要模糊搜索另行决定；没有必要仅为模仿 ST 引入 Fuse。搜索状态不能修改原文、条目顺序或触发参数。

### 保存行为不能照搬

ST 已有角色的字段输入会触发 `saveCharacterDebounced`；世界书正文输入会调用 `saveWorldInfo`。后者默认先更新内存缓存，再安排约 1 秒的延迟保存；只有 `immediately=true` 才直接等待 `_save`。在该固定版本中，`_save` 发出 `fetch` 后没有检查 `response.ok` 就发出更新事件，因此不能用这个函数的默认返回或更新事件表达强意义的保存成功。[^st-character][^st-wi-save][^st-debounce]

本次检查的 `public/script.js` 末尾卸载保护检查 `isChatSaving` 和消息编辑 ID，未把角色/世界书的待保存草稿列为该条件。这个证据只能说明这段 guard 的覆盖范围，不能据此断言整个上游不存在其他保护。[^st-unload]

Between 当前编辑器已有 dirty、路由离开拦截、关闭确认、`beforeunload` 和保存失败保留草稿；重写不能回退这些能力。[^between-editor]

## 两个社区项目的对照

| 观察维度 | RisuAI | RisuAI Lorebook Manager | 对 Between 的取舍 |
| --- | --- | --- | --- |
| 条目组织 | 列表区分全局/角色/聊天来源，有文件夹和可展开详情；打开详情时限制拖拽 | 全屏容器，按角色/聊天/模块分区，列表有搜索和目录层级 | 保留“库→条目”的稳定层级；Between 没有的来源范围不做空入口 |
| 全文编辑 | 条目 `content` 绑定长文本控件；通用大编辑器可显示 Monaco 与解析预览 | 外层全屏，但单条内容仍放在模态框内的 textarea | 真正给正文宽度与高度；不要仅把外壳全屏就称为大编辑器 |
| 搜索 | 本次所读列表源码主要证明目录/来源组织，未据此声称其具备整库正文搜索 | `matchesSearch` 明确查标题、关键词、正文和备注 | 可借鉴明确搜索覆盖面；详情结果必须直接定位原文 |
| 关闭含义 | 通用文本大编辑器关闭后，把弹窗值回写原字段；不能把 X 解释成取消 | 关闭与取消直接隐藏模态框；这条处理路径没有 dirty 检查 | 明确区分“收起大编辑器”“放弃修改”“保存到服务器” |
| 元数据安全 | 本次未完整审计持久化链，不把 UI 绑定等同服务器保存成功 | 保存时生成一套新字段再覆盖旧对象，会重置二级词、部分扩展和 UID | 只借鉴交互思路；采用字段级更新和原对象保留 |

以上分别来自固定版本的 `LoreBookList.svelte`、`LoreBookData.svelte`、`TextAreaInput.svelte`、`PopupEditor.svelte`，以及插件的 `matchesSearch`、`generateHybridLore`、保存和关闭处理。[^risu-list][^risu-data][^risu-large][^plugin-search][^plugin-save][^plugin-close]

插件反例尤其值得保留：即使写成 `{...旧条目, ...新条目}`，新条目中自带的默认值仍会覆盖旧字段。它会新生成 UID，把 `secondkey/secondary_keys` 置空，把 `selective` 置为 false，并用新 `extensions` 替换原扩展。表面上“保留旧对象”，实际仍可能改变未编辑的触发规则。[^plugin-save]

## Between 字段完整性清单

### 角色

| 分组 | 字段 | 展示与保存约束 |
| --- | --- | --- |
| 标识与列表 | `id/name/icon/tag/description` | ID 稳定；公开简介与内部设定使用明确不同的标签 |
| 人物与场景 | `detail/personality/scenario` | 逐字段全文；可选字段缺失不能因表单初始化擅自填入新的默认设定 |
| 对话 | `greeting/examples` | 保留完整换行、示例分隔符与宏文本；开场白不是角色描述 |
| 模型指令 | `system/postHistory` | 标注内部上下文用途；角色历史后指令与全局 `preset.postHistory` 是两份不同值 |
| 用户设定 | `persona` | 明确这是默认用户 Persona，不能与角色性格合并 |
| 作者信息 | `creatorNotes/source` | 作者备注全文可读；导入资源的 source 归因只读、原样保留 |
| 世界关联 | `bookIds/world/keys` | `bookIds` 决定独立世界书绑定；原始 `world/keys` 仍需可读可保留，不能误写成当前唯一注入来源 |

11 个正文是 `description/detail/personality/scenario/greeting/examples/system/persona/postHistory/creatorNotes/world`。除全文之外，还必须能看到 ID、标签、来源和绑定书名。`makeSnapshot` 会用绑定世界书重新设置 `entries`，保存后的内容进入新会话快照，已有快照不重写。[^between-types][^between-role][^between-api]

### 世界书和条目

| 层级 | 必须保留/可核对的字段 | 交互建议 |
| --- | --- | --- |
| 书 | `id/name/keys/content/entries/source` | 书名、来源、绑定角色可查；区分 `entries` 缺失和空数组，两者行为不等价 |
| 条目标识 | `uid/comment` | 路由/目录使用 `book.id + entry.uid`；数组下标只作渲染位置 |
| 正文与关键词 | `content/key/keysecondary` | 全文编辑；关键词保持数组及原字符串；避免普通逗号拆分损坏带逗号的正则 |
| 基本条件 | `constant/disable/selective/selectiveLogic/useProbability/probability` | 中文说明与值同时可查；隐藏条件控件时不删除其已有值 |
| 注入 | `order/position/depth/role` | position 用有意义的选择项；只在指定深度时突出 depth/role |
| 高级保留 | `scanDepth/caseSensitive/matchWholeWords/excludeRecursion/preventRecursion/delayUntilRecursion/group/groupOverride/groupWeight/useGroupScoring/sticky/cooldown/delay/triggers/match…` 等 | 已知字段分组说明；未知字段可折叠查看并原样回写；`null` 的继承含义不能变成 false/0 |

`bookEntries` 在 `entries` 缺失时才用书级 `keys/content` 合成一条；`entries: []` 则没有条目。不要在加载/保存时把缺失数组自动变成空数组。服务限制每本最多 100 条、内容长度最多 24000 字符、UID 为非负安全整数且书内唯一；书级 `content` 最多 20000 字符。[^between-books][^between-api]

当前可选注入位置严格为：`0` 角色定义前、`1` 角色定义后、`4` 指定聊天深度、`5` 示例消息前、`6` 示例消息后。引擎拒绝 A/N 的 `2/3` 和 Outlet 的 `7`；服务也拒绝已启用的向量、自动化和 Outlet 条目。不要展示上游全量功能后让用户保存才碰到错误。[^between-engine][^between-enums][^between-books]

当前后台只为基本条件提供结构化控件，其余字段通过高级 JSON 保留；重写可以改善易读性，但“字段已存储”“前端可编辑”“引擎支持”“真实触发已验证”应分开描述。本报告没有把所有未知元数据判定为有效运行选项。

## 可直接实施的编辑流程

1. **从内容库进入。** 角色列表搜索覆盖名称、标签和正文；世界书搜索覆盖书名、条目标题、主次关键词和正文。结果带“字段/条目名称 + 命中片段”。选择结果打开对应资源，并定位命中字段或 UID。
2. **默认全文阅读。** 页面标题、来源、生效说明在内容前；左侧目录，右侧完整正文。全文保留换行与长词换行，正文不使用 line-clamp。列表摘要允许截断，并保留“阅读全文”入口。
3. **编辑保留上下文。** 从某字段或条目开始编辑时，自动定位对应输入框。大编辑器与普通输入共用一份草稿；收起大编辑器只改变布局。正文和条件可切换，但切换不丢失未挂载字段。
4. **保存一次，等待确认。** 主动作“保存修改”，附近持续提示“用于新会话”。普通保存无需重复弹出确认；移除资源、放弃草稿等动作单独确认。请求完成前禁重复保存并防止误离开。
5. **失败继续工作。** 网络/400 错误定位到问题并保留全文；409 显示草稿仍在、服务器版本已变。不要自动换用最新版本重试整份配置，那会覆盖他人的其他改动。提供查看最新版本/复制草稿的恢复路径，只有明确放弃时才清草稿。
6. **离开有明确结果。** dirty 时，取消、X、Escape、路由切换与浏览器关闭都必须有一致的保护语义。保留“继续编辑/放弃修改”；若有“保存并离开”，仅在服务器确认成功后离开。浏览器原生卸载提示不能替代应用内路由拦截。

这些是本次设计建议，除上文特别标注已有机制外，不代表已经实现。当前 API 和会话隔离可直接沿用。

## 验收必须验证的具体结果

- 用虚构角色填满 11 个正文字段，在每段末尾放不同标记；全文阅读和编辑都能找到末尾，长字段能进入大编辑器。
- 在正文中间搜索一个唯一词，结果明确属于哪个字段或哪本书的哪个 UID；进入后可定位，清空搜索可恢复全部内容。改变搜索不改变触发关键词。
- 使用两个世界书中相同 UID、以及同书乱序 UID，验证目录跳转不按数组下标或全库 UID 误定位。
- 修改一个条目的正文后保存，逐项比较其他条目、来源、UID、主次词、`null`、未知对象元数据完全保留；再验证 `entries` 缺失与空数组不会互相转换。
- 断网/模拟 400/模拟 409 时保留草稿；409 不自动覆盖服务器，后续可以读最新内容并恢复自己的改动。
- dirty 时实际操作 X、取消、Escape、侧栏导航、浏览器返回与刷新；保存中禁止重复提交。会话失效的恢复路径也不能被描述为草稿已安全保存。
- 验证每个允许的 position 标签与原始数值一致，二级逻辑按 `0 AND ANY / 1 NOT ALL / 2 NOT ANY / 3 AND ALL` 保存。触发参数的真实效果由隔离引擎测试验证，视觉标签不能代替。
- 保存后创建新会话读取新配置，已有会话保持原快照；普通用户响应和 SSE 不出现内部角色字段、世界书正文或来源内部字段。

## 限制

本次没有实际操作 ST/RisuAI 浏览器，也没有验证插件安装、浏览器无障碍或各尺寸视觉表现；这些结论来自固定源码，正式交付仍须由主任务在目标后台实际验收。本次未审计 RisuAI 的完整持久化/同步链，不将双向字段绑定等同数据已落盘；也未实现或验证 ST 全量世界书功能。
