# 记忆、画像与模型上下文

核查版本：`etherfunlab/eros-engine@9715af2ce7d8524ca5ce8771059d436c31951977`，2026-10-23。仅静态源码核查，未运行服务／模型／测试。默认值指源码，不代表线上启用。阅读导航见 [总索引](README.md)。

最需要避免的误读是“有画像表就会让人物记得”。本篇按真实 writer→reader 区分：用户原话存储、两阶段事实提取、常驻条件、按向量检索的材料、只供查询的表，以及仅修改提示词副本的历史清理。

持久契约（精简）：

```text
Memory(session_id, user_id, instance_id?, content, category?, metadata?, embedding)
  Profile 强制 instance_id = null；Relationship 保留 instance_id
HumanInsights(user_id, 城市/职业/家庭/兴趣/生活节奏/未来计划等...)
CharacterInsights(instance_id, location, occupation, current_situation, relationships,
                  desires, vulnerabilities, habits, personal_values, likes, dislikes)
UserInsights(instance_id, 真人用户画像字段...) // DB-only，不是 HumanInsights
```

Model-facing history 是从原始聊天行产生的副本；原文与清理后的提示词不能混成同一个存储事实。

## E04 记忆、画像和短期历史：原话留痕与结构化事实承担不同责任

**写入触发：** 文本成功产出后，五条并行后处理链写原话记忆、human_insights、character_insights、user_insights、关系变化。画像链通常先从这一轮提取事实，再带既有画像把事实整理为结构化增量；已有画像读取失败会停止整理，避免把“没读到旧值”当成“旧值为空”覆盖掉。[^src-1][^src-2]

**回读区分：**

- 向量记忆：用户级分组事实 + 与这个实例的关系记忆，按当前消息查询，去重后进提示；embedding 或检索出错可以省略这一块。
- human_insights：用户的重要基础条件常驻，不依赖一次向量命中。
- character_insights：只有 current_situation/occupation/location/relationships 进入人物当前状态；不再把 habits/values 等重新概括为一套与底稿竞争的人格。
- user_insights：仅入库和接口查询，本版不作为回复上下文。

[^src-3][^src-4][^src-5][^src-6]

**历史窗为什么可变：** 人物画像越充分，模型越不必反复读很长的旧对话；代码按填充字段数决定额外历史数量。但保留当前消息和上一回合，至少保护两条先前消息，使“那个呢”等指代仍能解。未完成队列中的当前驱动消息是锚点，不能直接读“数据库最新 N 条”偷看之后的新来信。[^src-7][^src-8]

还有专门的 history echo cancellation／noise cancellation：只改模型看到的副本，移除重复行、部分开头句及括号动作描写等，以避免模型从自己的旧措辞里反复学回同一套路。原始聊天存储不因此被改写；这种强清理可能损失语义，应作为可比较的产品策略而非普遍正确的规则。[^src-9]

## E05 闲置会话“做梦”：异步提炼，而不是后台继续聊天

**触发：** dreaming 扫描闲置、尚未分类、未归档、非群聊会话；数据库 claim 防止多个 worker 同时提取。取规范聊天记录，交 memory_extraction 模型分类，逐条 embedding 写 profile memory，然后标记分类完成。语音可包含，但有独立开关；产品咨询不算人物经历。[^src-10][^src-11]

**消费者：** 下一轮 profile recall，世界导演还会读取近期提取记忆作为外部反馈。

**恢复细节：** 整次模型失败不会写“已分类”，需等 stale claim 允许后再尝试；不能按注释笼统理解成每个下一 tick 都能立即重试。逐候选 embedding/upsert 失败只记录 warning，循环仍可能最终标记“已分类”；这些局部失败未形成逐条可靠重试。这个差别决定能不能把“后台抽取跑过”称为“所有记忆都保存了”。

**感知边界还存在旁路：** dreaming 的历史 SQL 只按会话、角色和 channel 过滤，没有按 read_at 或 ghost 过滤。因而离线回合未进入 PDE／回复模型的原话，仍可能在会话闲置后被分类模型读取，并写成用户级 profile memory；世界导演的近期反馈查询会读取这类已分类用户记忆。静态接线允许这条信息影响后续世界材料，但本轮没有运行模型证明具体会提取或生成什么。采用时必须明确：后台提取算不算人物已查看？如果不算，就不能让它绕过人物注意边界。[^src-12][^src-13][^src-14][^src-15]
