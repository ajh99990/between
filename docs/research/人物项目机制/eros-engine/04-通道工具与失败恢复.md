# 通道、工具、异步执行与失败恢复

核查版本：`etherfunlab/eros-engine@9715af2ce7d8524ca5ce8771059d436c31951977`，2026-10-23。仅静态源码核查，未运行服务／模型／测试。默认值指源码，不代表线上启用。阅读导航见 [总索引](README.md)。

“她回复了一条文字”“她在电话里说出前半句”“客户端在画图”“后台继续生成”具有不同完成与取消语义。这篇从真实 route→pipeline→持久结果说明边界，避免用一个统一的 agent/tool 名词掩盖差别。

关键数据（精简）：

```text
VoiceTurn(session_id, instance_id, user_id, user_message_id, content,
          memory_scope, affinity_scope, session_metadata)
VoiceBootstrap(insights, prev_call, prev_session_id, effects, needs, created_at)
ProducedMessage(message_id, full_text, action)
ChatQueueRow(驱动的 user_message_id, session_id, 参数, 状态, 尝试数, 占用时间...)
ProtocolFrame(meta/delta/done/final/image_request/body_state/action_response/error/...)
```

文字与语音不同：前者断线继续，后者断线取消，另外用 interrupt 记录实际已听到的前缀。该差异直接影响“什么进入历史、什么后果能够发生”。

## E11 文本、多模态、产品问答和语言清理

文本主路在动作确定后才做可选 vision、input filter、完整背景组装、聊天模型输出、regex／模型 output filter。管线支持一轮多条消息与模型 fallback，记录最终实际服务的模型和失败链。过滤器既有 before 模式（最终可见内容形成后再发）也有 after 等模式；后处理使用哪份文本有专门选择，不应一概写成“原始生成就是最终记忆”。[^src-1][^src-2][^src-3][^src-4]

图片路径先用人物外观、当前穿着、身体状态、最近场景、用户话、风格和画幅构图，然后发 image_request 帧给调用方生成。历史／后处理可使用图片 caption 作为事件代理；仅图片回复不应被误判为空白 ghost。某些旧 enum 注释仍说图片 action reserved，但当前 stream 已有实际委托构图分支，应以装配为准。[^src-5][^src-6][^src-7]

产品咨询单独走 operator 提供的产品文档任务，标 channel=product_qa；跳过 persona prompt、vision、input/output filter 与人物 post_process，避免“产品套餐怎么购买”污染她的人生记忆。[^src-8]

“工具”在这套实现里主要是程序执行既定动作、对外提供 HTTP 和把绘图工作交给宿主，不是任意工具发现／选择／执行／观察的 ReAct 循环。要给公共人物 B 站／小红书操作权，仍需要一个明确工具执行层和结果记账，而不是给现有 reply action 多取几个名字。

## E12 语音：低延迟优先，行为边界并不完全等同文本

语音客户端送已识别的文字；引擎读 8 条历史，首次回合组装并冻结 bootstrap（用户画像、以前通话摘录、身体余效与需求），之后复用；每轮可以做有预算的向量召回。bootstrap 不完整不写完成标记，下轮重试；竞争创建时使用先写入的快照。回复走单独 voice prompt 和模型 fallback，不走完整文本 PDE／世界片段读取／每轮关系与画像后处理。闲置后 dreaming 可以提取通话记忆。[^src-9][^src-10]

打断有精确区别：关闭语音 SSE 会 drop 上游生成；interrupt 接口不是“再次取消”，而是保存用户实际听到的前缀，并给本轮写 interrupted 标记，避免未说出的长尾进入历史。只允许最新语音用户轮，防止改写旧对话。相同 client_msg_id 若没有回复且没有人工打断标记，可以用已保存用户原文修复；已有回复或明确打断则不重复生成。[^src-11][^src-12]

文本 SSE 则相反：断线只失去观察连接，后台生成继续。把两者都叫“取消回复”会掩盖实际状态语义。


**独立调用链证据：** voice route 直接构造 VoiceTurn → run_voice_turn；run_voice_turn 并行加载 persona、跨文本会话只读 affinity、锚定历史、bootstrap、recall → build_voice_prompt → voice 模型流 → insert_voice_assistant_message → Done，函数结束，没有转入 stream::run_stream 的离线闸门或 PDE，也没有普通 post_process 调用。关系读取还明确只取这个 user×instance 最近的文本关系，不在语音通道创建关系行。这个结论来自入口到出口的路径，不能只凭“voice”名称断言。[^src-13][^src-14][^src-15][^src-16]

## E13 群聊：另一位导演决定谁先说，人物依次接力

进入群聊后，先载入各成员底稿、只读关系与各自的信号；把共同历史标注说话者。可选 group_director 读取成员性格／关系档、@mentions、对话和图片能力，返回发言 cues；配置缺失／模型失败／空结果走规则 fallback。随后按 cue 串行让每个人物回复，后面人物能承接本轮前面人物说过的话，前端先收到 cast。[^src-17]

它明确不写普通 companion_affinity，但说出的内容仍可以进入群聊专用后处理和相应画像链。不能因为共享了回复函数，就默认拥有一对一的同套沉默／关系更新策略。[^src-18][^src-19]

## E14 异步执行、取消、归档与失败恢复

队列保证的是“一个会话不要同时有两轮生成”。数据库 claim 同会话串行、待处理取最新优先；generation_timeout 后重试，过时占用回收。成功已有助手行或 user row 已标 ghost，重驱动前就视为已完成；同 client_msg_id 防止重复入库。它没有“人物稍后再读”或“答应三点回复”的语义，二者不能借一个 pending 状态混用。[^src-20][^src-21]

普通文本路由把驱动器 tokio::spawn 出去，继续耗尽 stream；用户关闭页面不会撤销生成，避免一次断网留下孤立消息。语音则是上节的显式不同选择。[^src-22][^src-23]

归档与后台写入存在竞争，因此后处理开始时检查会话仍活跃，真正写入时还有 _if_live 事务保护；不能只在任务开始判断一次。审计采用尽力写入且有超时，审计失败可丢 trace 关联而不拖住用户回复。[^src-24][^src-25]
