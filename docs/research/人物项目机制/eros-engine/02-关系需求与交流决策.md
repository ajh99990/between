# 关系、需求与交流决策

核查版本：`etherfunlab/eros-engine@9715af2ce7d8524ca5ce8771059d436c31951977`，2026-10-23。仅静态源码核查，未运行服务／模型／测试。默认值指源码，不代表线上启用。阅读导航见 [总索引](README.md)。

这篇区分三个问题：长久以来怎样看待这个人、此刻身体和社交需求怎样、这一条消息采取什么动作。Eros 分别用持久关系、needs 与 PDE 计划承载，不存在一个情绪值包办三者。

关键结构（精简）：

```text
DecisionInput(event, affinity, persona, conversation_signals)
Affinity(session_id, user_id, instance_id, trust, intrigue, intimacy, tension,
         warmth_grade, patience_grade, derived_warmth, derived_patience,
         pending_deltas, feeling_clause, ghost_counters, updated_at)
Needs(hunger, social, stamina, emotional) 每项 low/mid/high
ActionPlan(action_type, context_hints, reply_mode, nudges, clothing,
           image_ref, aspect_ratio, action_response, affinity_deltas, ...)
```

注意：PDE 的最终 wire payload 比 DecisionInput 多了从数据库补读的 needs／events／身体效果；关系评分器与回复模型也各读不同材料。我们不能把这几份输入画成一份“完整意识上下文”。

## E01 先决定怎样交流，再生成文字：PDE 与回复并非同一个模型任务

**解决的问题：** 单一聊天模型容易每轮都热情接话，也难以可靠控制“这轮沉默、发图还是处理产品问题”。

**触发与输入：** 普通文本消息已入库、未被离线事件提前阻断后，若配置了 pde_decision，判官先读取人物简述、最近对话、关系档位、耐心档位、对话次数与沉默次数、之前的需求、当前生活事件、身体余效、用户动作和衣柜。世界 digest、故事 digest、完整画像／向量记忆在后面的回复组装中另读，不在这份判官输入里。[^src-1][^src-2]

**产生什么：** 判官给 action、inner_state、reply_mode、reason、图像参考与比例、穿着、动作接受／拒绝、needs。action 是封闭集合：文字、沉默、图片、文字加图、产品咨询；这不是能随意发现和调用 MCP 的通用工具循环。reply_mode 是 listen/follow/ask/judge；未明确给模式时，程序才按关系滚动 affirm/share_slice/open_question 等轻量提示。[^src-3][^src-4][^src-5]

**消费者和后果：** 程序检查动作能力与保护规则、把 inner_state 清洗成回复上下文，再调用回复模型。启用判官时真实流程是 **模型先判、失败回退规则**；未配置时直接走规则，不能按 pde.rs 的概括性旧注释写成“始终规则先行”。模型想沉默也可能被新关系保护、反连续沉默、全局禁沉默开关否决；强制图片请求还可覆盖沉默。审计同时保存 proposed_action 与实际 action，以便知道是谁改了决定。[^src-6][^src-7]

**状态：** 可选模型判官，始终有程序执行路径；这证明模型判断与数值规则可以组合，但不能把它说成“模型拥有所有决策权”。哪些硬规则适合我们仍须另定。

## E02 关系不是每轮一句心情：评分、累积、档位、文字感受

**解决的问题：** 每轮直接让模型加好感容易快速失控；当下态度、长期信任和紧张不应只有一个数字。

**写入链：** 成功回复后，把本轮用户话、最终助手回应、人物名与当前关系交给关系评估器。它给 trust/intrigue/intimacy/tension 的有符号等级，以及 warmth/patience 的绝对级别和原因。程序在锁定最新数据库行后，先按时间更新，再把等级换成增量、按既有档位压低正增长、施加两条关系线的交叉惩罚、累积小于阈值的变化，最后保存状态和审计。**warmth/patience 是由本轮等级、关系基础、时间衰减导出的端点，不与另外四项使用完全相同的增量规则。**[^src-8][^src-9][^src-10][^src-11][^src-12]

**下一轮怎么用：** 判官读程序预计算的亲密档位和耐心档位；回复读关系基线、态度、可选的 feeling_clause，另外带上一条最近的情感变化原因。feeling_clause 由可选摘要任务在发生变化的回合重写，不直接把一串裸浮点数塞给回复模型。默认规则沉默分数则直接使用 intrigue、patience、tension。[^src-13][^src-14]

**同一冲突／道歉例：** 她说在忙，用户催促，她回了一句短话；事后模型才评“耐心低、紧张上升，原因是被催”。下一轮道歉时，模型看到旧关系与最近原因，可以把当下耐心评回中档，同时不给信任加分，或按证据少量加分。程序保存两类后果，确保短暂态度不等于长期关系清零。这里的等级结果是举例，**源码没有保证模型一定这样评价**，也没证明这些公式比别的方法更自然。

**失败／限制：** 评分失败降为无语义增量，已有端点等级保留；异步后处理可能落后于紧接着的下一轮。成熟度可说“有持久化、审计、原子更新和领域测试”，不能说“情感质量已验证”或“可直接照搬所有关系惩罚”。

## E03 需求与身体余效：两种时间，不能混称完整情绪系统

需求只有 hunger/social/stamina/emotional 四项、low/mid/high 三档。PDE 这轮给出的需求写到当前用户消息的 metadata；哪怕本轮最后选择沉默也写。下一次读取此前最新有效评分时，程序按时间把饥饿向 high（每 4 小时一步）、社交欲向 high（12 小时）、体力向 mid（8 小时）、情感需求向 mid（12 小时）推进。没有一个后台任务定期重写四项。当前评分可直接影响本轮回复。[^src-15][^src-16][^src-17]

礼物余效则是**按后续对话轮数**计算：之前接受了某类给物动作，从该种类／数量对应的曲线取 rising/peak/fading 与 level。它不是现实时间药理模型，也不是饥饿／体力方程。接受决定落在成功回合，后续判官、回复与图片构图读一致的 body_state；通话把它冻结在开场快照里。[^src-18][^src-19][^src-20][^src-21]

因此，Eros 有“需求连续性”和“关系情感连续性”，不能仅凭 emotional 字段称其为已完成的通用情绪引擎。全局感受、对特定人的感受、被一段关系影响后是否外溢到别人，上游这些表本身没有替我们回答。
