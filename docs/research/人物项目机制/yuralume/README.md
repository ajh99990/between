## 首先认识它的设计和边界

作者明说的核心问题是：人物不能只有用户发话时才存在。实现里，人物的日程、已发生事件、认识的人、对用户的认识、主动念头、发帖与承诺都有单独的保存位置。聊天只是这些材料的一位消费者，也会在结束后写回新的材料。后台同时推动生活，不要求每次生活进展都先有用户消息。[^y-readme][^y-tick]

但不能把它描绘成已经统一完成的“一个自主主体”。当前代码仍有几条并存的驱动方式：日程到时、模型生成生活余味、预设剧情节点到时、用户拉起剧情场景、主动联系三道判断，以及运营限额/夜间静默规则。它们通过共享日程和记忆互相连接，并没有统一的“感知—意愿—行动”总控制器。某些人体状态只有人工配置与提示输入，某些低层状态仍由关键词改变。

**尤其重要：它的“同一个人跨设备”主要是同一账号拥有的人物在Web/Telegram等渠道共享记忆，不等于我们要做的“所有现实用户面对同一个公共人物”。** `Character.user_id`是所有者账号；`OperatorProfile.id`是人类账号；相遇规划也明确拒绝跨所有者的人物对。情绪事件里的`operator_id`不能直接解释为任意微信联系人的ID。[^y-owner][^y-encounter-plan]

## 用一天串起机制，不把一切都归成聊天

以下是根据源码结构构造的讲解案例，不是模型实测记录。

- 早晨后台确保她今天的日程，已有“14点赶报告”就复用；世界RSS收进一条她感兴趣的消息，暂时只是素材。
- 午间聊天中，用户告诉她自己换了工作，约晚上八点聊。回复之后，记忆提取保存这次谈话；persona提取产生职业变更候选；日程调整可以加未来约定；若她明确承诺八点主动发消息，还会另建scheduled_promise。四种保存不是同一个东西。
- 14:10用户又来问。当前活动busy=.8，busy模型已经读到问题，选择短答并保存busy_defer；它不是未读收件箱。忙中另有一条刚才想分享的念头，可由主动意图判断暂存在DeferredIntent；这些队列不能互换。
- 15点报告结束，活动余味/事实形成记忆；后台补回流程重新判断能否处理待答问题。她也可能在公开动态发表报告结束后的心情，但公开候选会过滤私密关系材料；公开动态不等于主动私信。
- 用户给动态留言。评论回复按后台节奏处理；用户下一次打开聊天，反馈记忆先同步，人物才有依据提到这次留言。
- 晚上两名被设置为朋友的人物在共同空闲时相遇，各自生成对话与记忆；她不会凭对方完整数据库知道一切，只拿自己认识对方的材料。
- 夜里条件满足后，persona候选整理更新她对用户职业的认识；反思读取近期经历与情绪事件；行为观察可能确认新习惯；性格改变需更长证据和冷却。第二天规划才有机会读到这些新增材料。

这条链的关键不是“更多prompt”。**不同材料有不同承诺程度和知识权限：想做、计划做、答应做、做过、告诉过别人，不应由同一段自由文本混着表示。** 但Yuralume仍有多条并行规则和兼容层，不能假装它已经把所有机制统一成一个精简主体模型。

## 哪些没有证明、哪些不应遗漏

1. 没有统一“所有现实联系人共享同一人物”的实现证明，现有owner边界不能直接平移。
2. 没有找到通用“未读消息不进入模型—人物自主打开收件箱”的状态控制器；当前busy是已读延期，评论是程序按tick批处理。
3. 身体状态有结构/提示，无自动生理演化证据。
4. route_b旗标不能据名称判断当前相遇开关；既有注释有版本残留。
5. 累积对话checkpoint代码已存在但默认关闭；默认仍临时摘要。
6. 人格反思/习惯/漂移依赖persona梦流程，不是完全独立的时间服务。
7. 全包还有多人物fusion短篇、branching drama视觉小说、角色卡导入导出与创作素材库；本轮确认container相关服务装配（6356–6672），未逐项追创作工作室的生成/审核/导回细节。这些是创作产品机制，不能从“多人故事生成”直接推断角色自主群体生活。
8. 图像、视频任务、TTS、多模态识别、restricted-content路由、计费/配额与跨进程调度真实存在。本轮确认接口装配和对主链的门槛，未运行媒体服务/真实连接，也没有把商业配额等同人物心理。
9. 原项目没有B站追番/公开空间和小红书管理工具证据；内建社交feed只提供相似行为链参考。
10. 所有自然度、忙碌判断质量、情绪语气连续性、长时间自主生活效果，都未实测；模型返回示例必须标自拟。
