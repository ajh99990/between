# 日常生活与时间推进

研究对象：`Yuralume/yuralume-core@6996b152604e83a1cf6344cd236a9b9456f47bba`。本篇从固定源码核对真实写入者、读取者和默认装配；未启动完整服务或调用模型。伪代码为解释真实分支的简化版本，示例为自拟，不代表效果测试。人物的 `user_id/operator_id` 主要指拥有它的账号，不能先解释成任意联系人。

## 先看保存了什么，谁使它成为事实

| 保存结构 | 关键内容 | 谁写 | 谁读，以及改变什么 |
|---|---|---|---|
| `Character` | 人物底稿、生活方式、表达倾向、owner | 创建/编辑；长期性格漂移可小幅修改 | 日程、聊天、主动联系、相遇各自读 |
| `DailySchedule` | `character_id/date/activities/is_planned/manually_adjusted` | 规划服务；聊天日程调整；天气检查；相遇规划 | 当前活动、忙碌判断、共同空闲、结束后记忆化 |
| `ScheduleActivity` | 起止时间、描述、类别、地点、`busy_score`、参与者、`memorialized/has_memory`、隐私/可相遇条件 | 规划/变更生成活动；专门实现路径更新标记 | 时间查询判当前活动；已结束活动进入记忆化 |
| `CharacterGoal` | 内容、状态、优先级、来源、最近推进时间、复盘备注 | 对话后提取及目标review | 以后聊天/主动联系/目标复盘 |
| 活动生成的 `MemoryItem` | 实际事实、重要度、参与者、知识边界、余味 | 活动记忆化服务，或相遇/剧情专用写入 | 以后语义召回、反思、公开候选 |

日程与目标结构分别见[^y-schedule-shape][^y-daily-shape][^y-goal-shape]；保存并不等于发生，也不等于用户参与过。专门记忆化路径会检查用户是否答应、最后一次互动是否落在活动时段内；这是程序的粗略判据，不是实际共同参与的证明。[^y-memorialize]

## 一个 tick 怎样推动生活

```text
人物 tick(character, now):
  刷新休息恢复
  检查剧情节点是否到期
  确保今天有日程；按条件检查天气是否需要调整
  对已结束且未记忆化的活动，尝试留下事实/余味
  若取得当日复盘权，复盘目标
  关闭闲置超时的场景
  尝试生成公开动态；处理到期评论批次
  若主动私信开关及门槛允许，再尝试主动联系
```

这说明人物生活并不由“主动消息开关”总控。步骤间有不同的错误隔离与花费门槛，上述列表是调用次序概览，不表示整体是一个数据库事务。[^y-tick]

### Y01 持续推进：不是每过几秒让人物随便说一句

FastAPI按进程角色启动调度器。自托管常见`all`角色同时启动人物/社交调度和世界事件调度；分布式版本把发现到期任务与执行任务拆到coordinator/worker。人物tick依次做：休息恢复、剧情节点到期、确保日程并核查天气变化、活动记忆化、每日目标复盘、超时场景收尾、发帖、评论回复、主动私信。社交tick另外推动人物相遇、对熟人的知识整理、对用户画像的梦中整理。[^y-start][^y-tick][^y-social-tick]

`proactive_enabled=False`仅让主动私信部分不执行，不会整体停止生活；冻结人物、订阅与运行资源门槛才是另外的控制。静默生活更新、公开发帖和私信是不同消费点，不能统称“主动消息”。部分步骤异常后继续，其目的之一是某个模型失败不让全天停止。

### Y02 人物底稿和关系起点

人物保存性格、兴趣、表达风格、边界、生活方式与四个定性倾向：自我中心程度、直言程度、分享欲、联想程度。倾向按low/medium/high转成提示里的描述，相关实现声明不能直接拿这些band做行为if/else。关系起点则单独记录人物与账号拥有者原本的关系，避免新建人物因“聊天次数少”就否认已设定的青梅竹马/朋友身份。互动频率只描述最近熟悉程度，不应重写关系起点。[^y-owner][^y-disposition][^y-milestone]

这不是统一“人格数学模型”，而是不同时间尺度的事实与倾向输入。后续Y15才可能缓慢改动倾向。

### Y03 日程：已存的安排是事实来源，变更是单独操作

`ScheduleService.ensure_schedule`优先使用已存可用日程，没有才调规划模型。输入包括人物生活方式、日历/天气、最近活动摘要、近期故事、约定、观察到的习惯与关系背景。结果保存为`DailySchedule`及带起止时间、位置、忙碌值、参与者等字段的`ScheduleActivity`。当前聊天只查询此刻活动及刚结束、接下来、今天完成的活动，不每轮重编一天。未来日期可先只有约定，之后围绕它补全天的安排。[^y-schedule]

**允许日程空档，并不强制排满 24 小时。** 2026-10-23 补核：领域模型明确把活动之间的缺口视为“空闲／未安排”，`activity_at` 在没有活动覆盖当前时间时返回 `None`。创建日程只对活动排序；规划结果解析会校验起止、过滤无效条目、裁剪重叠，但没有自动填满所有空档的步骤。[^y-gaps-shape][^y-gaps-parser]

生成提示与程序约束要分开看：提示要求一天大多数时间有具体活动，允许短暂自然空档，不鼓励白天连续多小时不知道在做什么；较长留白建议安排成放空、散步、休息等低强度活动，松紧随人物性格变化。这是给规划模型的要求，不是数据库拒绝长空档的规则；没有明确的“超过多少分钟就不能保存”的阈值。[^y-gaps-prompt]

自拟例子：日程有 13:00—14:00 整理房间、15:00—16:00 出门买菜，中间一小时可以没有条目。14:30 查询时，`current=None`；`resolve_current` 仍提供接下来活动，并在最近三小时内找刚结束的活动，给回复模型交代前后背景。聊天的忙碌延期分支遇到没有当前活动会跳过专门的忙碌判断，继续普通回复路径；不表示其他流程门槛都被绕过，也不证明人物实际在这段时间做了某件事。[^y-gaps-runtime]

规划失败是另一种情况：LLM planner 内部捕获模型调用失败时，只保留已有承诺，标为 `is_planned=True`，没有承诺就为空；异常进一步抛到 `ScheduleService` 时，外层可保存 `activities=[]、is_planned=True` 的空日。这些恢复分支防止每条消息或 tick 重复付费规划，不代表角色主动选择整天留白，也不保证当天自动恢复；显式 regenerate 可重新规划。[^y-gaps-failure]

一次普通聊天回合的最终回复生成并保存后，post-turn 提取可以返回`add/modify/remove`日程变更；它不等待整段会话结束。有 worker 或后台提取时会异步执行，因此启动后处理不等于下一条消息到来前已经保存成功。仅有明确行程异动才建议调整，不会因讨论某个视频自动把交流过程追加进活动描述。服务定位日期/活动、解决重叠并保存；天气变化也有单独审查路径。人工改过的日程可阻止当天因天气自动重生成。**现有历史保护主要依赖`memorialized`，不是所有已过去的时间**，因此不满足我们已确定的统一历史不可改规则。[^y-post-turn-timing][^y-adjust][^y-weather]

#### 空档可能导致什么，哪些还没有验证

2026-10-23 用户进一步质疑：人类没有日程时仍有真实生活和身体状态，人物 Agent 如果拿不到当前活动，会不会临时编出近况？**源码能确认缺少材料与后续保存的路径，不能据此给出编造概率，也不能断言留空必然出错。** 本轮未运行模型对话试验。

实际传给回复模型的内容分两种：有接下来或刚结束的活动时，当前日程区块把空档解释为没有特定安排、忙碌程度低，同时声明日程是当前活动的权威来源；若当前、接下来和刚结束活动均不存在，`_render_schedule_block` 直接返回空列表，这个区块连同其来源约束都不出现。其他上下文仍可能包含人物、世界位置和记忆，不能说模型完全没有信息。该区块没有实现“空档时先选择并保存当前活动，再依据它回应”的流程。[^y-gaps-render]

自拟风险例子：14:10 用户问“干嘛呢”，模型临时回答“刚下楼买了杯咖啡”。即使没有对应安排或实际事件，这句话也会作为助手正文进入 post-turn。提取器若选中它，就可能生成一条经历记忆，经过结构校验、去重和向量化后保存；以后召回时又成为回复材料。这条保存路径没有逐件核验助手自述对应的实际活动，但不能因此断言全项目没有其他软性质量审查，也不意味着每句自述都会进入长期记忆。[^y-gaps-postturn]

| 可能后果 | 前提与已核实边界 |
| --- | --- |
| 当轮或隔轮近况矛盾 | 模型在缺少当前活动依据时作不同补写；可能发生，尚未测量。近期原文也可能帮助它保持一致。 |
| 多人面对不一致的生活 | 若移植到我方多人系统且各对象独立补写，同一时刻可能对甲说在家、对乙说在外面；这是我方架构推演，不能写成已发现的上游多人故障。 |
| 临时自述成为长期材料 | 需要提取器选中并写入成功、以后被召回；数据流已确认，具体错误与频率未实测。文字相似去重不负责事实核验。 |
| 空白被当成可回应 | 已确认当前活动缺失会跳过专门的忙碌判断；这可能把状态缺失和真正空闲混为一谈，不代表必然发出回应。 |
| 未执行的实际平台活动被声称完成 | 我方若把日程或临时口述当工具结果，就可能说看过未读取的视频；是待验证的设计风险，不是本轮观察到的 B 站行为。 |

后果不必都严重。若只是一次普通的闲聊描述、未被记住且没有改变后续行为，影响可能很小；虚构人物也需要产生新细节。需要判断的是新细节在哪里确立、是否向同一人物的其他回合持续提供，以及是否错误声称真实工具动作已完成。不能把“允许生成虚构生活细节”和“真实平台动作可以随口编造”混为一谈；前者的授权与生成规则仍在讨论。

把日程填满可以提供更多背景，但不能单独保证上述问题消失：计划写了某项活动不等于已经开始或完成，宽泛的活动也不能涵盖所有细节。建议比较“全天粗粒度计划”“计划可空但维护共享当前活动”“各轮即兴后追记”三种方式；我方倾向及用户是否采用统一见[现行方案决定](../../../plans/人物主体Agent方案/02-决策依据与取舍.md)，不从上游允许空档直接推导我方必须允许。

本轮 OpenCode 只读审查使用 `opencode-go/deepseek-v4.1-flash`、`max`，有效正文及同会话追问均已检查。独立复核后，接受其“保存只证明选择，不证明执行”“过期状态和停服需要明示未知”“多对象共用同一活动状态”的提醒；仅把全天覆盖保留为对照，未采纳它最初将全天计划当作首选解决方案的建议。追问指出计划不能提供执行事实后，审查者认可改用共享当前状态作为目标候选。审查不构成用户批准或行为效果验证。

### Y04 活动结束：计划、实际参与、留下的感受不是一件事

记忆化扫描今天和昨天已结束但未处理的活动。普通独自活动的记忆正文主要沿用日程描述，接入 aftermath 模型时附加感受；只有涉及用户约定的分支才读取“邀请是否被接受”和“最后一次互动时间”来请求 `factual_summary`，不能泛称每项活动都会根据实际经过重新提炼事实。相遇和剧情占位活动由各自专用路径写记忆，避免重复。嵌入或存储失败不标完成，留给下一次重试，原子claim防同一活动两次写入。[^y-memorialize][^y-aftermath-input]

这里原先简称的“参与证据”，具体只有两项输入：

1. 活动 `participant_refs` 中用户的 `role`：邀请还没被接受、已过期或人物单方面希望，属于未答应；`operator_confirmed_shared` 或 `operator_confirmed_lapsed` 表示曾答应。
2. 人物状态的 `last_active_at`：用户最后一次互动的时间。程序比较它是否落在该活动的起止区间内（含开始，不含结束）。它没有读取这段聊天的正文，也没有查询完整互动日志。

曾答应且最后一次互动在活动内，程序给出 `VERIFIED`，允许后续模型使用共同经历的叙述；曾答应但缺少这个时间信号则为 `UNVERIFIED`，既不能写“一起完成了”，也不能断言用户爽约；没答应则为 `SOLO_ONLY`，不能把计划写成共同经历。没有用户参与者的普通独自活动不适用这套检查。[^y-shared-rule]

自拟例子：计划 14:00—15:00 一起看视频，用户已经答应，最后一条消息在 14:20。程序允许写共同经历，但不会检查那条消息谈的是视频还是快递。反过来，即使 14:20 一起讨论过视频，15:10 又聊了一句，15:11 收尾时单个 `last_active_at` 已变成 15:10，便无法从它还原 14:20 的互动。这是“最后一次时间”带来的信息损失；`VERIFIED` 不能解释成已核实完整观看或线下到场。[^y-shared-rule]

这项规则要避免“她曾邀请用户喝咖啡”被写成“用户陪她去了”。模型依检查结果生成允许的事实描述；缺少合规摘要时，相应共同活动记忆可以跳过。留下的感受进入记忆和后续提示，不等于每项活动必然另写一个 EmotionEvent；这条与 Y13 分开追踪。[^y-shared-writer]

活动收尾的模型输入没有直接加载这段时间的聊天正文、浏览内容或原始工具结果，不能把它解释成一次完整的实际活动复盘。日程与聊天分开保存本身并非缺陷；当前聊天另有动态组合日程、近期对话和记忆的路径，历史时间段联合查询的核查边界见[交叉场景说明](03-记忆认识与知识边界.md#日程与聊天交叉时谁组合材料)。[^y-aftermath-input]

### Y05 目标会被定期整理

目标是`CharacterGoal`列表，聊天上下文和主动联系读取活跃目标。除了若干对话后的复盘，还有**每天一次的目标review**：即使用户不聊天，也会拿当前日期、目标和近期对话请模型判断合并重复、完成、放弃或调整；程序保存review结果。日复盘有DB claim，纯内存无claim时该定时路径跳过，不能说所有配置都自动运行。[^y-goal]

这补的是“想法不会因无人再问而永久挂着”，不是已具备任意复杂任务规划器。
