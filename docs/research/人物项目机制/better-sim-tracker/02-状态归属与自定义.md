## 状态究竟是什么、归谁

### 内置关系、当前情绪与内心一句话

**解决的问题：** 同一段关系不能每轮随机重猜，人物当前反应又不能永远等同于关系总体状况。

**输入结构：** 不是一颗“情感值”，而是 `statistics.affection[owner]`、`trust[owner]`、`desire[owner]`、`connection[owner]`、`mood[owner]`、`lastThought[owner]`。四维数值分别用来表示温暖/喜爱、可靠与安全感、吸引、联结；情绪是 15 项枚举之一，thought 是短句。关系默认技术值 50 不代表心理测量结论。[^src-1] [^src-2] [^src-3]

**归属：** owner 通常是角色名，同时有 entityId 影子桶解决同名/别名；当前 SillyTavern 聊天隐含“这个 user”。内置提示明确把 affection 等定义为角色对 user 的关系；部分 mood 提示也写作 toward user。它没有在该内置结构里显式表达 `(characterId, otherPersonId)` 二元关系键。不能把它直接说成“全平台一个人物对所有微信联系人的关系系统”。[^src-4] [^src-5] [^src-6]

**状态改变：** 模型给四维 delta、一个 owner confidence、新 mood/thought，程序计算：

```text
boundedDelta = clamp(modelDelta, -maxDeltaPerTurn, +maxDeltaPerTurn)
scale = (1 - confidenceDampening) + confidence * confidenceDampening
newValue = clamp(round(oldValue + round(boundedDelta * scale)), 0, 100)
newMood = confidence < moodStickiness ? oldMood : proposedMood
```

默认 maxDelta=15，dampening=.65，moodStickiness=.6。confidence 不是独立验证器估出的可信度，而是提取模型自己输出的数。手工 Retrack、AI/User 消息编辑会绕过 confidence damping/stickiness，但仍有数值范围/单次delta边界。[^src-7] [^src-8]

**消费者：** 注入模板说 mood 影响当轮表达，关系维度影响长期倾向；trust/connection 约束冒进亲密。程序没有把 trust<30 写成“禁止回复”；它把值与解释送给聊天模型。低中高区间和行为 guidance 是上游带有价值取向的提示规则，不是自然定律。尤其高 affection 默认会诱导 caring/concern/emotional support，这和我们之前不希望角色过度关心的体验有潜在张力，采用前应保留上游原文并单独比较效果，不悄悄改写。[^src-9]

**时间边界：** 在已核对的默认提取、数值应用、存储与事件入口链里，没有“过去十分钟自动把 Angry 衰减”的钟表步骤。这里的稳态是历史保留+confidence门槛+新回合修正。图表 moving average 也只是显示，不是情绪动力学。不能把这套机制等同于带衰减、心境基线、情绪事件核的系统。[^src-10] [^src-8] [^src-11]

### 情绪枚举也有硬编码语义折叠

解析器会把模型返回的非标准情绪词映射到固定枚举，例如 tired/fatigued/sleepy → Sad，worried/stressed → Anxious，annoyed → Frustrated，calm → Content。它因此不仅做JSON格式容错，也内置了“哪些感受算同一类”的工程选择。疲劳与悲伤并不天然等同；若我们有独立体力/环境状态，这种折叠需要作为对照实验中的明确变量。不能因为字段叫Mood就当作细致的人类情绪本体。[^src-12]

### 自定义字段与环境：不是只能追踪关系

自定义支持 numeric、text_short、enum_single、boolean、array、date_time。每项还包含 description、behaviorGuidance、defaultValue、maxDeltaPerTurn/enum选项/长度、trackCharacters、trackUser、globalScope、privateToOwner、showOnCard、showInGraph、includeInInjection 和 promptOverride。[^src-13]

例如可定义“地点=办公室”“疲劳=65”“正在做=赶报表”“手持物品=[水杯]”。这不是仓库替我们生成了生活系统；只是同一个提取/存储框架允许这些状态随文本更新。`globalScope=true` 用 `__bst_global__` 存一份场景状态，强制关闭 privateToOwner；“全局”指此聊天场景共享，不是所有账户、所有群聊的世界事实。date_time 提供叙事时间解析/相对推移等规格，不是现实日程调度器。[^src-14] [^src-15] [^src-16]

新增自定义字段在已有聊天中、某 owner 过去没有该值时，可先用默认值种下基线；但是第一份聊天 tracker、以及单用户提取有例外，立即根据当前文本提取。因此“所有 custom 第一轮永远只写默认值”的旧概括不准确。[^src-17]


## 场景人物、消息人物与身份连续性

标准模式从SillyTavern人物/群成员开始，最近发过言、活动持续窗口、手工inactive、离场词等影响active集合。这里“active”是场景/卡片是否活跃，不是人物当前 CPU 运行与否，也不是有无看见微信。英文离场词规则对中文场景的等效性没有测试证据。[^src-18] [^src-19]

非standard模式先让 resolver 区分**inScene**与**inMessage**：旁边未说话的人可能仍在场，而当前消息只实际推进一人的状态。解析结果携带alias/evidence/confidence；程序将owner映射为稳定entityId，动态模式还可materialize叙事人物。构造持久化快照时再次区分scene活跃与请求owner，避免某人一句话就清掉其他在场人，也避免无关人被本轮变化误伤。[^src-20] [^src-21] [^src-22]

registry保存在聊天metadata，带 introduced/lastSeen/lastActive/archived/deleted消息索引与生命周期历史；状态变更不仅靠当前UI显示。Dynamic Characters管理器可人工archive、restore到inactive、delete及改颜色；后续符合条件可再次active。自动archive默认关，开后按消息距离阈值，不是情绪遗忘或时间衰减。[^src-23] [^src-24] [^src-25] [^src-26]

要注意这不是通用社会关系图：它解决“同一聊天里到底有谁/当前谁被推进”，不直接解决“所有用户面对同一个人物、各自关系隔离且共享她的生活”。
