## 先抓住贯穿全项目的逻辑

它把聊天里已经发生的内容，转成一个**按消息和候选回复分支保存、可以人工纠正、又能送回下一轮模型的状态账本**。聊天模型仍负责说话；另一轮提取调用负责判断这段交流使关系、当前情绪和自定义状态发生了什么。程序限制变动、选定数据归属、保存历史，再决定哪些状态可被卡片、图表、提示词和宏读取。

因此它不是一个自行生活的完整人物 Agent，也不能简化成“给 LLM 加好感度”。围绕状态账本，它实际解决了人物归属、分支、重提取、手工改值、旧数据恢复、提取与回复的先后顺序、提示词可见性等问题。作者自述的产品目标是聊天内 relationship/state tracking；“状态账本”是本文依据源码整理的设计推断。[^src-1] [^src-2] [^src-3]

默认主线：

```text
SillyTavern 生成角色回复
  → 收到生成结束/角色消息落地事件
  → 定位这条消息和当前 swipe
  → 确定本次该跟踪哪些人物
  → 读取目标消息之前的同人物状态、最近聊天和有限历史
  → 提取模型建议增量/新值
  → 程序解析、限制、保留缺失字段
  → 写到该消息当前 swipe，同时更新恢复副本
  → 卡片/图表读取；注入器和宏为下一轮提供状态
```

这条默认链是**回复后评价，并约束下一轮**，不是先让情绪系统决定本轮是否回消息。可选 User Tracking 有另一条“先提取用户本轮状态、再重放原回复请求”的链，详见[用户状态先提取门闩](03-提取注入与生成协调.md#用户状态先提取门闩)；不要把它当作角色不想看消息或忙完再回复。[^src-4]
