## 核心不是一颗心情分数

它先问“这件事对我的目标、标准和预期意味着什么”，再产生有原因和对象的情绪。活动情绪与较弥散的 Mood 不同：对甲的生气可以有明确事件原因，整体心境可以受到影响，之后又影响下一次情绪形成。[^fm-map-appraise]

```text
事件 + 观察者 + 信念/目标
  → 评价框架产生变量
  → OCC 推导对应情绪
  → AddEmotion 结合阈值与 Mood
  → 保存活动情绪（原因、对象、强度、起始时间等）
  → Mood 受到反馈
  → 后续 Update 推进衰减
```

解释性数据视图如下，字段语义对应 DTO/活动情绪，但不是完整构造请求：

```text
active emotion:
  type: anger
  target: contact-a
  cause: event-42
  intensity: current strength
  activation time: host simulation tick
mood:
  diffuse overall value
```

同一原因的重评价、情绪阈值和已有心境共同决定最终状态；不是每回提到事件都无条件再加一次生气。原始接口、构造与衰减公式见源码。[^fm-detail][^fm-map-appraise]

## 时间与两个容易误用的入口

宿主 Update 增加 tick 并调用 Decay；tick 的物理时长由宿主决定。不能默认一次 Update 就是一分钟，也不能把只在用户说话时 Update 称为独立生活中的持续时间。[^fm-map-rpc]

完整 AddEmotion 会参与心境更新等路径；直接 AddActiveEmotion(EmotionDTO) 的行为不同，DTO 构造路径也未建立同样的标准衰减基准。若跳过评价，只塞 intensity 字段，并不能宣称已接入完整系统。需要走完整链，或验证自定义适配在这些方面等价。[^fm-map-appraise][^fm-detail]

## 如果接大模型，谁还负责什么

模型可以成为语义解释来源，但固定源码没有现成的自由中文 LLM 接口。可研究让模型生成结构化评价材料，通过公开 IAppraisalFrame 接 OCC 推导，或用可配置评价规则。两种接法都需要验证，本文没有实现。

这个候选的价值是有原因、有对象、可随时间延续的状态；它不自动解决多人隐私、真实工具成功、收件箱注意范围、重复外部事件及并发持久化。target 是情绪对象，不能当访问权限。私人冲突影响心境与向另一个人透露冲突细节是两个问题。[^fm-detail]

与 Emotion Engine 比较，应分别验证语义判断、连续状态和最终行为，而非只比哪个变量更多。它们有职责重叠，尚无证据支持把两个引擎叠在一起就一定更好。
