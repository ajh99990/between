# 人物主体、日程调整与情绪状态的进一步研究

用途：固定版本的日程、离线消息与情绪机制补查。初次核查：2026-10-22；机制扩查与修订：2026-10-23。上游实现证据继续保留；我方采用状态统一见 [当前 Agent 方案](../plans/人物主体Agent设计方案-v0.1.md)。

接续[四个人物系统的核心设计逻辑与运行主线](四个人物系统的核心设计逻辑与运行主线.md)，补查 Yuralume、eros-engine、Emotion Engine、BetterSimTracker 的日程调整、注意边界及情绪更新实现，并扩展核查 FAtiMA 与 WASABI。

本轮做概念讨论、源码研究及候选组件离线机制验证。没有修改运行代码、角色提示词、现存服务或用户数据，没有进行真实模型对话试验。以下演算与情境用于解释机制；实际离线测试单独注明，不是实测聊天记录。

## 1. 研究问题与当前采用入口

本研究解释三个问题：聊天如何改变日程且不改写过去；没有接触到消息与看过后不愿回应有何区别；情绪引擎究竟增加了什么。它们为当前 Agent 方案提供依据，不构成已采用上游阈值、公式或整套工具协议的证明。

用户已确认人物是主体，重要当前事实持续可用，过去日程不可改写，自主暂不看消息时先保存在收件箱。最新补充明确允许并要求评估成熟的情绪/情感系统，不能从“模型决定行为”推导出数值与程序规则一律禁止。共享人物、逐人关系及真实平台日常的决定见当前方案第 2 节；具体算法与系统选型仍待评审。

## 2. Yuralume 怎样让聊天改变日程

核查版本：`Yuralume/yuralume-core@6996b152604e83a1cf6344cd236a9b9456f47bba`；本轮按此固定提交核查，不将其等同于所有后续版本。

### 对话里的约定如何变成下一次会读到的安排

假设原来今晚 19:00 看电影，聊天中双方改约 20:00。Yuralume 的正常回复结束后，会让后处理模型读取本轮交流及当日活动 ID 清单，提出增、删、改建议。没有明确日程变化时，提示要求返回空列表。修改已有活动必须引用已知 ID；服务随后把有效字段写回日程，后续当前活动定位和规划再读取保存结果。这里的语义识别由模型完成，存储、ID 核对、时间格式等由代码完成。[^y-post][^y-parse][^y-write]

它也考虑“明天见”这种跨日约定：未来某天尚未有完整日程时，先保存约定；以后规划整天时，把约定作为已有条件，围绕它补齐生活。这比每次重新规划后再希望模型记住约会更明确。[^y-write]

不过，当前对话后处理只得到今天已有活动的 ID，所以它允许未来日期的新增，不能通过这条模型解析路径任意修改未来已存在的活动。提示特意要求未来共同约定在新增时写对确认状态。这是接口视野的限制，不能把它说成已经提供了任意日期的完整日程协商能力。[^y-post][^y-parse]

此外，源码还有日程查询、手动新增、修改、删除及整日重生成的 HTTP 管理接口。**本轮核到的聊天主线是“后处理模型提出调整 → 日程服务保存”；它不是我们所设想的 Agent 自主调用日程 MCP。** 工具接口的设想可以借这条读写逻辑，但两者不能混称。[^y-api]

### “过去不能改”尚不是它严格兑现的规则

对增删改服务而言，决定一项旧活动能否被直接修改的主要保护是 `memorialized` 标记。直接修改和删除会跳过已标记活动。单独核查的新增路径检查时间格式、结束晚于开始等，但没有用当前时刻拒绝已过去的时段；已有日程的过去日期也没有在这一服务入口统一禁止变更。[^y-write]

这带来具体区别：**现在已是 15:00，不代表 09:00 的活动一定已经被锁住。** 如果上午活动尚未被记忆化，增删改入口并未仅因其时间已过去而拒绝。聊天路径会尝试在后台记忆化已结束活动，但它不作为回复前必须完成的屏障；后台尚未完成或失败时，保护状态可能尚未产生。这个结论是入口条件与异步顺序的源码推断，不是已经观察到真实聊天改写历史。[^y-memorialize]

因此，不能把“正常情况下后台会保护许多已结束活动”写成“已经实现过去不可改”。我们后续若采用日程工具，用户提出的时间约束必须是服务端执行的规则，不能仅依靠提示词自律，也不能用是否已生成记忆代替真实时间边界。

独立复核还发现，该标记也不是跨入口的绝对保护：整日重生成只在原日程尚未完整规划时传入约定种子，没有统一把已规划日程的过去部分合并回去；重叠整理还存在已标记旧项被新活动完整覆盖后跳过的分支。因此应借鉴其局部保护思想，而不能照搬并宣称历史已经不可变。这些是静态路径核查，未运行真实场景复现。[^y-history-boundary]

当前方案已提出分别保存过去计划、实际发生与当前解释，从当前时刻调整进行中活动的后续部分，具体接口仍待评审。遇到邀约冲突，由模型结合占用信息选择协商、拒绝或调整，程序不替人物选择对象或自动取消约定。

## 3. Yuralume 忙碌判断：从日程到补回的完整过程

### 先理解它在解决什么

Yuralume 是本次调研的开源人物陪伴项目。以下解释属于其固定提交 `6996b152604e83a1cf6344cd236a9b9456f47bba`，依据源码中的规划、聊天和补回入口；不是我方已决定采用的实现。

假设她 14:00–15:00 在赶报表。14:10 有人发消息，她既可能抽空答完，也可能先说一句、稍后再答。**这个机制的目标，是让事先已有的活动影响聊天节奏，并把“稍后回你”变成系统会继续处理的事情。** 它不是一种情绪算法，也不是根据一句“我很忙”直接启动计时器。

需要分清三个角色：

| 环节 | 回答的问题 | 实际承担者 |
| --- | --- | --- |
| 日程规划 | 她这时在做什么，回消息有多困难？ | 规划模型生成活动和忙碌值，程序保存并按时间定位 |
| 来信处理 | 在这个处境下，这条消息要现在答完，还是先简短说明、稍后补回？ | 程序筛选是否调用专用判断模型；模型阅读消息和背景选择 |
| 后续执行 | 说过稍后回，到了时间要怎样继续？ | 数据库保存未完成事项；后台检查条件，再调用补回模型 |

三个模型角色是三类任务，不意味着必须部署三种基础模型。规划一般在日程缺失、种子待补全或计划需重建时发生，有可用日程则读取；不是每条消息重新编一天。真实调用和写入可沿规划服务、规划器、聊天分支及补回器核查。[^y-busy-origin][^y-wiring][^y-busy][^y-followup]

### 忙碌值从哪里来

`busy_score` 的源码定义是这段活动中**回消息的成本**，范围 0–1。它不是报表完成百分比、CPU 使用率、不喜欢某个人的程度，也不是实时传感器测量。日程模型获得人物资料、日常规律、近期活动、约定和已有背景，在规划活动的 JSON 中填写这个估计。程序解析、限到有效范围，保存到 `ScheduleActivity`。[^y-busy-origin][^y-busy-entity]

上游规划提示按以下范围指导模型（这里是解释性转述，不是提取或改写提示词）：[^y-busy-origin]

| 范围 | 规划时的大致含义 |
| --- | --- |
| 0–0.3 | 容易查看并回复，如放松或散步 |
| 0.4–0.6 | 在做事，但通常仍可抽空回复 |
| 0.7–0.8 | 不方便长聊，需要看具体消息是否值得打断 |
| 0.9–1 | 很难接触手机，例如驾驶或考试 |

模型漏填或输出不可解析时，还有代码备用表，例如 `work=0.55`、`meeting=0.8`、`sleep=0.95`；无法识别类别则为 0.4。因此不能说这个数值永远是模型判断，更不能把它当现实已验证事实。[^y-busy-entity]

### 三种数据各保存什么

以下为同一自拟案例的简化表示；真实字段来源已核对，省略附件、参与者与部分审计信息。时间以 Asia/Shanghai 表示，源码持久化使用带时区的 UTC 时间。不是运行得到的模型输出。

**活动记录**在收到消息之前就可存在，回答“此刻安排是什么”：

```json
{
  "id": "report-1",
  "start_at": "2026-10-22T14:00:00+08:00",
  "end_at": "2026-10-22T15:00:00+08:00",
  "description": "赶报表",
  "category": "deadline",
  "location": "办公室",
  "busy_score": 0.8
}
```

当前活动通过 `start_at <= now < end_at` 查找。14:10 落在这段活动里；日程内容和 busy_score 不会因有人发消息自动重新测量。[^y-busy-entity]

**本次决定**是专用模型这次的判断，回答“怎么处理这条来信”。上游模型原始输出为四行文本，适配器解析后才形成 `BusyDecision`，不能把下面 JSON 写成上游原始协议：[^y-decider][^y-busy-parse]

```text
模式：延後
短回覆：我这报表还没弄完，三点忙完回你。
延後到：15:00
原因：赶报表
```

```json
{
  "mode": "brief_defer",
  "brief_reply": "我这报表还没弄完，三点忙完回你。",
  "defer_until": "2026-10-22T15:00:00+08:00",
  "defer_reason": "赶报表"
}
```

**待回复记录**是持久化的未完成事项，回答“答应了继续处理哪条消息、此前说过什么、什么时候重新检查”：[^y-pending]

```json
{
  "id": "follow-up-1",
  "character_id": "person-1",
  "conversation_id": "conversation-a",
  "kind": "busy_defer",
  "status": "queued",
  "activity_id": "report-1",
  "messages": [{"content": "晚上八点聊会儿？", "queued_at": "2026-10-22T14:10:00+08:00", "content_mode": "normal"}],
  "brief_reply": "我这报表还没弄完，三点忙完回你。",
  "defer_reason": "赶报表",
  "scheduled_for": "2026-10-22T15:00:00+08:00"
}
```

活动记录由日程规划/调整写入；本次决定由忙碌判断模型及解析器产生；待回复记录由聊天服务写入、后台补回器读取。`activity_id` 留下延期的原始依据，后台仍会重查当前活动，不只读取这个旧 ID。状态随处理变为 `resolving`、`resolved` 或 `cancelled`，失败可回到排队等待。

### 收到消息时，程序到底怎么走

先看正常配置、普通文字来信的主要路径。伪代码是按源码简化的讲解，不是逐字复用或我方实现；省略模型/存储未接通等工程检查。[^y-busy][^y-input][^y-pending]

```python
def on_message(message, now):
    old = find_queued_busy_follow_up(message.conversation_id)
    if old:
        append_for_audit(old, message)
        cancel(old)                       # 上游的特殊产品策略
        return ordinary_reply(message)    # 新来信不再重新走忙碌判断

    current = schedule.activity_at(now)
    if current is None or current.busy_score < 0.7:
        return ordinary_reply(message)

    # 0.7 只决定是否值得追加这次专用模型调用。
    decision = busy_model(
        person=character,
        activity=current,
        message=message,
        relationship=relationship_context,
        recent_dialogue=summary,
        recent_contact=recent_proactive_attempts,
        now=now,
    )
    if decision.failed_or_invalid or decision.mode == "immediate":
        return ordinary_reply(message)

    save_user_message_and_short_reply(message, decision.brief_reply)
    save_pending_follow_up(
        original_message=message,
        prior_reply=decision.brief_reply,
        reason=decision.defer_reason,
        scheduled_for=decision.defer_until,
        activity_id=current.id,
    )
    return decision.brief_reply
```

`ordinary_reply` 仍由普通回复模型生成，不是套一个固定答复。专用模型选择立即回复后，完整回答交给这条普通路径；选择延期时，它写的短回复就是本次对外文字。**0.7 是作者设置的调用门槛，代码注释解释为避免在容易回应时增加调用，并让后台释放采用对应条件；没有查到它是实测最优阈值的证据。**[^y-busy]

因此，同样的 0.8：

- 来信“晚上八点聊会儿？”时，模型可能先简短说明、晚点认真处理。
- 换成需要马上协调的消息时，模型可能选择立即回复，普通模型随后生成答复。
- 哪条消息实际会走哪条路径，需要真实模型验证；源码能证明存在这两种选择，不能证明判断质量。

模型输入同时含活动、关系及互动背景，所以“忙”与“值得为这条消息打断”被分开处理。原实现会裁剪摘要、来信和近期主动联系，这也会影响判断。提示还偏向让新关系、睡着后被唤醒等情况即时回应，这是作者的交互倾向，不是忙碌值自然推导出来的结论。[^y-input][^y-busy-prompt]

### 后台怎样把“稍后回”落实

保存的 `scheduled_for` 是**最早重新考虑补回的时间**，不是到点保证送达，更不是早已生成一条完整回复等待发送。[^y-release]

```python
def on_background_tick(now):
    for pending in queued_rows_with_scheduled_for_at_or_before(now):
        person = load_character(pending.character_id)
        if person is None:
            cancel(pending)
            continue
        if person.frozen:
            continue

        current, just_finished = read_current_and_finished_activity(person, now)
        # 这里只展示 busy_defer；scheduled_promise 另走一条路径。
        if len(pending.messages) < 8 and current and current.busy_score >= 0.7:
            continue                       # 仍在忙，下次后台检查再看

        if not mark_resolving_successfully(pending):
            continue
        reply = follow_up_model(
            original_messages=pending.messages,
            prior_short_reply=pending.brief_reply,
            delay_reason=pending.defer_reason,
            waiting_since=pending.queued_at,
            current_activity=current,
            just_finished_activity=just_finished,
            person=person,
            recent_dialogue=load_summary(),
            now=now,
        )
        validate_deliver_and_record_result_or_retry(pending, reply)
```

15:00 如果接下来已是较空闲的活动，或者没有当前活动，就有机会让补回模型重新组织回应。如果报表延长到 15:30 且忙碌仍为 0.8，后台会继续保留排队，稍后再检查。达到 8 条积压时可绕过这项忙碌门槛，其他阻断依旧有效；当前普通来信会取消旧事项，所以这个容量分支不能解释成“平常连发八条才会被理会”。这里只确认读取到已有八条记录时的释放分支，未验证当前常规消息路径如何累积到八条，不另推断有批量或离线入口。[^y-release][^y-pending]

**同一个 0.7 在两个地方承担不同作用：前台决定是否询问专用模型；后台则会直接阻止本次补回。** 上游已经是模型和程序共同影响节奏的混合机制。把它说成“全是代码决定”或“全是模型决定”都不准确。

### 哪些地方不能照着理想故事理解

- **已读后延期不等于未读收件箱。** 忙碌模型已经看到消息正文，才选择先回一句；这不能直接代替我们确认的“暂不看消息”机制。
- **延期检查不等于新的约会。** 15:00 再处理问题，不代表已答应 20:00 聊天。忙碌短回复路径跳过普通 post-turn，原问题出现“晚上八点”不保证自动新增八点约定。[^y-postturn]
- **缺失输出有代码默认值。** 延期时间无效时可回落活动终点/30 分钟后；过去的 HH:MM 会滚到明天，过去 ISO 时间则夹到至少一分钟后。短回复为空或过长会退回普通路径。这些不是模型自己做的语义选择。[^y-busy-parse]
- **有记录不等于可靠履约。** 上游先保存短回复，再保存后续事项；后者失败时仍保留短回复。完整可靠性还取决于后续存储、调度、生成与投递。[^y-pending]

可借的结构是：已有活动 → 针对来信判断 → 保存未完成事项与说过的原话 → 到时带新处境继续。哪些数值和门槛值得采用，留在方案里评审；这里解释上游真实做法，不先替我们选算法。

## 4. 忙碌与不愿回应可以互补，直接拼接现成策略会冲突

用户认可有限回应与争取回应的体验，这应作为后续设计的真实目标来讨论。它与自己的生活并不矛盾：她可能忙但愿意为这个人腾出一点时间，也可能很闲却暂时不愿交流。

为理解两套机制的关系，可以先区分以下问题。这是本轮提出的讨论方式，不是已经决定的软件模块划分：

| 问题 | 对人物行为的影响 | 源码对照 |
| --- | --- | --- |
| 她有没有接触到这条消息？ | 未看到内容时，不应按内容判断被冒犯或感动。 | Eros 离线分支在判断模型前结束；Yuralume 忙碌判断已把内容交给模型。 |
| 现在能否投入注意力？ | 开会、开车、深度工作与自由时间有不同打断成本。 | Yuralume 根据活动筛选，并交给模型作语境判断。 |
| 对这个人、这件事愿不愿意回应？ | 同样空闲，不同关系、边界和当下意愿仍可产生不同选择。 | Eros 的普通沉默规则或可选 PDE 判断作用于互动意愿。 |
| 这次怎样处理？ | 完整回复、简短确认、推迟、暂时不回，具有不同后果。 | 两项目都有部分选择，但不是同一套完整协议。 |
| 已经答应的后续怎样履行？ | “我忙完找你”产生一项后续事项；不能与从未承诺的沉默完全混为一谈。 | Yuralume 有待回复记录；Eros 离线结束本身没有自动补回。 |

例如同一句“在干嘛”：她没有看到时，尚无内容判断；她看到了但正在赶报告，可能简短确认；她空闲却不想继续这个话题，可能不回；她此前明确答应 16:00 联系，还需要面对这份约定。**这些选择可以共同支持人物主体性，不需要都压成一根忙碌值或好感值。** 约定怎样履行、是否可能失约仍需设计，不能由研究者替用户规定人物必须可靠。

实际拼接时至少有两处冲突：Yuralume 在已有延后事项时，因再次来信取消该事项并进入普通回复路径，会削弱原有等待；Eros 的离线硬阻断会使后面的模型根本没有机会根据消息内容选择打断。如果两层各自独立做沉默决定，也可能出现重复压制，或已经承诺补回却再次被普通稀缺性规则拦住。后两种是组合方案的风险推断，尚未实现或测试。[^y-busy][^e-offline][^e-ghost]

这两套上游机制解释了不同问题。当前方案已选择由模型决定查看与回应，由服务保存注意安排和后续责任；Eros 的默认增长、沉默公式及 Yuralume 的再次来信取消延期规则均不是已采纳的人物决策。电话等更强通知如何打断仍待讨论。

## 5. “手机静音，忙完集中看”与 Eros 现状的差别

核查版本：`etherfunlab/eros-engine@9715af2ce7d8524ca5ce8771059d436c31951977`。

这个类比抓住了它在普通离线路径中的重要特征：消息先保存，当前离线时跳过行为判断器和回复模型，不把这次环境造成的未回复计入同样的关系冷处理。这接近“暂时不进入人物注意”，但没有完整实现手机通知、已读或电话语义。[^e-offline]

有三点不能说成已经具备：

- **没有忙完自动批量处理。** 当前生成结束后，离线消息并未作为“到时间必须补回”的生成任务保留；正常队列把这轮 ghost 作为已完成处理。离线事件到期本身不触发一次补回。
- **后续可能读到旧消息，不等于保证完整批次。** 下一次正常生成读取聊天历史，查询不因 ghost 标记而排除这些用户消息；但历史经过条数窗口裁剪。另有“刚才离线期间收到过消息”的背景供下一次承接，任一后续非空助手文字即可让该机会结束，不检查是否逐项回应。
- **电话例外尚是我们的设想。** 源码中的实际绕过条件包括结构化当面动作或强制图片请求，不能把它们说成已有电话打断功能。[^e-queue][^e-history][^e-resume]

项目另有独立语音会话，其生活事件接入范围不同；这不等于已有“电话响起、人物察觉、决定接听或拒接、打断当前工作”的完整流程。已读字段也不能直接当成人物知晓状态：该字段只覆盖向可选判断模型派发当前消息的部分路径，旧消息后来进入历史并不会因此完整补记。[^e-perception]

我方已确认：人物自主暂不看消息时，普通来信先留在收件箱，查看前正文不得进入摘要、情绪判断或模型上下文。当前方案建议先提供概况，再按模型选择读取原文；查看不等于每条必回。具体工具协议和电话打断仍待讨论。

## 6. Emotion Engine 到底算什么，哪些仍由模型决定

核查版本：`pioneerjeff-labs/emotion-engine@e7fab5c3984a4885ac74c972d573b05b45a8c496`。

用户的质疑成立：**模型可以依据近期事件、当前处境和人物底稿判断感受，不必先有数值情绪引擎。** 而 Emotion Engine 推荐的接法本身也依赖模型作这项语义判断。它主要增加的是明确保存与更新后果的机制，不是独立理解世界的心理模拟器。[^ee-host]

### 一轮互动怎样经过它

继续用赶报告的例子。宿主先拿出此前状态，做适用的时间或轮次更新，将状态说明、人物和对话背景交给模型。模型判断这次催促是玩笑、求助还是施压，并给出回复和新的情绪值。推荐 API 伪代码让这两者来自同一次 `model_result`；写入通过后，宿主原样返回其中的回复，不再让情绪引擎改写它。[^ee-host]

三个值是愉悦 P、唤醒 A、坚定／边界感 D。**当前主写入入口接收模型／宿主提供的最终值**，限制其合法范围；并不是核心算法看一遍冲突内容，就必然算出唯一正确的感受。之后才用新旧差异计算短暂波动 pulse，并把事件解释、未解决事项等一并存下。[^ee-record]

确实还存在一条规则备用路径：按关键词选评价标签，再用固定变化量、已有信任和波动档位给出建议；宿主没有提供 PAD 时，原子更新入口可以采用它。它不能理解完整处境或可靠区分玩笑与讽刺，不能把这条备用建议描述成完整的情绪理解算法。默认 `light` 记录策略也不要求每句中性任务或泛泛赞扬都新写情绪，关系事件需宿主批准。[^ee-policy]

下次准备输入时，通用预览将当前坐标按阈值翻译为语气倾向，把 pulse 变成强度与标签，再带上少量近期记录。pulse 没有在这里自动叠加回 PAD，也没有直接控制某句台词。例如低 P 被概括为“防备”，本身就是作者选择的表达映射，不能等同于所有低愉悦情绪。Nora 示例另外携带关系意义和后续偏向；保存字段不等于所有宿主都会取出这些字段。[^ee-consumer]

因此，当前流程更准确地说是：**模型解释并给出感受 → 程序保留、衰减并整理为后续依据 → 模型再判断如何表达。** 上述 API 指南接法没有在“判断感受”和“说话”之间强制再走一次独立决策；另一份集成文档建议记录后生成或修改回复，那仍需宿主实际实现，不能写成引擎内置的必经步骤。[^ee-host]

### 程序真正增加的几类规则

| 内容 | 程序做了什么 | 没有因此得到什么 |
| --- | --- | --- |
| 当前心境 | 保存最终 PAD；按所选档位逐轮向基线回拉；适用入口按真实时间回落。 | 没有证明模型给的值就是人物合理感受，也没有保证每轮变化一定很小。 |
| 短暂波动 | 从新旧 PAD 差值产生 pulse，之后比心境衰减更快。 | 没有独立判断这次事件重要与否；新一次写入会产生新 pulse。 |
| 关系信任 | 宿主明确提交关系证据，结束匹配会话后按规则结算，控制重复消费。 | “道歉”或心情好转不自动证明可靠；证据是否成立仍由宿主判断。 |
| 记录边界 | 检查人物、关系、会话、事件身份及部分语义归属，保留解释和轨迹。 | 通过检查不代表解释为真，最终语言也不被该引擎强制验证。 |

这些机制能让保存过程可检查，也能让不同后果采用不同延续规则；其参数是工程选择，不能直接当成人类情绪规律。[^ee-record][^ee-time][^ee-trust]

一个仅用于解释公式的例子：采用 `steady`，假设 P 的人物基线为 `0.10`，此前 P 为 `0.10`，模型这次给出 `-0.40`。程序保存 `-0.40`，P 的差值 `-0.50` 被截为 pulse `-0.45`。下一次逐轮更新把 P 变成 `-0.40 × 0.92 + 0.10 × 0.08 = -0.36`，P 对应的 pulse 分量衰减到 `-0.081`。这不是程序理解“生气多久”，而是既定回拉与保留比例的结果；下一轮模型仍可给出新的最终 PAD 覆盖它。这里只演算一个分量，不是完整人物状态或聊天测试。[^ee-time]

另一个容易误会的地方是时间：逐轮 `pre_turn_decay` 不按真实间隔计算；会话启动或显式 `decay` 才有真实小时／天的路径。宿主若隔天仍只走同一会话逐轮入口，就不能宣称它已模拟了隔夜恢复。同样，按轮回拉意味着快速来回聊天也会触发多次回拉，这是程序策略，不是自然规律。[^ee-time]

### 与“把有限事实交给模型”的比较应如何看

外置状态的潜在价值在于：上次已接受的判断不会完全靠下一轮重新猜，可以明确保留未解决事项、复查某次更新的来源、规定哪些后果缓慢变化。它不能补出根本没有保存的生活事实，也不能修复宿主错误地把一句玩笑认作冒犯。

**文字状态可以作为对照，不能因此排除数值系统。** 例如可以保存“她还介意昨天临时取消，但认可了对方今天的解释”这样的文字及依据，让模型结合当前环境继续判断。评估数值系统的额外价值时应考察：是否比保留同样信息的文字状态更稳定、自然、容易纠错，而不能拿“有额外记忆和详细指导”与“完全没有这些背景”比较后，把提升都归给 PAD。

本轮核读的展示材料没有提供足以解决这个问题的效果证据：网页比较是预置台词及数值，最小 Agent 示例使用 mock；Nora 示例构造昨天的状态和低／高信任对照包，额外携带不同的关系意义与措辞指导，未形成同等信息条件下、可复现的真实模型对照评测。我们因此不能声称它已被证明优于上下文模型方案。[^ee-demo]

未证明聊天效果不等于没有复用价值，持久化、衰减、证据结算与状态消费者可以先做源码与离线机制核查。未来若进入对话试验，可以在同一人物、同一模型、相同事实与对话预算下，比较三种候选：仅事实和历史；再加可更新的文字状态；再加数值及其更新规则。重点看事件误解能否纠正、道歉是否抹去未解决问题、时间经过与来回消息数是否被混淆、以及真实措辞是否自然。这里仅记录对话比较标准，本轮未启动真实模型对话试验；离线机制测试见第 7 节。

### Emotion Engine：实测的工程价值与两个适配问题

在隔离临时副本、Python 3.14.6 下，执行固定提交的三个指定离线测试集：

```text
python3 -m unittest discover -s tests -p 'test_emotion_engine_utils.py'
73 tests — OK
python3 -m unittest discover -s tests -p 'test_mcp_server.py'
19 tests — OK
python3 -m unittest discover -s tests -p 'test_minimal_agent_example.py'
4 tests — OK
```

**合计 96 个指定测试通过**，覆盖状态和身份、幂等、关系证据、衰减及持久化/MCP 等接口；不是仓库全套测试，不调用真实模型，最小 Agent 使用 mock。锁、临时文件替换和备份等代码说明它并非只提供概念图。[^ee-tests]

第一个适配问题是**一个状态包同时绑定 `character_id + relationship_id`，其中同时有 PAD 和信任**。直接为每位用户建一份包，就会形成逐关系的情绪状态，源码没有自动把它们合成为人物整体感受。这个事实不意味着必须拆成全局心境：用户在 2026-10-23 要求保留共享、逐关系和条件外溢三条路线，见[方案第 2 节未决项](../plans/人物主体Agent设计方案-v0.1.md#明确保留的未决项)。需要比较复杂度、切换时的连续性与强烈事件对其他生活的影响，不能把上一轮的拆分建议视为已确认决定。[^ee-reuse]

第二个适配问题是**连续生活系统不能原样重复调用旧时间衰减命令**。临时纯内存探针给 P=-0.4、基线0.1、trust=0.5，最后互动设为一小时前，连续两次调用 `apply_time_decay`，实际得到：

```json
{"before": -0.4, "first": -0.3468, "second_immediately": -0.2993, "same_last_interaction": true}
```

两次连续调用之间没有等待，也没有单独测量间隔；代码仍按“距最后互动的一小时”衰减已衰减过的当前值；命令没有推进时间锚点。以上是实际标准输出；测试使用真实 UTC 时钟，未固定或 mock 时间。对应公式是 `decay = exp(-0.15 × (1-trust×0.5) × hours_since_last_interaction)`，然后将当前值向基线回拉。[^ee-time-repeat]

若用它支持无人聊天也持续生活，需独立的 `last_decay_at`、或从固定基准和累计时间重新求当前值，避免同一时长被重复计算；还要区分逐轮回拉与真实时间回拉。**上述探针揭示的是具体入口的集成风险，不推断全部入口都错误，也不否定整个情绪状态层。** 原有 96 个测试通过并没有覆盖这个连续调用情境。


在该固定源码根目录可以复查同一纯内存操作（不写状态文件、不调用模型）：

```python
import copy, datetime, importlib.util, json
spec = importlib.util.spec_from_file_location("ee", "scripts/emotion_engine_utils.py")
ee = importlib.util.module_from_spec(spec)
spec.loader.exec_module(ee)
s = ee.default_state("fictional-person", "contact-a")
s["personality_baseline"] = {"pleasure": 0.1, "arousal": 0.3, "dominance": 0.5}
s["emotion"] = {"pleasure": -0.4, "arousal": 0.7, "dominance": 0.6}
s["trust"] = 0.5
s["last_interaction_iso"] = (
    datetime.datetime.now(datetime.timezone.utc) - datetime.timedelta(hours=1)
).isoformat()
s1, _ = ee.apply_time_decay(copy.deepcopy(s), character_id="fictional-person", relationship_id="contact-a")
s2, _ = ee.apply_time_decay(copy.deepcopy(s1), character_id="fictional-person", relationship_id="contact-a")
print(json.dumps({
    "before": s["emotion"]["pleasure"],
    "first": s1["emotion"]["pleasure"],
    "second_immediately": s2["emotion"]["pleasure"],
    "same_last_interaction": s["last_interaction_iso"] == s1["last_interaction_iso"] == s2["last_interaction_iso"],
}))
```

### 扩展候选 FAtiMA：评价事件，再让情绪持续存在

新增核查 `GAIPS/FAtiMA-Toolkit@56b7cbd992f953cfe21a7b12cb1a0e6cdf6ccf9f`。FAtiMA 是有多年研究与应用历史的情感 Agent 工具集，作者论文讨论虚拟角色和社交机器人中的用例；固定 HEAD 的提交为 2024-05-31。它的历史应用证据不能当作当前维护活跃或中文陪伴效果证据。核心库目标 `netstandard2.0`，现有 NUnit 测试工程目标 `netcoreapp3.0`；本轮核读源码和测试，没有在本机运行。[^fatima-paper][^fatima-build]

它最值得参考的思路是：**人物先评价一个已感知事件与自身目标、标准的关系，再产生有原因、有对象的情绪；情绪影响较弥散的整体心境，心境又影响下一次情绪反应。** “评价”不是查找文本里的生气词，而是判断这件事对人物是否有利、对方行为是否值得认可。

实际主线如下：[^fatima-appraise][^fatima-state]

1. 宿主提供符号事件、人物信念及目标。完整 `AppraiseEvents` 入口记录事件，必要时更新属性类信念。
2. 规则评价器用事件模板和条件生成评价变量，例如 Desirability（对自己有利/不利）、Praiseworthiness（对行为的赞许/责备）及对象。
3. OCC 推导组件把这些评价组合为愤怒、欣喜、感激等情绪。
4. `AddEmotion` 结合当前 Mood 与该情绪的阈值、衰减参数加入状态池，保留原因及对象。
5. 宿主推进时间，状态池减弱各项情绪并更新 Mood；原有决策模块可读状态，接入大模型时也可将状态提供给它。

主要情绪记录包含：

```text
EmotionDTO {
  Type           // 情绪类别
  Intensity      // 强度
  Target         // 针对谁或什么
  CauseEventId   // 哪个事件引起
  CauseEventName
}
```

另有整体 `Mood`，范围为 -10 至 10。多个不同事件引起的情绪可以并存；匹配同一原因及评价键的重评价会替换旧项，不再给 Mood 叠加同一次冲击。这个局部规则不代替外部事件去重，也不代表重新解释事件后会完全撤销过去所有心境影响。[^fatima-state]

用“赶报表时被甲反复催促”说明。以下是机制演算，未经运行；数字为自拟配置，不是心理测量：

- 宿主/模型解释为这次催促妨碍目标，且不认可甲的行为，提供 `Desirability=-6`、`Praiseworthiness=-4` 和对象甲。
- 上游复合愤怒计算可得潜在强度 `abs(-6 + -4)/2 = 5`。假设原 Mood=0、人物愤怒阈值=1，这两个值及前面的 -6/-4 都是自设案例。上游公式扣除阈值得到强度4；源码默认情绪对 Mood 的影响系数为0.3，因此负向情绪在此例使 Mood 为 `0 - 4×0.3 = -1.2`。0.3 是上游默认，不是本次测量或我方已采纳参数。
- 下一次模型可同时看到“对甲这次催促的愤怒4”“整体心境-1.2”和另存的关系/约定，选择怎样行动。情绪模块本身没有“愤怒4就拒聊”的必要规则。[^fatima-formula]

随后甲道歉，宿主仍需判断道歉意味着什么。若评价为新的积极事件，可以产生积极情绪，旧愤怒继续按自己的原因和时间演化；不是遇到“对不起”就清零。若新信息证明原先误解了甲，应修订对原事件的评价，不能只新增一笔道歉奖励。长期信任也应另看证据，不能由 Mood 回升自动代表。

**这更贴近我们想研究的“事情过去了，感受仍有余波；对甲有意见，不等于对乙也失去信任”。** 是否能最终表达得自然，还取决于事件解释、状态参数和模型如何消费，未取得中文聊天效果证据。

### FAtiMA 的具体接入限制

- 它没有现成的自由中文/LLM 评价适配器，内部默认构造规则评价器。可研究动态规则/结构化事件，或用公开 `IAppraisalFrame` 接 OCC 推导链；不能声称配置一个模型地址即可使用。候选接法是模型提供语义评价、引擎维护连续后果、模型作情境行动判断，不强制一起采用原规则行为决策器。[^fatima-appraise]
- 默认情绪半衰期基准为 **15 ticks**、心境为 **60 ticks**。不是15秒/60分钟；原包装器 `Update()` 增加一次 tick。我们要用一个人物共享的实际时间推进，不能按甲乙总聊天轮数让心情更快消退。[^fatima-time]
- `AddActiveEmotion(EmotionDTO)` 直接注入路径与完整 `AddEmotion` 路径不同。前者不执行完整的心境更新，且 DTO 构造路径未设置标准衰减基准；不能绕过评价链，只填一条强度就宣称完整接入。应走完整链或明确验证等价适配。[^fatima-state][^fatima-formula]
- `Target` 是情绪对象，不是访问权限；隐私、关系隔离、持久化并发与外部事件去重仍由宿主负责。不能把甲的私聊原因全文交给乙。
- 规则测试说明计算与序列化可检验，不保证一套统一阈值适合任何人物。作者工具研究也讨论了使用者理解情绪建模的困难；采用库不免除事件与参数设计。[^fatima-usability]

### WASABI：有源码的动力学对照，暂不列首选

核查 `CBA2011/WASABIEngine@c1dbd5f8a2fcf95c3f60f222fd61ef20c272a1dd`，固定 HEAD 为 2017-08-06。它是实际 C++ 情感动力学实现：宿主给正负冲击，持续更新快变情绪、慢变心境和 PAD/情绪激活输出。冲击来自谁、为什么如此、是什么事件，不由该动力学核心理解。现有 CMake 要求 Qt5；本轮未编译运行，也未找到足以证明现代工程维护质量的测试证据。[^wasabi]

它适合比较“无人聊天时仍持续演化”的机制，但当前 FAtiMA 对事件原因、对象及评价的支持更符合本轮问题，建议优先级较低。ALMA 的人格/心境/情绪资料可继续追踪，本轮未完成可用源码版本核验，不把它列为已取得的可复用库。

**建议把 Yuralume 的事件情绪层与 Emotion Engine、FAtiMA 一起比较。** 2026-10-23 的机制扩查补出了前轮遗漏的事件聚合、证据与实际消费者，替代此前只优先比较 EE/FAtiMA 的建议。EE 偏宿主持续状态协议，FAtiMA 偏评价与对象，Yuralume 提供已接生活和聊天的事件链；它们存在职责重叠，应先分别验证，不先堆成多套引擎。这是研究建议，尚未决定采用、移植或开展真实对话测试。
