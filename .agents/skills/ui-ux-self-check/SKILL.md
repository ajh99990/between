# UI/UX 七项自查

把 AI 原型当成待验收草稿。让原型从“漂亮截图”，变成“可被正确实现的产品”。

七项清单及其问题、示例和提示整理自用户提供的“任天真AI设计室｜AI 生成 UI 界面：7 项 Agent 自查清单”。检查流程、证据要求、优先级和输出格式是为 agent 执行补充的约定。

## 使用时机与范围

- 在完成本次 UI/UX 设计、交互原型、页面或组件实现后，提交最终交付说明前执行；用户明确要求自查或评审时也执行。
- 检查本次交付涉及的页面、组件、状态及其关联的核心任务路径。小范围修改重点检查受影响部分；七个维度都要说明覆盖情况。
- 沿用用户已经确认的需求、品牌、设计系统和交付阶段。把清单作为判断依据，不把某种风格、单一主按钮、18 字长度或全部状态一律变成硬性产品要求。
- 纯截图、静态设计、可交互原型和可运行产品的可验证范围不同；按当前交付阶段评审。

## 检查流程

1. **明确对象与核心任务。** 从当前任务和产物中确定目标用户、最重要的动作、入口、完成条件及本次范围。记录实际页面、组件、路由或文件；缺失的业务信息明确标注，不自行假设。
2. **先跑核心任务。** 先跑一遍用户的核心任务，不要先评价“好不好看”。有可运行界面时，实际查看渲染结果并走通相关操作；只有设计稿时，沿页面与状态说明推演。代码检查可以补充证据，不能替代对实际视觉和交互的验证。
3. **逐项核对下面七项清单。** 每发现一个问题，都问：会影响用户、评审，还是开发？把“感觉不对”改写成明确可改的检查项。按既定目标设备和尺寸检查，并在本地预览、测试数据或设计副本中验证适用的长内容、空数据和失败状态。
4. **记录证据与覆盖限制。** 用页面位置、组件名、文件位置、实际操作结果或截图位置支撑判断。区分实际观察、代码推断和未验证内容。工具或环境不足时，继续检查可验证部分，并记录缺少的证据与补验方法；不要把未验证项目写成已通过。
5. **在当前授权范围内处理问题并复查。** 若自查是正在进行的设计或实现任务的一部分，修复明确且属于原任务范围的问题，并重查相关项及受影响的核心路径。若用户仅要求评审，输出问题和建议。需要新增业务规则或扩大范围的事项列为待确认；已有授权的常规修复无需重复请求确认。
6. **输出检查结果。** 说明本次实际验证范围、七项结论、问题优先级、需补页面或状态、已修复项及仍待验证的内容。没有发现问题时如实说明，无需为凑数制造问题。

## 七项检查清单

### 01｜核心任务闭环：核心任务真的闭环了吗？

第一次使用的人，能否完成“最重要的那个动作”？

- 用户从哪里进入？第一步该做什么？
- 每一步是否说明了“为什么要做”？
- 完成后有没有清晰结果与下一步？
- 中途退出后，用户能否继续完成？

例：午餐推荐产品不只要“展示卡片”，还要完成「输入限制 → 看懂理由 → 做出选择 → 去下单」。

### 02｜信息层级：信息层级一眼清楚吗？

用户能在 3 秒内看出页面主任务和主按钮吗？

- 一个页面是否只有一个主行动？
- 标题、解释、数据、按钮的阅读顺序合理吗？
- 次要信息有没有抢走主任务？
- 用户是否需要思考“我该点哪里”？

AI 常见问题：每张卡片都很突出、每个按钮都像主按钮，用户反而无法决策。

### 03｜状态与异常：主页面之外，状态补全了吗？

如果操作没有成功，用户会看见什么？下一步还能做什么？

- 首次使用、空状态、无内容
- 加载中、AI 执行中、进度反馈
- 网络失败、无结果、内容生成失败
- 权限不足、额度用完、内容过长
- 完成、取消、撤回、过期

AI 最容易漏掉的不是主界面，而是用户真实会遇到的“没有按计划发生”。

只检查当前业务和交付范围适用的状态；例如没有 AI 执行或额度机制的产品，应注明相关状态不适用。

### 04｜真实内容与数据：换成真实数据，页面还成立吗？

不要只看 AI 的英文短句和两位数金额。请用最复杂的数据压一遍。

- 18 字中文标题会不会截断？
- 长地址、商品名、多标签会不会拥挤？
- 大金额、异常时间、空数据是否清晰？
- 没有配图时，结构还能不能成立？

找一页最复杂、最脏的数据替换进去。它比完美示例更接近上线后的真实画面。

没有可用真实样本时，使用符合已知业务约束的构造数据，并明确标注。18 字是原文的检查示例，具体边界以实际内容为准；截断是否有问题取决于信息是否仍可理解和获取。

### 05｜视觉一致性：是产品感，还是 AI 默认审美？

视觉有没有服务任务与品牌，而不是复制“高级感模板”？

- 颜色是否有业务含义，而非随手渐变？
- 卡片、圆角、阴影是否有层级职责？
- 字体、间距、图标、按钮是否属于同一系统？
- 去掉装饰后，核心信息还清楚吗？

紫蓝渐变、玻璃卡片、满屏悬浮标签不一定错；错在它们没有理由，只是默认答案。

按现有品牌、设计规范与使用情境判断，不能仅因个人审美偏好判定设计有问题。

### 06｜交互可控性：能点，不等于交互成立。

用户知道点击后发生什么，也知道怎么改、怎么停吗？

- 点击后是否有即时反馈？
- 高风险操作是否需要确认？
- 用户能否返回上一步修改？
- AI 执行中是否说明进度与依据？
- 失败后是否有明确恢复路径？

好的 AI 交互不是显示“正在思考”，而是让用户始终知道：发生了什么、我还能控制什么。

检查可见的执行阶段、结果依据和可用控制；产品未提供的进度或依据应标记为缺失，不编造执行过程。

### 07｜交付与可实现性：别人接手后，还能继续做吗？

这份原型交给产品、研发、测试后，他们知道怎么做对吗？

- 页面和组件是否清楚命名？
- 相同模块是否真的复用？
- 关键规则、尺寸、动效、状态是否有说明？
- 有没有区分“效果示意”与“必须实现”？
- 有没有提前标出实现风险与待确认项？

好交付不是让别人“看懂稿子”，而是让别人能在不同条件下把它做对。

复用、规则和状态说明可以体现在设计组件、代码、类型、测试或现有文档中；按交付阶段寻找证据，不要求为已有明确实现重复写一套文档。

## 判断与优先级

每个维度使用以下状态；同一维度可同时存在已发现问题和待验证内容，需分别说明。

- **已通过**：本次范围内的适用检查项已有足够证据。
- **发现问题**：有可定位的缺陷，写出触发条件、影响及修复方向。
- **待验证**：材料、业务规则或运行环境不足，写出缺少什么、如何补验。
- **不适用**：当前业务或交付范围不涉及，给出具体原因。

优先使用项目已有的优先级标准；没有时使用：

| 优先级 | 判断依据 |
| --- | --- |
| P0 | 会造成严重且不可逆的损失或错误操作，需要立即处理。 |
| P1 | 阻断核心任务、关键失败无法恢复，或交付缺失导致核心行为无法正确实现。 |
| P2 | 可以完成任务，但明显增加理解、操作或实现成本。 |
| P3 | 不影响任务完成的局部一致性或细节优化。 |

优先级依据实际影响和触发条件，不以视觉显眼程度排序。信息不足的事项标为待验证；不要凭猜测赋予已确认缺陷的结论。

## 输出格式

用用户的语言输出，中文为默认。遵循用户已有的报告格式；没有指定时采用以下紧凑结构：

1. **检查范围与结论**：产物、核心任务、交付阶段、实际检查的页面和状态、验证方式及限制。结论限定为“本次范围内通过”“需修改”或“证据不足，待验证”。
2. **七项概览**：七项各占一行，列出状态、关键证据或问题编号。通过项可简述，待验证和不适用项必须说明原因。
3. **问题清单**：按优先级排序，每个问题包含下列字段；没有问题时省略空表。

| 编号 / 检查项 | 优先级 | 页面或组件 / 证据 | 问题与触发条件 | 影响 | 修改建议 | 需补页面 / 状态 | 修复与复查状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |

4. **未完成事项**：列出仍需补充的页面、状态、业务决定和验证证据；已解决的问题记明修改及复查结果。

相同根因跨越多个维度时合并问题，引用相关检查项。建议必须能落实到明确页面、组件、文案、规则或状态，避免只写“优化体验”“提升高级感”。

只有本次范围内适用项均有足够证据且无未解决问题时，才写“本次范围内通过”。存在已确认问题时写“需修改”，存在证据缺口时同时说明“待验证”；不要用一个笼统的“全部通过”掩盖限制。

## 调用示例

> 完成界面后，使用 $ui-ux-self-check 做七项自查，修复本次任务范围内的问题，再给出检查结果。

> 使用 $ui-ux-self-check 评审这份原型，逐项输出优先级、问题、影响、修改建议，以及是否需要补页面或状态。信息不足时明确说明，不要自行假设。
